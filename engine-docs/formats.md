# Version-one workspace formats

Machine-written documents begin with one YAML mapping between `---` lines, followed by Markdown or preserved Canvas HTML. Use `schema: 1`; duplicate keys, unknown fields, and YAML aliases in the header are rejected. Everything after the closing delimiter is body content, including text that resembles YAML. Decimal scores may be written as ordinary finite numbers (`12.5`); quote them when a spreadsheet or other tool might rewrite them. Do not use Markdown tables as machine data.

Folder names: **Source** is the development checkout and starter templates; **Install** is the local runnable CE-SE folder; **Sync** is an optional dedicated locally accessible OneDrive/Google Drive directory for authoritative teacher rules. With no binding, files stay in Install. Logical workspace paths for teacher instructions, playbooks, root .md/.txt guides (except product README.md) and context references resolve to Sync when configured. `context/courses.md`, `context/students.md`, course work, private state, Engine and launchers stay in Install. MCP workspace tool names and `--workspace` retain that internal spelling; `--workspace` always selects Install. The provider synchronizes Sync; CE-SE directly reads and edits those files without replication.

## Settings

`context/courses.md` contains `schema`, the HTTPS Canvas `instance` origin, `aliases`, optional `module_hint`, and `courses`. Each course has a unique `nickname`, positive Canvas `id`, `current` scan flag, and optional IANA `timezone`. The clean starter has an example origin and an empty course list; replace the origin during setup.

`context/grading.md` contains `schema`, optional `voice`, and optional `feedback_guidance`. `context/students.md` contains `schema` and `notes`. Each note may identify a student by stable `student_ref`, or by unambiguous `name` and optional `course`, and has a required `note`. These are teacher preferences and private context; neither is included in rendered student feedback. `context/school-calendar.md` contains `schema`, IANA `timezone`, inclusive `start_date` and `end_date`, `non_school_dates`, and optional `non_school_ranges`. It is reference data the agent uses to work out school-day lateness (the Engine does not read it); update its coverage, closures, and make-up days. Early-release dates count as full student dates.

## Quiz file (QuizForge)

`push-quiz COURSE FILE` reads a **QuizForge v3.0-json** file in a `<QUIZFORGE_JSON>` envelope or as bare JSON. The supported contract here and `examples/synthetic-quizforge-mixed.md` are embedded and available through `engine_reference` (`formats` / `examples`) or `help formats` / `help examples`; external QuizForge design references are optional. Types that become New Quiz items: `MC`, `MA`, `TF`, `NUMERICAL`, `FITB` (open entry, dropdown, word bank; up to 3 linked blanks), `MATCHING`, `ORDERING`, `CATEGORIZATION`. `STIMULUS` is not creatable in Canvas, so its HTML is copied into each item that names it with `stimulus_id` (an item inside a STIMULUS..STIMULUS_END span without `stimulus_id` is an error). `ESSAY` and `FILEUPLOAD` also become New Quiz items (written responses; no answer key, `scoring_algorithm` "None", points from `points`). `ESSAY` accepts optional `word_limit_min` / `word_limit_max` (whole words, student-visible limits). `FILEUPLOAD` accepts optional `accepted_formats` (for example `["pdf", "docx"]`, which restricts the upload types). Fields `rubric_hint`, `length_guidance` and `notes` are private design notes and are never sent to Canvas; the agent can use rubric hints to author an explicitly attached rubric or local scoring basis, while anything students must see goes in `prompt`. A rationale on a written item is refused. New Quizzes, including these written items, are open for authoring, use and scoring within supported limits: explicitly scoped `pull-work COURSE QUIZ_ID` reads written work for comment-only assessment; see Student operations below. The teacher enters written-item points in SpeedGrader. Canvas Live (CS8, 2026-10-10) stored both item types, their points and the word limits and accepted types as sent; whether students see the limits enforced has not been viewed yet. Rationales become per-choice (`MC`/`MA`) or neutral item feedback.

The root needs `title` and `items`; optional `version` or `quizforge_version`, `instructions` (HTML), `metadata`, `notes`, `rationales`, and hub fields are accepted. Every question needs `type`, `prompt`, explicit nonnegative `points`, and preferably a unique `id` (required to attach rationales). `MC` / `MA` use `choices: [{"id":"a","text":"Answer text","correct":true}, ...]`: MC has exactly one correct choice; MA has at least two. `TF` uses `answer: true` or `answer: false`, a JSON boolean. `ESSAY` has no answer key. Unknown item or choice keys warn, naming the item/choice and pointing here; `metadata` and teacher `notes` are known fields. Inline `rationale` on an item or choice is an error: place feedback in the root `rationales` array, outside `items`:

```json
"rationales": [
  {"item_id": "q1", "choices": [
    {"id": "a", "rationale": "Explain the correct choice."},
    {"id": "b", "rationale": "Explain the distractor."}
  ]},
  {"item_id": "q2", "rationale": "Explain the true/false answer."}
]
```

MC/MA feedback matches choice IDs; omitted choice IDs use uppercase `A`, `B`, etc. Other auto-scored items use the entry's `rationale` as neutral feedback. Review shows recognized student feedback separately from questions and the teacher answer key. Push does not read item feedback back, so a successful write is not proof of stored feedback or student rendering.

Differences from the QuizForge contract: every scored item needs an explicit `points` value (the Engine never invents points), and the quiz ID is kept in a sidecar `FILE.cse.json` so an interrupted push resumes the same quiz and adds only the missing items. A New Quiz with the same title that has no sidecar blocks creation (it may be an unfinished push): rename the new quiz or point the sidecar at the existing one. Em dashes in student-visible text become " - ".

Quiz settings and assignment settings go in `metadata.canvas`; unknown keys are rejected by local validation, review and push. Quiz: `shuffle_answers` (default true), `shuffle_questions`, `access_code`, `allow_multiple_attempts`, `allowed_attempts` (whole number greater than one, `-1`, or `"unlimited"`), `score_to_keep` (`highest` default, `latest`, `average`, `first`), `build_on_last_attempt`, `attempt_cooldown` (minutes), `has_time_limit` with `time_limit_minutes`, `calculator_type`, `one_at_a_time` with `allow_backtracking`, `hide_results`. For a single attempt, omit `allowed_attempts` and the multiple-attempt settings. For multiple attempts set `allow_multiple_attempts: true`; `allowed_attempts` then sets the limit (omitted means unlimited). An explicit limit without the enabling flag, or a limit of one with the flag, is rejected rather than ignored. Review displays effective requested settings, not stored Canvas readback. Assignment (applied only after every item is in): `due_at`, `unlock_at`, `lock_at` (RFC3339), `assignment_group_id`, `post_to_sis`, `published` (default unpublished), `module_id` (an existing module). Publication happens after requested module placement succeeds; the existing sidecar supports resumption on failure. Results show students feedback and correct answers after the last attempt unless `hide_results`; Canvas shows nothing if result viewing is left unset.

Presentation: every `<pre><code>` block in a prompt (or an inlined stimulus) is re-rendered as a dark Monokai code box with inline-styled colors, Python rules by default. A block marked `class="language-xyz"` for another language keeps the box but is not colored. Prose, poetry `<div>`s and inline `<code>` are never changed. An item's `metadata.teks` (one code or a list) appends a small muted "TEKS: ..." label to its prompt.

No automatic local-image import or module/group lookup by name. Authored image HTML may use uploaded Canvas file IDs; see native link examples below and verify its saved appearance and access in Canvas.

### Differentiated hub (quizzes)

Hub is the only differentiation style: one quiz, one gradebook column, the same questions for everyone, plus restricted support pages. Add `"differentiation": "hub"` and `"tiers": [{"label", "tag", "title" (optional), "supports" (HTML)}]`. `tag` is the exact name of a Canvas differentiation tag (a non-collaborative group). Each tier becomes a Canvas Page titled `<quiz title> - <tag>` (or `title`). The quiz `instructions` must contain exactly one `{{tier:LABEL}}` link destination per tier, for example `<a href="{{tier:Silver}}">Silver supports</a>`; the Engine replaces each with the verified page path. `"differentiation": "bridge"` is refused. The bound links go in the quiz `instructions` field and the sidecar keeps `tier_pages` beside `assignment_id`.

Order of work: validate; create each page unpublished; restrict it to overrides and re-read; assign the tag (or, if no tag has that name, leave nobody assigned and report a teacher action naming the page and tag); create the quiz with the bound links; and only after every question is in, publish the pages if the quiz is being published (`metadata.canvas.published`). A page is never visible to everyone: if a re-read ever shows that, the page is unpublished and the push fails. A page titled the same as a tier page that this file did not create blocks the push before anything is written. Students in another tier can see a link but get Canvas's access-denied page.

## Versioned task documents

Every document's required identity fields are described below. IDs returned by Canvas belong in their matching fields. Omit optional fields when unknown; never manufacture an ID, timestamp, rating, or result.

| `kind` | Header fields and body |
|---|---|
| `assignment` | Header has `schema`, `kind`, `operation` (`create`, `update`, or `attach-rubric`), `course`, `title`, `points`, `submission_types`, and optional `due_at`, `unlock_at`, `lock_at`, `timezone`, `module_id`, `published`, `rubric`, and outcomes. Updates and rubric attachments also have `instance`, `course_id`, `assignment_id`, and `observed` live baseline. Creation accepts optional `body_format: markdown` (default) or `html`; update and attachment bodies retain their existing Canvas HTML meaning with format omitted or `html`. |
| `page` | Header has `schema`, `kind`, `operation` (`create` or `update`), explicit `course`, `title`, required `body_format` (`markdown` or `html`), `published`, and optional create-time `module_id`/`module_position`. Engine records `instance`, `course_id` and `created` exact returned Page ID, slug, URL and placement outcomes. Updates also have top-level `page_id`, `slug`, `url` and `observed` live baseline. |
| `module` | Header has `schema`, `kind`, explicit `course`, `title`, optional exact existing `module_id`, optional `published`, and ordered `items`. Each entry has `type: Page`, `File`, `Assignment` or `SubHeader`; content entries have numeric `content_id`, SubHeaders have `title`, and optional `position` specifies a one-based insertion position. Engine records origin/course, module and item IDs/outcomes in `created`. Body is not instructional content. |
| `packet` | Header has `course`, a validated `assignment` snapshot, and `students` workspace-relative paths to student-work files. Those files carry stable student references. The snapshot includes instance/course/assignment IDs, title, points, Canvas `description_html`, submission types, dates/publication, rubric, grading type, anonymity/moderation, and group category when returned. |
| `student-work` | Header has `student_ref`, display `alias`, `assignment_id`, `current` attempt, optional `prior` attempts, existing `comments`, and `excused`, `monitored`, and `notes` state. Attempts include attempt number and RFC3339 submission time, `submission_type`, original `body_html`, readable text (for a discussion, the student's own posts), attachments (`id`, `name`, optional local/readable paths, status/reason), late/due information, and any existing rubric assessment. Work the Engine cannot open (web address, recording, external tool, annotation) carries `url` and a `note` saying to open it; every submission type is pulled. Grades post as points on points, percent, letter-grade and GPA-scale assignments; pass/fail and not-graded work is pulled but its result is entered in SpeedGrader. |
| `results` | Header has `packet`, assignment snapshot, shared `interpretation`, optional documented accommodation `variants`, and unique `students`. Each student has `student_ref`, `operation`, optional `variant`, and exactly one operation body: `grade`, `comment_only`, or `revise_feedback`. A New Quiz snapshot has `new_quiz: true`; its scored results use `operation: comment-only`. |

A rubric has a title, optional Canvas rubric and association IDs, grading flags, and criteria. Each criterion has an ID, description, maximum points, optional long description and ratings. Each rating has an ID, points no greater than the criterion maximum, description, and optional long description. Never fabricate IDs for a live rubric or select a rating whose points do not match.

New rubrics on `operation: create` or `attach-rubric` require `use_for_grading: false` or omission: rubric assessments are independent and grades are computed and posted separately. A true value is rejected without rewriting the draft. Existing coupled rubric snapshots keep their true grading flag and remain supported for honest scoring and posting.

### Standalone Pages and rich bodies

Run `cse push FILE` for a Page document. Creation always starts unpublished; requested placement in an existing module must finish before requested publication. Returned numeric IDs and actual slugs are persisted immediately. Rerun the same document to resume known resources; an uncertain creation is held for bounded live lookup, never blindly replayed. Ordinary Pages have no hub tag restrictions or assignment overrides. They must contain student instruction, not private teacher keys.

Use `cse pull-page COURSE ID|LINK` to obtain exact live HTML and an editable baseline. Change requested fields and push the pulled document. Updates check only relevant baseline fields, preserve unsent work on conflict, and report a fresh baseline for reconciliation. Page edits do not use the assignment review gate. Do not change an ordinary Page into a restricted hub Page through this contract.

`body_format: html` sends agent-authored HTML directly: headings, lists, code, tables, links and images. Canvas may normalize it; check its saved body. Do not include scripts, launch forms, signed URLs or vendor exercises. `markdown` uses the existing small renderer, which escapes raw HTML and does not supply rich tables/images. Missing assignment-create format retains that renderer. Assignment updates keep their existing HTML contract. HTML assignment creation review displays escaped source safely and explains that Canvas rendering still needs checking.

### Course-file receipts and native links

Upload student assets first: `cse upload-file COURSE FILE --access course|hidden|locked [--folder ID] [--receipt PATH] [--new-upload]`. `course` requests ordinary course access; `hidden` means hidden from file listings but accessible through a link, not private. `locked` requires an explicitly selected locked course folder so the transfer is restricted before file settings can be applied. The Engine reports actual returned size, content type and availability. Canvas's non-overwriting rename behavior preserves existing files. Images, PDFs, spreadsheet/code downloads, MP4 and VTT use the ordinary course-file workflow; there is no media conversion or Studio integration.

The small JSON receipt records configured origin/course, local source path and SHA-256 digest, actual returned filename/file ID, stable course link/API reference and access state. Default receipts are beside the source and course-specific. An unchanged known receipt verifies/reuses its exact live file. Changed bytes require an explicit `--new-upload` and a new receipt; the old mapping is preserved. Do not delete receipts to force replay after uncertainty. Upload URLs, upload parameters, PATs and signed download URLs are never receipt content.

For an uploaded file ID `123` in course `456`, a Page or assignment HTML download link is `<a class="instructure_file_link instructure_scribd_file inline_disabled" title="Starter code" href="/courses/456/files/123/download?download_frd=1" data-api-endpoint="/api/v1/courses/456/files/123" data-api-returntype="File">Download starter code</a>`. An image is `<img src="/courses/456/files/123/preview" alt="Diagram of the program flow" data-api-endpoint="/api/v1/courses/456/files/123" data-api-returntype="File">`. Replace both IDs with the verified receipt values. Use a full configured Canvas origin for links in a New Quiz HTML `prompt` or instructions; the quiz service may normalize image references into signed URLs in its response. Do not persist those response URLs as source mappings. This is an explicit HTML path, not automatic local-image import.

Keep source-to-destination asset mappings and provenance in the conversion workspace. An unpublished Page alone does not restrict uploaded files. Teacher keys stay in the private archive unless the teacher selects an appropriate destination/access scope. MP4 upload is not proof of embedded playback: verify the saved Page's player, file access and VTT captions in Canvas's live browser; use a native download/link fallback when markup or captions fail. Missing source captions remain a reported gap.

### Ordered module assembly

Run `cse push FILE` for a module document after its native children exist. Omit `module_id` to create an unpublished module; an explicit ID selects an existing module, never a title match. Each numeric content ID is verified against the selected live course before insertion. For a Page use its returned numeric Page ID; the Engine sends Canvas's returned slug in `page_url`. A New Quiz uses its assignment ID with `type: Assignment`. SubHeaders use only their title.

Entries without `position` append in document order; explicit positions add only the requested entries to an existing module. Existing teacher structure is not deleted or replaced. Successful module item IDs and identities are saved immediately. Reruns verify those exact items and add only missing entries; uncertain writes are held rather than replayed. Partial reports show successes and remaining items, with no rollback of unrelated content.

`published: true` requests publication on the module itself and never implicitly publishes children. Omitted or false `published` leaves an existing module's publication unchanged; new modules begin unpublished. This slice does not unpublish existing modules. The Engine reports child publication/access settings; these are teacher API observations, not a student-view guarantee. Module synchronization, prerequisites and completion requirements are outside this contract.

Canvas API references: [Pages and exact numeric identifiers](https://developerdocs.instructure.com/services/canvas/resources/pages), [course uploads](https://developerdocs.instructure.com/services/canvas/basics/file.file_uploads), [file settings](https://developerdocs.instructure.com/services/canvas/resources/files), and [module items](https://developerdocs.instructure.com/services/canvas/resources/modules). These specify transport contracts, not evidence that this build has rendered content for students.

When authoring, omitted ratings produce numeric maximum/zero anchors so Canvas preserves criterion points. Supplied ratings remain intact, with a numeric maximum anchor added if necessary. These anchors carry the requested scale; they do not select a rating for an assessment.

For `operation: attach-rubric`, `observed.rubric` must be absent and the desired `rubric` must have `use_for_grading: false`. Preserve every assignment setting and exact HTML from the baseline; module placement and ordinary update outcomes are forbidden. The Engine records the target assignment and new rubric/association IDs in `created`, with assignment/publication preserved, module not requested, and a separate rubric outcome. This is a new association, not a way to replace or edit an existing/shared rubric. A pulled New Quiz assignment (`submission_types: [external_tool]`) accepts only `attach-rubric`; an `update` of it is refused. See `playbooks/edit.md` for the authoring path and uncertainty handling.

An interpretation has `mapping: repeated` or `direct`, a private `rationale`, and components with unique `key`, student-facing `label`, nonnegative relative `weight` with a positive total, and (for direct mapping) the exact `criterion_ids` and weight `1`. Repeated mapping applies the whole rubric to each required response. Direct mapping assigns each existing criterion exactly once. Use the assignment directions to identify required response units; a choice among prompts is one selected unit, and a missing required unit is scored as missing. Unknown or unreadable evidence holds that student only.

For every component, `evidence` is `present`, `missing`, or `unknown`, and `criteria` supplies each mapped `criterion_id` with explicit `points` and optional truthful `rating_id` or concise `comment`. Missing components explicitly score zero; unknown evidence holds that student (exit code 3) while the others post. The `assessment` is derived from the fixed interpretation and component scores, normalized to assignment points, then rounded to two decimal places. It may be omitted; the Engine fills in the computed value, and a wrong value is an error. `cse validate FILE` on a results file prints per student the `student_ref`, assessment, and late timing (`1d 3h`, `none`, or `—`).

### Differentiated hub (assignments)

An `operation: create` assignment may declare `tiers`, each `{label, tag, title (optional; default "<assignment title> - <tag>"), supports}`; `supports` is the Markdown body of that tier's Canvas Page. `tag` is the exact name of a Canvas differentiation tag. The assignment body places exactly one `{{tier:LABEL}}` per tier that has `supports`, normally as a link destination, for example `[Silver supports]({{tier:Silver}})`. A tier without `supports` creates no page and takes no token. Labels must be unique, each tag non-empty, and page titles distinct; tiers on `update` or `attach-rubric` are rejected, and Hub is the only differentiation style (no Bridge).

`push` creates and verifies the pages first (unpublished, restricted to overrides, re-read, tag assigned when exactly one non-collaborative group has that name, otherwise nobody assigned with a teacher action), records them in `created.tier_pages` (Engine-written; leave it alone), binds the links, then creates the assignment. Pages publish only when the document has `published: true`; they are never placed in modules. The Markdown renderer accepts `[text](/courses/N/pages/...)` and `[text](http(s)://...)` links and escapes every other link. It renders `**bold**`, `*italic*`, and `_italic_` in paragraphs, list items, and link text; headings stay plain. See the hub paragraphs under "Quiz file" for the visibility rules, which are the same.

### Scoring without a Canvas rubric

If the live assignment or New Quiz has no rubric, add a top-level `scoring_basis` to the results document: `title` and `criteria` (each `id`, `description`, nonnegative `points`; ratings optional). The interpretation and component scores work exactly as they do for a Canvas rubric, using `scoring_basis` criteria ids. It is used only for arithmetic and compact criterion lines: ordinary grading posts the grade and comment with no rubric assessment; New Quiz scoring posts only the comment. `scoring_basis` is rejected if the assignment already has a Canvas rubric, and scored results without either basis are rejected.

### Student operations

For New Quiz written responses, pull the quiz by assignment ID or include it in a course pull; both read written responses. Read essay text and downloaded file contents from the packet. A file marked unavailable or a student/attempt mismatch must be explained specifically; do not invent its contents or block independent students. The Engine downloads file bytes; the agent uses its own reading tools.

For `operation: comment-only`, include only `comment_only` with `attempt` (the pulled `attempt` and RFC3339 `submitted_at`), `components` (the same evidence/criterion-score shape used for grading), and conversational `feedback`. Use the shared `interpretation` and attached rubric or explicit `scoring_basis`. The snapshot must have `new_quiz: true` and individual `points` or `percent` grading; anonymous, moderated and group grading are unsupported. The Engine validates criterion arithmetic and review/post writes one attempt-scoped whole-assignment submission comment, with criterion lines then feedback and no aggregate quiz assessment. No `grade`, `assessment`, `late_timing`, rubric-assessment or item-score payload belongs in `comment_only`. The Engine owns its optional `outcome`. The teacher enters per-item points in SpeedGrader. See `examples/synthetic-results-new-quiz-comment.md` for a complete synthetic field shape.

For `operation: grade`, include `grade` with the target `attempt`, every `components` score, optionally the derived `assessment`, and `feedback`. Optional `teacher_note`, `strongest_prior`, and `late_timing` are private. The workflow writes the honest `assessment` as the grade for the target attempt and records the rubric assessment when a Canvas rubric exists. Outcomes record each remote action independently.

When you have worked out lateness, `late_timing` contains `status` (`late` or `none`), `seconds_late` (a positive integer when late; 0 or absent when none), `due_at` (the student's due date you used, RFC3339), and `basis` (required free text for the teacher; the Engine never parses it). Omitting `late_timing` means the Engine does not touch Canvas lateness. At post the Engine checks only that the attempt is still current and Canvas's live due date still equals `due_at` (otherwise it holds lateness only; grade and comment still post), then writes `late_policy_status` and `seconds_late_override`. Canvas calculates any point penalty. See `playbooks/score.md` for how to work out lateness.

Any `grade`, `comment_only` or `revise_feedback` body may set `header`: `score` (the default: `Assessment: X / Y` first), `full` (the score line plus a line for each criterion), or `none` (the feedback is posted exactly as written, so the agent can lead with any score text or layout the teacher wants). The grade written to Canvas is unaffected.

For `operation: revise-feedback`, include `revise_feedback` with the exact `attempt`, existing `comment_id`, replacement `feedback`, and optional preserved `assessment` object (`assessment` and component scores). This path changes feedback only; do not add grade, rubric, or late-write instructions.

The renderer accepts the validated rubric, selected interpretation, component scores, computed assessment, assignment maximum, and conversational feedback. It returns plain text for Canvas's `comment[text_comment]`: ordinary assignment grading includes the score before compact criterion lines and feedback; New Quiz comment-only output omits the aggregate assessment. It does not serialize rationale, `teacher_note`, notes, failure details, or outcomes. `MarkdownHTML` is for assignment authoring; do not apply it to student feedback. An accepted grading/comment write counts as done; do not add a post-write readback or rerun solely to confirm it.

The `examples/` directory contains synthetic, schema-valid documents for field shape. Treat them only as examples: infer required response units, weights, and choices from each actual assignment's directions.
