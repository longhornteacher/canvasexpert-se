# Version-one workspace formats

Machine-written documents begin with one YAML mapping between `---` lines, followed by Markdown or preserved Canvas HTML. Use `schema: 1`; duplicate keys, unknown fields, and YAML aliases in the header are rejected. Everything after the closing delimiter is body content, including text that resembles YAML. Decimal scores may be written as ordinary finite numbers (`12.5`); quote them when a spreadsheet or other tool might rewrite them. Do not use Markdown tables as machine data.

Folder names: **Dev** is the development checkout and starter templates; its `dist/` ZIP is the user distribution. Extracting it creates **UserInstall**, the local runnable CE-SE folder; setup connects apps and Canvas in place. **UserSync** is an optional dedicated locally accessible OneDrive/Google Drive directory for reusable teacher setup. With no binding, files stay in UserInstall. Logical workspace paths for teacher instructions, playbooks, root .md/.txt guides (except product README.md), context references, `context/courses.md` and `context/students.md` resolve to UserSync when configured. Private student settings, roster and contact records also use UserSync but remain excluded from agent file tools. Grading/planning sessions, pulled work, drafts, machine runtime state, Engine and launchers stay in UserInstall. MCP workspace tool names, `--workspace`, `install_root`, `rules_root`, `sync_root` and modes `local`/`sync` retain their spelling; `--workspace` selects UserInstall. The provider synchronizes UserSync; CE-SE directly reads and edits those files without replication.

## Settings

Private quiz settings (Dev, 2026-10-28): the Students page stores `quiz_time` (empty for Standard, `50%`, `100%`, or 1–10080 whole extra minutes) and `reduced_choices` (boolean) in the active private student table. Older 9-, 10- and 11-column tables remain readable; only the pre-`alias_source` formats trigger the existing alias migration. Invalid values fail with row/field errors. These settings remain excluded from agent reads and scoring packets, and are distinct from the deadline `extra_time` flag. Saving them does not yet apply accommodations to Canvas; private `from_saved` planning and pre-publication checks are available; automatic accommodation writes remain pending the semantics evidence.

`context/courses.md` contains `schema`, the HTTPS Canvas `instance` origin, `aliases`, optional `module_hint`, and `courses`. Each course has a unique `nickname`, positive Canvas `id`, `current` scan flag, optional IANA `timezone`, and optional `effort_floor` (a percent above 0 and at most 100; see `honest_effort` under results). The clean starter has an example origin and an empty course list; replace the origin during setup.

`context/grading.md` contains `schema`, optional `voice`, and optional `feedback_guidance`. `context/students.md` contains `schema` and `notes`. Each note may identify a student by stable `student_ref`, or by unambiguous `name` and optional `course`, and has a required `note`. These are teacher preferences and private context; neither is included in rendered student feedback. `context/school-calendar.md` contains `schema`, IANA `timezone`, inclusive `start_date` and `end_date`, `non_school_dates`, optional `non_school_ranges`, and optional `grading_periods` (`name`, inclusive `start_date`, inclusive `end_date`). The Engine counts school time from this calendar and resolves the current grading period for current-term parent reports. Scoring sessions use Canvas's own closed-grading-period flag, not this calendar. Keep its coverage, closures and grading-period dates accurate; early-release dates count as full student dates. A parent-report run requires exactly one period covering its local as-of date.

## Quiz file (QuizForge)

`push-quiz COURSE FILE` reads a **QuizForge v3.0-json** file in a `<QUIZFORGE_JSON>` envelope or as bare JSON. The supported contract here and `examples/synthetic-quizforge-mixed.md` are embedded and available through `engine_reference` (`formats` / `examples`) or `help formats` / `help examples`; external QuizForge design references are optional. Types that become New Quiz items: `MC`, `MA`, `TF`, `NUMERICAL`, `FITB` (open entry, dropdown, word bank; up to 3 linked blanks), `MATCHING`, `ORDERING`, `CATEGORIZATION`, `HOTSPOT`. `HOTSPOT` needs an `id`, `prompt`, `points`, `image` (a PNG, JPEG, GIF or WebP file up to 20 MiB, as a relative path inside the quiz file's folder; checked by content, and `validate_quiz` checks it) and `region`: `{"type": "oval|square|polygon", "coordinates": [{"x": 0.1, "y": 0.2}, ...]}` with coordinates as proportions (0 to 1) of the image. An oval takes two coordinates (center, then width and height), a square two (top-left, then bottom-right), a polygon three or more vertices. Push uploads the image to Canvas storage once (never sending the Canvas token there), records the accepted upload in the `.cse.json` sidecar beside the quiz file so a rerun does not upload again, and sets the item's `image_url`; an edited image file uploads again. The shape follows the New Quizzes API reference and has not been checked in Canvas Live. `STIMULUS` is not creatable in Canvas, so its HTML is copied into each item that names it with `stimulus_id` (an item inside a STIMULUS..STIMULUS_END span without `stimulus_id` is an error). `ESSAY` and `FILEUPLOAD` also become New Quiz items (written responses; no answer key, `scoring_algorithm` "None", points from `points`). `ESSAY` accepts optional `word_limit_min` / `word_limit_max` (whole words, student-visible limits). `FILEUPLOAD` accepts optional `accepted_formats` (for example `["pdf", "docx"]`, which restricts the upload types). Fields `rubric_hint`, `length_guidance` and `notes` are private design notes and are never sent to Canvas; the agent can use rubric hints to author an explicitly attached rubric or local scoring basis, while anything students must see goes in `prompt`. A rationale on a written item is refused. New Quizzes, including these written items, are open for authoring, use and scoring within supported limits: explicitly scoped `pull-work COURSE QUIZ_ID` reads written work for comment-only assessment; see Student operations below. The teacher enters written-item points in SpeedGrader. Canvas Live (CS8, 2026-10-10) stored both item types, their points and the word limits and accepted types as sent; whether students see the limits enforced has not been viewed yet. Student feedback is required on every auto-scored item (see below); the Engine formats and colors it.

The root needs `title` and `items`; optional `version` or `quizforge_version`, `instructions` (HTML), `metadata`, `notes`, `rationales`, and hub fields are accepted. Every question needs `type`, `prompt`, explicit nonnegative `points`, and a unique `id` on every auto-scored item (the root `rationales` entry names the item by `id`; ESSAY and FILEUPLOAD may omit it). `MC` / `MA` use `choices: [{"id":"a","text":"Answer text","correct":true}, ...]`: MC has exactly one correct choice; MA has at least two. `TF` uses `answer: true` or `answer: false`, a JSON boolean. `ESSAY` has no answer key. Unknown item or choice keys warn, naming the item/choice and pointing here; `metadata` and teacher `notes` are known fields. Inline `rationale` on an item or choice is an error: place feedback in the root `rationales` array, outside `items`:

```json
"rationales": [
  {"item_id": "q1", "choices": [
    {"id": "a", "rationale": "Explain the correct choice."},
    {"id": "b", "rationale": "Explain the distractor."}
  ]},
  {"item_id": "q2", "rationale": "Explain the true/false answer."}
]
```

**Every auto-scored item must have student feedback; validation, review and push refuse the quiz otherwise.** `MC`/`MA` need a rationale for every choice, the correct ones and each distractor. `TF`, `NUMERICAL`, `FITB`, `MATCHING`, `ORDERING` and `CATEGORIZATION` need an entry with a `rationale`. `ESSAY` and `FILEUPLOAD` take none. Write each rationale as plain explanation text: the Engine adds the label and color, so authors do not write labels, `<p>`, colors or `style`. Correct MC choices appear green ("Why this is the best answer:"), MC distractors red ("Why this isn't the best answer:"); MA uses "Why this choice is correct:" / "Why this choice isn't correct:" with the same colors; other auto-scored items show green neutral feedback ("Why this is correct:"). Canvas shows a choice's feedback only for the choice the student picked, so the Engine also copies each correct choice's rationale into the question's incorrect feedback, green and naming the choice ("Why “…” is the best answer:", MA "Why “…” is a correct choice:"): a student who missed the question sees why their choice isn't right and why the correct answer is. Write the correct choice's rationale so it stands on its own for that student. Wrappers, `style` attributes, `span`/`font` tags and an earlier "Why this ...:" label in the authored text are removed so the Engine's label and color always apply; two paragraphs are joined with a line break and ordinary emphasis is kept. Colored per-choice feedback has local tests only; its rendering in the quiz player has not been viewed.

MC/MA feedback matches choice IDs; omitted choice IDs use uppercase `A`, `B`, etc. An MC/MA entry may also carry a `rationale` beside `choices`, sent as the item's general (neutral) feedback in plain, uncolored text; the general-feedback path for choice items has not been checked against Canvas Live. Other auto-scored items use the entry's `rationale` as green neutral feedback. Review shows recognized student feedback separately from questions and the teacher answer key. Push does not read item feedback back, so a successful write is not proof of stored feedback or student rendering.

Differences from the QuizForge contract: every scored item needs an explicit `points` value (the Engine never invents points), and the quiz ID is kept in a sidecar `FILE.cse.json` so an interrupted push resumes the same quiz and adds only the missing items. A New Quiz with the same title that has no sidecar blocks creation (it may be an unfinished push): rename the new quiz or point the sidecar at the existing one. Em dashes in student-visible text become " - ".

Quiz settings and assignment settings go in `metadata.canvas`; unknown keys are rejected by local validation, review and push. Quiz: `shuffle_answers` (default true), `shuffle_questions`, `access_code`, `allow_multiple_attempts`, `allowed_attempts` (whole number greater than one, `-1`, or `"unlimited"`), `score_to_keep` (`highest` default, `latest`, `average`, `first`), `build_on_last_attempt`, `attempt_cooldown` (minutes), `has_time_limit` with `time_limit_minutes`, `calculator_type`, `one_at_a_time` with `allow_backtracking`, `hide_results`. For a single attempt, omit `allowed_attempts` and the multiple-attempt settings. For multiple attempts set `allow_multiple_attempts: true`; `allowed_attempts` then sets the limit (omitted means unlimited). An explicit limit without the enabling flag, or a limit of one with the flag, is rejected rather than ignored. Review displays effective requested settings, not stored Canvas readback. Assignment (applied only after every item is in): `due_at`, `unlock_at`, `lock_at` (RFC3339), `assignment_group_id`, `post_to_sis`, `published` (default unpublished), `module_id` (an existing module). Publication happens after requested module placement succeeds; the existing sidecar supports resumption on failure. Results show students feedback and correct answers after the last attempt unless `hide_results`; Canvas shows nothing if result viewing is left unset.

Presentation: every `<pre><code>` block in a prompt (or an inlined stimulus) is re-rendered as a dark Monokai code box with inline-styled colors, Python rules by default. A block marked `class="language-xyz"` for another language keeps the box but is not colored. Prose, poetry `<div>`s and inline `<code>` are never changed. An item's `metadata.teks` (one code or a list) appends a small muted "TEKS: ..." label to its prompt.

No automatic local-image import or module/group lookup by name. Authored image HTML may use uploaded Canvas file IDs; see native link examples below and verify its saved appearance and access in Canvas.

### Differentiated hub (quizzes)

Hub is the only differentiation style: one quiz, one gradebook column, the same questions for everyone, plus restricted support pages. Add `"differentiation": "hub"` and `"tiers": [{"label", "tag", "title" (optional), "supports" (HTML)}]`. `tag` is the exact name of a Canvas differentiation tag (a non-collaborative group). Each tier becomes a Canvas Page titled `<quiz title> - <tag>` (or `title`). The quiz `instructions` must contain exactly one `{{tier:LABEL}}` link destination per tier, for example `<a href="{{tier:Silver}}">Silver supports</a>`; the Engine replaces each with the verified page path. `"differentiation": "bridge"` is refused. The bound links go in the quiz `instructions` field and the sidecar keeps `tier_pages` beside `assignment_id`.

Order of work: validate; create each page unpublished; restrict it to overrides and re-read; assign the tag (or, if no tag has that name, leave nobody assigned and report a teacher action naming the page and tag); create the quiz with the bound links; and only after every question is in, publish the pages if the quiz is being published (`metadata.canvas.published`). A page is never visible to everyone: if a re-read ever shows that, the page is unpublished and the push fails. A page titled the same as a tier page that this file did not create blocks the push before anything is written. Students in another tier can see a link but get Canvas's access-denied page.

| `results` | `cse results-init PACKET` (MCP `init_results`) writes a scaffold with the packet, its assignment snapshot, a nested component/criterion example, each student's work-file path and current `attempt`, operation and discussion `evidence` digest, reusing an earlier results file's `interpretation` and `scoring_basis` for the assignment; its blank interpretation, components and feedback fail validation until filled. Header has `packet`, an `assignment` snapshot supplied by the scaffold (handwritten files may omit it; the Engine resolves it from the packet in memory on validate, review and post; validation and review never rewrite the draft or change its hash; if you include it, it must match the packet's grading basis and an error names the differing field), shared `interpretation`, optional documented accommodation `variants`, and unique `students`. A New Quiz snapshot has `new_quiz: true`; its scored results use `operation: comment-only`. |

A rubric has a title, optional Canvas rubric and association IDs, grading flags, and criteria. Each criterion has an ID, description, maximum points, optional long description and ratings. Each rating has an ID, points no greater than the criterion maximum, description, and optional long description. Never fabricate IDs for a live rubric or select a rating whose points do not match.

New rubrics on `operation: create` or `attach-rubric` require `use_for_grading: false` or omission: rubric assessments are independent and grades are computed and posted separately. A true value is rejected without rewriting the draft. Existing coupled rubric snapshots keep their true grading flag and remain supported for honest scoring and posting.

### Standalone Pages and rich bodies

Run `cse push FILE` for a Page document. Creation always starts unpublished; for course Pages, requested module placement must finish before requested publication. Group Pages cannot be placed in a course module. Returned numeric IDs and actual slugs are persisted immediately. Rerun the same document to resume known resources; an unclear creation is matched against live Canvas on the rerun and adopted, never blindly replayed. Ordinary Pages have no hub tag restrictions. They must contain student instruction, not private teacher keys. A course Page may carry an individual club audience; see [Course Page audiences from clubs](#course-page-audiences-from-clubs).

Use `cse pull-page COURSE ID|LINK` to obtain exact live HTML and an editable baseline. For a group Page, include `--group GROUP_ID`; the link must use `/groups/GROUP_ID/pages/SLUG`. Group identity is saved in the document and baseline, and the Engine verifies that the exact collaborative group belongs to the selected course. Change requested fields and push the pulled document. Updates check only relevant baseline fields, preserve unsent work on conflict, and report a fresh baseline for reconciliation. A title-only update sends no body, so newer student writing remains intact. Do not regenerate a populated notebook from its starter template. Page edits do not use the assignment review gate. Do not change an ordinary Page into a restricted hub Page through this contract.

For a small correction, `cse replace-text COURSE page ID|LINK|assignment ASSIGNMENT_ID --find TEXT --replace TEXT [--all] ... [--expect-updated-at TIME] [--expect-sha256 HASH] [--push]` (MCP `replace_text`) pulls a fresh document, applies exact replacements to the stored Canvas HTML of a course Page body or assignment description, and saves it as an ordinary update that changes only the body. Pairs apply in order; each find must match exactly once unless `--all`, and nothing is saved unless every pair matches. The optional baseline is Canvas `updated_at` (compared as an instant) or the SHA-256 of the body HTML; the output prints both for the body it read. A no-match, several-match or stale-baseline result is held, writes nothing and leaves the fresh pull unchanged. `--push` sends the edit through the ordinary Page or assignment push, which holds and keeps the edit if Canvas changed after the read; without it the file is ready for `review` or `push`. Assignment description edits follow the assignment review default; New Quizzes and group Pages are not supported.

Group Page `editing_roles` is an optional YAML list of `teachers` and/or `members`; it maps to Canvas's comma-separated `wiki_page[editing_roles]` string. Omission defaults to `teachers`, never `public`. `members` requires `group_id`; module placement is rejected for group Pages. `cse page-history COURSE PAGE_ID --group GROUP_ID [--revision REVISION_ID]` reads revision metadata; selecting a revision includes its historical HTML body. History does not establish who contributed every change or whether simultaneous edits occurred, and Canvas requires update rights to read it.

A course Page may carry the same `audience` intent as an individual assignment. `cse prepare-audience COURSE FILE` / MCP `prepare_audience` records the selected-club snapshot and the exact date-details baseline in the course-local draft without Canvas writes. Group Pages and Hub tier Pages keep their existing tag semantics and never use this contract.

The date-details collection is replaced as a whole, so every unrelated group/section/student row and the Page's availability dates are preserved from `observed_dates`; an unknown or unmappable row holds the replacement instead of being dropped. ### Ordered module assembly

Run `cse push FILE` for a module document after its native children exist. Omit `module_id` to create an unpublished module; an explicit ID selects an existing module, never a title match. Each numeric content ID is verified against the selected live course before insertion. For a Page use its returned numeric Page ID; the Engine sends Canvas's returned slug in `page_url`. A New Quiz uses its assignment ID with `type: Assignment`. SubHeaders use only their title.

For an existing module, `remove` is a list of exact observed entries with `module_item_id`, `type`, `title`, and the observed `content_id` (File, Assignment, Quiz, Discussion), `page_url` (Page), or `external_url` (ExternalUrl); SubHeader needs only title. Read the module's items with `canvas_get` or `cse api` first. Assignment, Quiz and Discussion removals require explicit `confirm_graded: true`. Optional `replacement` names the one-based index in `items`: the Engine adds that item first, checks and removes the observed item, then moves the replacement to its position. Outcomes and the old position are saved; an uncertain operation is held. Removal affects only the module, not its course content.

Entries without `position` append in document order; explicit positions add only the requested entries to an existing module. Existing teacher structure is not deleted or replaced. Successful module item IDs and identities are saved immediately. Reruns verify those exact items and add only missing entries; an unclear create is matched against the live module and adopted, never blindly replayed. Partial reports show successes and remaining items, with no rollback of unrelated content.

Use `type: Discussion` with a positive course `content_id`; the Engine verifies that exact discussion topic in the selected course. Distributed topics use the course parent topic ID. For a group-specific Page or discussion, use a clearly titled `ExternalUrl` item with the exact Canvas URL; the Engine checks same-origin `/groups/{id}` targets against the configured course. A module link provides a route from the course module; it does not grant group membership or group-resource access. Group Pages and direct group discussions still use their Canvas audience rules, so students outside the group may see the module item but be denied at the destination. External provider links are teacher-selected; the Engine does not create documents or meetings or confirm provider access.

Use `cse external-resources COURSE [--group ID]` or MCP `list_external_resources` to read collaboration/conference metadata in a configured course or exact collaborative club. Conference results use Canvas's `conferences` envelope and both lists follow pagination. Missing or unsafe URLs are reported unavailable; known participant refs come only from the existing private student mapping. The tool does not return participant names/raw IDs or read provider documents/recordings, and metadata does not prove contribution or attendance.

`published: true` requests publication on the module itself and never implicitly publishes children. Omitted or false `published` leaves an existing module's publication unchanged; new modules begin unpublished. This slice does not unpublish existing modules. The Engine reports child publication/access settings; these are teacher API observations, not a student-view guarantee. Module synchronization, prerequisites and completion requirements are outside this contract.

Canvas API references: [Pages and exact numeric identifiers](https://developerdocs.instructure.com/services/canvas/resources/pages), [course uploads](https://developerdocs.instructure.com/services/canvas/basics/file.file_uploads), [file settings](https://developerdocs.instructure.com/services/canvas/resources/files), and [module items](https://developerdocs.instructure.com/services/canvas/resources/modules). These specify transport contracts, not evidence that this build has rendered content for students.

When authoring, omitted ratings produce numeric maximum/zero anchors so Canvas preserves criterion points. Supplied ratings remain intact, with a numeric maximum anchor added if necessary. These anchors carry the requested scale; they do not select a rating for an assessment.

For `operation: attach-rubric`, `observed.rubric` must be absent and the desired `rubric` must have `use_for_grading: false`. Preserve every assignment setting and exact HTML from the baseline; module placement and ordinary update outcomes are forbidden. The Engine records the target assignment and new rubric/association IDs in `created`, with assignment/publication preserved, module not requested, and a separate rubric outcome. This is a new association, not a way to replace or edit an existing/shared rubric. A pulled New Quiz also accepts an `update` limited to `assignment_group_id`, `unlock_at`, `due_at` and `lock_at`; preserve the other baseline fields. See `playbooks/edit.md` for the authoring path and uncertainty handling.

An interpretation has `mapping: repeated` or `direct`, a private `rationale`, and components with unique `key`, student-facing `label`, nonnegative relative `weight` with a positive total, and (for direct mapping) the exact `criterion_ids` and weight `1`. On a New Quiz, a component may name the written item it scores with `item_id` (either id from the packet's `written_items`); the comment then shows that part in the item's Canvas points, and an `item_id` the quiz does not have holds that student. Repeated mapping applies the whole rubric to each required response. Direct mapping assigns each existing criterion exactly once. Use the assignment directions to identify required response units; a choice among prompts is one selected unit, and a missing required unit is scored as missing. Unknown or unreadable evidence holds that student only.

For every component, `evidence` is `present`, `missing`, or `unknown`, and `criteria` supplies each mapped `criterion_id` with explicit `points` and optional truthful `rating_id` or concise `comment`. Missing components explicitly score zero; unknown evidence holds that student (exit code 3) while the others post. The `assessment` is derived from the fixed interpretation and component scores, normalized to assignment points, then rounded to two decimal places. It may be omitted; the Engine fills in the computed value, and a wrong value is an error. `cse validate FILE` on a results file prints per student the `student_ref`, assessment, and late timing (`1d 3h`, `none`, or `—`).

### Differentiated hub (assignments)

An `operation: create` assignment may declare `tiers`, each `{label, tag, title (optional; default "<assignment title> - <tag>"), supports}`; `supports` is the Markdown body of that tier's Canvas Page. `tag` is the exact name of a Canvas differentiation tag. The assignment body places exactly one `{{tier:LABEL}}` per tier that has `supports`, normally as a link destination, for example `[Silver supports]({{tier:Silver}})`. A tier without `supports` creates no page and takes no token. Labels must be unique, each tag non-empty, and page titles distinct; tiers on `update` or `attach-rubric` are rejected, and Hub is the only differentiation style (no Bridge).

`push` creates and verifies the pages first (unpublished, restricted to overrides, re-read, tag assigned when exactly one non-collaborative group has that name, otherwise nobody assigned with a teacher action), records them in `created.tier_pages` (Engine-written; leave it alone), binds the links, then creates the assignment. Pages publish only when the document has `published: true`; they are never placed in modules. The Markdown renderer accepts `[text](/courses/N/pages/...)` and `[text](http(s)://...)` links and escapes every other link. It renders `**bold**`, `*italic*`, and `_italic_` in paragraphs, list items, and link text; headings stay plain. See the hub paragraphs under "Quiz file" for the visibility rules, which are the same.

### Scoring without a Canvas rubric

If the live assignment or New Quiz has no rubric, add a top-level `scoring_basis` to the results document: `title` and `criteria` (each `id`, `description`, nonnegative `points`; ratings optional). The interpretation and component scores work exactly as they do for a Canvas rubric, using `scoring_basis` criteria ids. It is used only for arithmetic and compact criterion lines: ordinary grading posts the grade and comment with no rubric assessment; New Quiz scoring posts only the comment. `scoring_basis` is rejected if the assignment already has a Canvas rubric, and scored results without either basis are rejected.

### Student operations

The Engine-authored `student-work.extra_time` and each `group-work.members[].extra_time` are optional private booleans from the saved student setting at the active teacher-setup authority. New pulls emit true or false, including known group members without a returned submission; older packets with no field mean unknown. Refresh the affected evidence when the flag is needed for timing. No private roster rows are exposed. The fact supplies no allowance, duration, multiplier or waiver and never enters comments or parent output.

For batch timing preparation, `cse prepare-late-timing FILE` reads a `schema: 1`, `kind: late-timing-decisions` document under `courses/`; MCP `prepare_late_timing` accepts the same `packet`, `students` and `groups` choices inline. Ordinary `students` choices have `student_ref`, `first_genuine` (`attempt`, `submitted_at`) and optional paired `accommodated_deadline` (absolute RFC3339) and private `accommodation_basis`. Group choices have `group_id` and the same choices under `members`. The agent resolves documented allowances using the calendar, including whether Canvas already applied the extension; the Engine does not interpret `extra_time` or derive a duration. Set the resolved deadline once, including when it equals Canvas's individualized date. Preparation preserves Canvas's effective date in `late_timing.due_at` as the write guard and records the counted deadline in `school_time.deadline`. A flagged student without a documented allowance has only timing held by the agent; academic scoring continues. Keep flags and bases out of student/parent output. Shared timing still requires one matching decision for the complete audience; one member's allowance cannot change another member's timing. See `examples/synthetic-late-timing-decisions.yaml`.

For New Quiz written responses, pull the quiz by assignment ID or include it in a course pull; both read written responses. Read essay text and downloaded file contents from the packet. A file marked unavailable or a student/attempt mismatch must be explained specifically; do not invent its contents or block independent students. The Engine downloads file bytes; the agent uses its own reading tools.

For `operation: comment-only`, include only `comment_only` with `attempt` (the pulled `attempt` and RFC3339 `submitted_at`), `components` (the same evidence/criterion-score shape used for grading), and conversational `feedback`. Use the shared `interpretation` and attached rubric or explicit `scoring_basis`. It works on New Quizzes and ordinary assignments with individual `points`, `percent`, `letter_grade` or `gpa_scale` grading; anonymous, moderated and group grading are unsupported. The Engine validates criterion arithmetic and review/post writes one attempt-scoped whole-assignment submission comment and nothing else: no grade, rubric assessment or lateness. On a New Quiz the comment never has an overall line; it leads with the Engine's pulled auto-scored subtotal when the attempt has one; on an ordinary assignment the default header includes the honest overall line, and `header: none` posts the text exactly (the follow-up form for class exemplars). No `grade`, `assessment`, `late_timing`, rubric-assessment or item-score payload belongs in `comment_only`. The Engine owns its optional `outcome`. The teacher enters per-item points in SpeedGrader. See `examples/synthetic-results-new-quiz-comment.md` for a complete synthetic field shape.

For `operation: grade`, include `grade` with the target `attempt`, every `components` score, optionally the derived `assessment`, and `feedback`. Optional `teacher_note`, `strongest_prior`, and `late_timing` are private. Optional `honest_effort: true` records the agent's judgment that the work is a genuine try: when the course has an `effort_floor` and the assessment is below that percent of the assignment's points (rounded to two decimals), the floor is entered as the Canvas grade instead, and the comment keeps the earned overall line and adds "Entered as N/P (class minimum for an honest attempt)". Otherwise the workflow writes the honest `assessment` as the grade for the target attempt and records the rubric assessment when a Canvas rubric exists. Outcomes record each remote action independently.

For `operation: late-only`, include only `late_only` with the exact current `attempt` and `late_timing`. It updates lateness fields on an already graded attempt without posting a grade, rubric assessment or comment. `late_timing` has `status`, `seconds_late` when late, the current Canvas `due_at`, teacher-readable `basis`, `school_time` provenance (first genuine attempt, submitted time, counted deadline, result and skipped dates), and the `observed` Canvas timing baseline. Review is the default. Before writing, the Engine rechecks the attempt, due date, observed lateness fields and calendar calculation; a mismatch holds the timing action. The Engine owns `outcome`. See `examples/synthetic-late-only.md` and `examples/synthetic-late-timing-decisions.yaml`.

When you have worked out lateness for a grade, `late_timing` contains `status` (`late` or `none`), `seconds_late` (a positive integer when late; 0 or absent when none), Canvas `due_at`, `basis`, and the timing provenance prepared from the pulled evidence. Omitting `late_timing` means the Engine does not touch Canvas lateness. At post the Engine checks the attempt, live due date, current Canvas timing and school-calendar calculation before writing `late_policy_status` and `seconds_late_override`. Canvas calculates any point penalty. See `playbooks/score.md` for the workflow.

Any `grade`, `comment_only` or `revise_feedback` body may set `header`: `full` (the default: all scores on top, `Overall: X/Y` and, with several parts, one `Label: X/Y` line per part in assignment points; then a blank line and each part's label with its `- Criterion x/y` lines; then the feedback), `score` (only the overall line), or `none` (the feedback is posted exactly as written, so the agent can lead with any score text or layout the teacher wants). When `late_timing.status` is `late`, the overall line reads `Overall: X/Y (late)`; X stays the earned assessment and Canvas applies any deduction in the gradebook. The grade written to Canvas is unaffected. On a New Quiz, `score` and `full` both lead with `Questions Canvas scored: X/Y` (when the current attempt's pulled work has `auto_scored`) and then one `Label: X/Y` line per written part (in the item's Canvas points when the component has `item_id`, otherwise rubric points) and each part's rubric lines, never an overall line, because neither part alone is the quiz result. Part scores are rounded to two decimals, so on an ordinary assignment they can differ from the overall line by 0.01. To send a follow-up comment, such as class exemplars, post a second results file with `operation: comment-only`, `header: none` and no components; it writes no grade.

Each entry in `components` may also carry `feedback` (plain text explaining that part's score) and `exemplar` (a model answer the student hand-copies). When any part has `feedback`, the `full` layout becomes one block per part instead of the score summary and criterion lists: the line `Label X/Y` (New Quiz item points, or assignment points), the part's `- Criterion x/y` lines only when it has more than one criterion, then its feedback followed by `(Hand-copy exemplar: ...)` when the part earned under 90% of its points. The Engine drops an exemplar at or above 90%. The overall line (ordinary assignments) or `Questions Canvas scored` line (New Quizzes) still leads. The closing `feedback` is optional when every part has its own and the header is `full`; when given, it follows the blocks. `{{student_name}}` works in both.

For feedback **without scores**, use `operation: comment-only` and `comment_only: {attempt: {attempt: N, submitted_at: RFC3339}, header: none, feedback: text}`. Omit `components`; ordinary individual results need no rubric, `scoring_basis` or `interpretation` for these rows. This adds a new comment on the current pulled attempt, with the usual identity, evidence, duplicate and outcome checks, and never writes a grade, rubric assessment or lateness. If any components are supplied, their scoring data is validated even with `header: none`. Feedback-only comments do not mark New Quiz written work as scored in session discovery. Shared group comments still require scored components; individual-mode group student comments may omit scores, but group-results retain their rubric/scoring-basis requirement. See `examples/synthetic-results-feedback-only.md`.

For `operation: revise-feedback`, include `revise_feedback` with the exact `attempt`, existing `comment_id`, replacement `feedback`, and optional preserved `assessment` object (`assessment` and component scores). This edits an existing comment; use `comment-only` to add a new one. Do not add grade, rubric, or late-write instructions.

The renderer accepts the validated rubric, selected interpretation, component scores, computed assessment, assignment maximum, and conversational feedback. It returns plain text for Canvas's `comment[text_comment]`: ordinary assignment grading includes the overall line before compact item lines and feedback; New Quiz comment-only output omits the aggregate assessment. It does not serialize rationale, `teacher_note`, notes, failure details, or outcomes. `MarkdownHTML` is for assignment authoring; do not apply it to student feedback. An accepted grading/comment write counts as done; do not add a post-write readback or rerun solely to confirm it.

The `examples/` directory contains synthetic, schema-valid documents for field shape. Treat them only as examples: infer required response units, weights, and choices from each actual assignment's directions.


## Individual assignment audiences from clubs

[Validated assignment example](examples/synthetic-individual-club-assignment.md). An optional `audience` on assignment create or an initial `assignment-dates` update uses `mode: individual`, `policy: snapshot` and `source: {group_category_id: 501, group_ids: [701, 702]}`. Source clubs must be collaborative and belong to the configured course/set. They select a deduplicated union of active enrolled students with accepted membership; this never sets native `group_category_id`, shared grading or a group override. Native shared-assignment fields and explicit creation overrides cannot be mixed with this intent. Explicit ref-based student overrides remain supported and may be undated.

Save the draft under `courses/COURSE/`, then run `cse prepare-audience COURSE FILE` (MCP `prepare_audience {course, path}`), describe the prepared changes in the conversation, and `push` / `push_document` on the teacher’s go-ahead (or the request’s existing write scope). Preparation reads Canvas and changes only the course-local draft. It makes no Canvas writes. An initial audience-only update starts from `pull-assignment-dates`, adds `audience`, removes the unchanged pulled `only_visible_to_overrides` intent (retaining `observed_only_visible_to_overrides`), and leaves the pulled rows without date edits; prepare and review that document. Do explicit date edits separately. `only_visible_to_overrides: false` conflicts with an individual audience. Existing publication is preserved on assignment-dates updates.

Engine-managed `audience.state` stores `instance`, `course_id`, exact `target_id` once known, sorted `source`, display `labels`, `observed_at`, sorted `student_refs`, `fingerprint`, `complete`, `reasons`, explicit `exclusions`, preserved `exceptions`, an `observed_visibility` baseline, an `override_baseline` fingerprint and `owned` rows. Each owned row records exact `id`, private-ref/date `baseline` and `outcome`; `application` and `visibility` have distinct `ActionOutcome` records. Assignment publication remains in `created.publication`. No private roster objects, Canvas user IDs or names enter the state. Club labels remain teacher-authored text. Accepted bodyless writes retain succeeded status even without an override ID; a later identity-dependent action holds rather than guesses ownership.

Pending/invited/unresolved membership, unknown enrollment and incomplete selected reads are reported and hold publication; known inactive/completed students are explicitly excluded. Empty snapshots keep their draft or existing resource. Push rechecks the selected source immediately before unfinished audience/publication actions and never silently refreshes it. Manual student exceptions are preserved and excluded from newly created ad hoc rows; manual access beyond the selected clubs is disclosed rather than claimed as exclusive. Accepted and uncertain actions are never erased by initial preparation or blindly replayed. Explicit `--refresh` / `refresh: true` prepares an existing assignment audience refresh as described below. Course Pages and New Quizzes use the same intent through their own sections below.

Override baselines additionally retain `due_at_overridden`, `unlock_at_overridden` and `lock_at_overridden` presence. Updates merge requested date changes with every currently overridden date, preserving inherited dates versus explicit null; omission in the authoring document still means preserve. Previously saved baselines without these optional flags remain usable.

### Explicit assignment audience refresh

Run `cse prepare-audience COURSE RECEIPT_OR_ACTION --refresh` or MCP `prepare_audience {course, path, refresh: true}`. Preparation returns `path` in JSON and saves an Engine-authored `assignment-dates` action. Describe the changes at **that returned path** in the conversation, then use `push` / `push_document` within the teacher’s requested scope. A completed assignment create receipt keeps its original resources and `created.complete`; refresh never recreates the assignment. The source document links `audience.state.latest_refresh_path` to the next action, and a later preparation follows those course-local links with the original exact target/source intent. Reusing the latest returned action directly is also supported. Preserve every saved action; do not copy stale ownership into a new manifest.

[Validated synthetic refresh output](examples/synthetic-individual-club-refresh.md) illustrates the Engine-managed schema. `state.prepared_path` is the workspace-relative returned action; `state.refresh` has `add`, `remove`, `retain`, `protected`, `unknown`, and exact per-row `changes`. Each change records `operation`, `override_id`, `before`, desired `student_refs`, intended `remove_refs` and `outcome`. Once applied, `applied_operation`, `applied_student_refs` and `applied_remove_refs` describe the actual safe scope; these can retain a newly protected student while another removal succeeds. `state.student_refs` remains the requested current source; `state.applied_refs` records known actual managed recipients. Manual access is reported separately through exceptions. Accepted actions update `state.owned` immediately, so the next refresh uses current ownership. Exact rows with no remaining recipients are deleted; membership updates preserve every inherited/overridden/null date distinction and all unrelated rows.

Removal preparation and application both read the exact student's current submission plus requested history. A real submission, saved body/file/link/media, score (including zero), grade/rubric, earlier work or genuine quiz attempt protects access. An empty unsubmitted placeholder's attempt number alone does not establish ordinary assignment work. Missing history, unreadable evidence or wrong identity holds removal. Safe independent additions/removals continue; a changed or missing owned row is preserved, and its former recipients are not silently recreated as additions. The report/review distinguishes desired versus applied recipients and protected/unknown holds. `authorized_submitted_work_change_refs` on `audience` uses the existing exact-student exception convention only when the teacher explicitly authorizes those removals; it cannot bypass unreadable evidence. There is no general force option.

Pending or uncertain override/visibility actions are neither erased by preparation nor replayed. Membership/enrollment, manual exceptions, visibility and replaced owned rows are rechecked before unfinished writes, including no-op completion. Once accepted, row outcomes are retained through restart and later teacher edits are preserved. Initial or refreshed audience changes never edit assignment directions, quiz questions/settings, student attempts, grades or club membership.

## Assign To by differentiation tag (`assign-to`)

```yaml
---
schema: 1
kind: assign-to
course: ELA7 PAP
mode: replace            # replace (default) sets exactly these tags; add merges with the existing audience
everyone: false          # optional; per-target everyone wins. Default: restricted when tags are named
allow_remove_with_submissions: false
targets:
  - module: "Book Club: Ghost"          # title, or a bare integer for the module ID
    tags: ["Book Club/Ghost"]           # Set/Tag, a bare tag name unique in the course, or a tag ID
    cascade: none                       # module only: none (default, reports items with their own audience), apply_to_items, clear_item_overrides
  - page: "Ghost: Quiz 1 Study Guide"   # title, slug or page ID
    tags: ["Book Club/Ghost"]
  - quiz: "Ghost: Quiz 1"               # New Quiz or classic quiz; resolves to its assignment
    tags: ["Book Club/Ghost"]
    dates: {due_at: 2026-10-30T15:00:00-05:00}   # assignment and quiz targets only
  - assignment: 3706953
    tags: ["Book Club/Ghost"]
  - discussion: "Thought Log 1"         # graded discussions use their linked assignment
    tags: ["Book Club/Ghost"]
---
```

Tags are differentiation tags (non-collaborative groups) that the teacher already made; CE-SE never creates or edits them and writes no student names or user IDs. Set and tag names match ignoring case, spacing and a trailing `s` ("Book Club" matches "Book Clubs"). A missing or ambiguous name holds that target, names the problem and the other targets continue.

Each target is reconciled against live Canvas: the current audience is read, nothing is written when it already matches, and every write is read back. A module with no tags and `everyone: true` returns to Everyone. Removing access from an assignment or quiz that students have already submitted is held unless `allow_remove_with_submissions: true`. A native group assignment refuses tag targets. Module audiences inherit to items that have none of their own; an item in two modules is visible if either grants access, and a module target warns when its items also sit in a broader module. `cse assign-to FILE --preview` (MCP `assign_to {preview: true}`) resolves every name read-only and prints current -> new audience with member counts. Per-target outcomes are saved under each target's `outcome`.

## Differentiation tag management (`tags`)

`set-tags FILE [--preview]` (MCP `set_tags {path, preview?}`) accepts a course-local `schema: 1`, `kind: tags` document; use `examples/synthetic-tags.md`. `set: {name, id?, rename_to?}` identifies a non-collaborative set. A new unmatched name creates a set; set renames require an exact ID. `tags: [{name, id?, rename_to?, delete?}]` creates missing tags, preserves existing names, renames exact existing tags or deletes explicitly listed ones. Final names must be unique; exact IDs disambiguate existing names. No collaborative groups are changed.

Optional `members` has `mode: replace` (default) or `add` and one explicit list per final tag name (or an exact existing tag ID). Targets are stable saved student refs or unique aliases, verified as active students in the configured course. No real-name or raw-user-ID targeting. `replace` changes only listed tags; unlisted tags stay unchanged. `add` never removes. `[]` clears a listed tag through normal removal guards; null is rejected. Canvas permits several tags in one set for one student; intentional multiple memberships are supported. The teacher chooses placement; the Engine never infers a level or reports a reason.

Preview first: no Canvas write; saves the exact instance/course/set/tag identities and relevant names, member refs and content-usage baseline while preserving the body. Returns current -> desired counts, aliases added/removed, usage and holds. Changed membership/name/usage inputs hold the affected action for a fresh preview. Each apply resolves current names and memberships again. Structure is one atomic bulk call; a held delete holds that entire structure batch. Independent membership work on unaffected existing tags can continue. Destination bulk adds precede per-user removals; an unsuccessful/uncertain add preserves that student's old membership. Saved outcomes and exact current-state comparisons avoid duplicate structure or membership writes on rerun. Accepted writes have no confirmation read.

Before removal or an in-use deletion, complete direct and module-inherited usage and exact student submission/history evidence must be available. Submitted work, saved artifacts, grades or attempts protect access unless `allow_remove_with_submissions: true` expresses the teacher's specific removal request. The flag never waives unknown membership/usage/history coverage. Unknown or protected removals are held while safe independent additions continue. Saved public documents/results contain refs/aliases, never raw student IDs or private reasons. `observed`, `structure` and `member_outcomes` are Engine-owned reporting fields.

The Students page reads memberships with `bulk_user_tags`, using the already fetched roster rather than per-tag membership requests. The 2026-10-28 CS8 disposable API probe observed wrapped `{group: ...}` objects in bulk results, multiple same-set memberships, and a tag deletion removing the Page override while retaining `only_visible_to_overrides: true`. The Test Student REST Page GET returned 200 both before/after; this is not proof of browser access. Typed management, access guards and retries have local tests; ordinary teacher re-leveling and browser access remain separate evidence.

### Saved quiz settings and publication checks

Use MCP `set_quiz_accommodations {course, quiz_id, from_saved: true, preview: true}` or `cse quiz-accommodations COURSE QUIZ_ID --from-saved --preview` for private saved-settings planning. `from_saved` and explicit `students` are mutually exclusive.
