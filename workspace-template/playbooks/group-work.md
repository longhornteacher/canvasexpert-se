# Book clubs and group work

Use this playbook when the teacher is planning or supporting a book club, collaborative group, or discussion-based unit. Read `TEACHER.md`, `Teacher_Override.md`, this teacher's `context/teaching-profile.md` and `context/grading.md`, `context/courses.md`, and relevant student/course references through the active teacher-rules location first. Keep unit plans, drafts, discussion pulls and outcomes in UserInstall. Never read `.cse/` or put private student notes, accommodation details, contact data or grouping rationales into club materials.

This playbook covers the group features currently shipped: collaborative group sets and clubs, memberships, member-editable group Pages, ungraded course/distributed/direct-group discussions and explicit announcements, written discussion evidence and teacher replies, course modules with group links, metadata reads for existing collaborations/conferences, group assignment authoring with scoped assignment-date overrides, and individual club audiences for assignments, course Pages and New Quizzes. Shared-product submission pulls, shared or individual grading, and authoring and individually assessing graded course/distributed discussions are supported below. Provider document/meeting creation is separate; Tier C peer review, group calendars, conference bookings, group files and creating new club conversations remain frozen and out of scope. Existing teacher Inbox threads have a separate read/reply/state playbook. Do not promise or simulate unsupported group paths. Existing individual assignments and New Quizzes continue to use their own playbooks for content, with this playbook supplying the club-audience workflow.


## Plan the unit

Ask only for consequential choices that saved context and the request do not settle: course, books, how students choose or are assigned clubs, group constraints, dates/read schedule, learning targets and deliverables, and whether a requested communication should be sent. Book titles do not uniquely identify clubs; several clubs may read the same book. Reuse an existing club only after checking its exact group-set and group IDs and confirming it matches the teacher's intent.

Keep a regular local `unit.md` with the learning targets, books, group-set ID, club IDs and labels, reading/meeting schedule, teacher-chosen rotating roles, individual and shared deliverables, requested grading approach, communication choices, and links/paths plus returned Canvas IDs and outcomes for the real drafts and pulls. It is a working note for this unit, not a new CE-SE document kind or synchronization file. Choose a graded course or distributed discussion when the teacher wants individual assessment of a written conversation; plan its learning targets, required responses, dates and scoring basis. Choose a shared product assignment when the deliverable is a club artifact with shared or individual grades. A graded course or distributed discussion uses a linked individual assignment; follow the native-content and authoring instructions for its assignment block and review. Never imply that a shared Page has a shared grade.


Roles such as facilitator, evidence finder, connector and summarizer are directions for student learning. They do not grant Canvas group leadership or moderator permissions. Do not put private tier tags, accommodations, student notes or group-balancing reasons in club names, rosters, role sheets or student-facing content.

## Establish clubs and memberships

Use the current configured course and inspect collaborative group sets with `cse groups COURSE` (MCP: `list_group_sets`). Inspect a chosen set with `cse groups COURSE --set SET_ID`; use `--members GROUP_ID` only for the exact club being discussed. These views use stable student references and aliases and omit student names, Canvas IDs, logins, SIS IDs, contacts and differentiation tags.

To create or adjust a set and its clubs, use `cse pull-group-set COURSE SET_ID` for an existing set. For a new set, make a regular draft with `kind: group-set`, `operation: create`, the configured course nickname, and the teacher's requested club names/settings. Edit only what the teacher requested and run `cse push FILE`. Existing or omitted clubs and settings are preserved; save returned IDs in `unit.md` so later materials use exact identities. Do not remove a club that contains student work as routine cleanup.

For membership changes, first use `pull-group-memberships COURSE SET_ID` and work from that exact baseline. Make only explicit changes by `student_ref`; retain each observed `from_group_id`. A row with `from_group_id: null` is an observed unassigned student; `to_group_id: null` explicitly removes a member. Omitted students are not removal requests. Check for submitted work before a move/removal and include only the specific teacher-authorized refs in `authorized_submitted_work_change_refs`. Generic requests to balance clubs do not authorize moving a student away from submitted work. For even assignment of unassigned students, use `operation: allocate-unassigned` only when the teacher requests it; it uses Canvas's set-wide allocation and reports the refs actually assigned. If the roster changes after review, refresh the baseline. Do not replay an uncertain allocation.

Self sign-up is a group-set setting. Explain the actual choice to students through teacher-authored directions; do not promise a sign-up UI or membership until Canvas access is observed. Book matching, group balance and membership decisions remain teacher judgments. Continue independent rows when a particular move is held and report that exact row.

## Build club spaces and conversations

Run the review in `review.md` on club Pages, discussion prompts and role sheets before pushing them; group scoring is reviewed as `score.md` describes.

Create a course unit hub or other course Page using `native-content.md`. For each club, create a group Page with the exact course and `group_id`: a reading plan, evidence notebook or meeting log can be member-editable with `editing_roles: [members]`. Group Pages cannot be placed directly in course modules. Keep a simple starter that invites student writing, and never push that starter again over a populated notebook. Pull before editing; if the body conflicts, preserve the unsent draft and merge only the requested change into a fresh pull. A title-only edit preserves the current student body. `cse page-history COURSE PAGE_ID --group GROUP_ID` reads revision history, but revisions do not prove who contributed or capture every simultaneous edit.

Author discussions within the supported scopes:


- Course topic: no group IDs; optionally graded with an `assignment` block.
- One shared prompt with separate club conversations: use `group_category_id` for the collaborative set; optionally graded with an `assignment` block. The linked gradebook assignment stays individual.
- One ungraded topic directly in a club: use `group_id` for that exact group.

Use `kind: discussion` and the supported `push_document` path. Pull the exact topic before editing. A pulled baseline protects requested title/body replacement while settings-only changes can preserve newer live content. Keep discussion topics unpublished or scheduled as requested. `is_announcement: true` is a separate communication choice: create an announcement only when the teacher explicitly asks, and record its intended audience and purpose in `announcement_intent`. A request to assemble a unit or create discussion activities does not authorize an announcement. For a graded course or distributed topic, the create document's `assignment` supplies points, dates and an optional independent rubric; returned topic/assignment/rubric IDs support resume. Keep the collaborative set on the topic, never on its linked assignment, and check in with the teacher before the graded create, as for any assignment. Edit the linked assignment through its own assignment draft after creation. Direct group topics and announcements cannot be graded.


To inspect written discussion, run `pull-discussion COURSE TOPIC_ID [--group GROUP_ID]` (MCP: `pull_discussion`). Read both `topic.md` and the sibling `discussion-packet.yaml`. A distributed topic includes only verified child topics in the selected set; a direct group pull reads that club. Check every source's complete/partial status and as-of time before drawing conclusions. The Engine maps authors only through existing private student references for the same Canvas origin. Unmapped authors remain unknown; do not ask for or read a broad roster to fill them in. Deleted posts, inaccessible club topics, missing replies and unreadable attachments are incomplete or unknown evidence, not proof of no participation. The packet records written Canvas interaction only; it does not show in-person talk or edits in outside documents.

Summaries should point to the packet/topic links and as-of time, describe observed claims, evidence and questions worth revisiting, and offer next instructional moves as suggestions. Say when coverage is partial. Describe missing preparation only when the relevant source is complete. Do not grade from post counts or labels, call an inaccessible student disengaged, infer Google document authorship from timestamps, or claim to hear an in-person conversation.

Post a teacher entry or reply only when the teacher explicitly asks to communicate. Use `kind: discussion-reply`, exact topic context and, for a reply, the intended `parent_entry_id`. Put only publishable wording in the body; keep private analysis in `teacher_note`. For a group topic, `group_id` must match its group context. If the outcome is pending or uncertain, do not post again or search by similar wording. An accepted reply is recorded and is not read back for confirmation.

## Connect the unit in Canvas

Use `native-content.md` to assemble a course module after its children exist. A course discussion uses the native Discussion item and its verified parent topic ID. Link a group Page or direct group discussion with an explicitly titled `ExternalUrl` containing its exact Canvas URL; use the native course Discussion link for a distributed parent. External URLs must be stable HTTP(S) links without embedded credentials or signed temporary parameters. A module link and module publication do not publish the child or add students to the club. Course visibility does not prove a student can open the group resource.

`cse external-resources COURSE [--group GROUP_ID]` (MCP: `list_external_resources`) can discover existing collaboration and conference metadata and safe returned links. It does not create Google/Microsoft documents or meetings, read provider content or recordings, or prove contribution or attendance. Use teacher-selected provider links; if a usable link is unavailable, ask the teacher for one or leave that link out.

## Assess a shared club product

Read the teacher's grading choice first. Check Canvas's "assign grades to each student individually" setting in the pulled snapshot. **Off:** one grade and rubric reach every member (`operation: grade` or `comment-only`). **On:** each student is graded on their own (`operation: individual`). If it is unknown, pull again. Never change the setting to fit your plan.

Pull with `pull-work COURSE ASSIGNMENT_ID [--group GROUP_ID]` (MCP `pull_work`) and read the `group-packet` and each `group-work` file. For shared grading, require `shared_assessment_status: ready`: a complete assignment-specific audience, one current artifact and attempt for every member, nobody excused or hidden. If shared assessment is held, read the reasons, tell the teacher the specific cause, and keep assessing independent groups. Individual-mode packets use `shared_assessment_status: not-applicable`; assess each selected student from their own linked artifact and current submission/attempt evidence, holding only an unresolved student while independent students continue. A shared artifact does not prove every member contributed; do not infer missing work from it, and treat unreadable files or unknown membership as unknown, never as zero.

Write one `kind: group-results` file (see `examples/synthetic-group-results.md` in the format reference) with a row per shared-ready group (name the group `packet`; the Engine fills the `assignment` snapshot from it): its `group_id`, the `artifact_key`, `member_refs` for the whole audience, and either `operation: grade` or `comment-only`. Use the same interpretation, component and criterion rules as `score.md`; the Engine does the arithmetic, so never multiply a score by contribution or adjust it to a preferred total. Write `feedback` for the whole group in the group's voice. Put anything meant for one student in that student's `individual_feedback` row and anything for the teacher in `teacher_note`; the Engine keeps private text out of shared comments, but do not repeat it there. Use `feedback_audience: none` when no shared comment is wanted.

For `operation: individual`, assess each student from what is observed and the teacher's criteria: a shared artifact does not prove equal contribution, so do not split one score or apply a participation multiplier, and use an entry in `variants` only for an established accommodation without describing its reason. Each student's feedback is private to them; add a `shared_feedback` row only when the teacher wants one comment every member sees. Re-pull and reassess a student whose attempt changed; the others still post.

Each group member's private `extra_time` fact follows the lateness instructions in `score.md`: read the standing policy, individual accommodations and assignment directions, resolve an absolute deadline using the calendar, and apply the allowance only once if Canvas has not already included it. A missing field in older evidence is unknown; refresh that member's evidence when needed. False does not cancel a documented accommodation. A true flag without a usable allowance holds that member's timing decision while valid academic scoring continues; ask for the rule once and save the teacher's standing answer in the appropriate context file. Never expose the flag or accommodation basis in shared materials, student feedback or parent reports. In individual grading mode, use only that member's timing. In shared mode, an unresolved member or differing deadlines holds the shared timing action for the full audience while a valid shared assessment can proceed; never use one member's allowance to change another's timing.

Report to the teacher in the conversation as `score.md` describes, one line per club (shared grade, or the range of individual grades) plus general impressions, and post on the teacher's go-ahead. In shared grading a club's grade and group comment go together: hold the whole club or none of it, though a single private comment can be left out. In individual grading, holding one student does not change another student's grade or turn private feedback into a group comment. For shared grading, posting sends the grade and rubric once, then the group comment and included private comments. Individual mode posts each included student's grade and private feedback, plus any included shared feedback. Batch-prepare the first genuine attempt for every member. Shared-product lateness uses one common `late_timing` only when the complete audience has a matching Canvas due date and homogeneous timing result; preserve the prepared `member_school_time` map keyed by stable member ref on the shared grade or late-only row. If member evidence is incomplete or timing does not match, omit/hold that timing action while allowing a valid shared assessment to proceed. In individual mode, use each student's own prepared timing and late-only action. The Engine counts school time from the calendar; Canvas calculates any point penalty. If a group is held (membership, attempt or audience changed, or the work was edited after the pull), pull again and reassess that group. Report each group's outcome plainly: what posted, what is held and why, and what is uncertain and should be checked in Canvas rather than repeated.

## Assess graded discussion work

A graded discussion is an ordinary individual assignment whose evidence is a conversation. Pull it with `pull-work COURSE ASSIGNMENT --session` (title or ID; omit `--session` only for a requested reassessment), then read each `student-work` file's `discussion_evidence` and the pulled `discussion/discussion-packet.yaml`. Read the whole thread around the student's posts: what they claimed, how they used evidence, how they answered or built on others. Never grade from post counts, labels or length, never treat a clubmate's post as the student's work, and report oral or outside-document contributions as unobserved. If coverage is `partial` or authors are unresolved, score only what the evidence supports and mark the rest unknown rather than missing; missing work can be scored zero only when coverage is `complete` and the teacher's task actually required it.

Write ordinary `kind: results` rows. Each `grade` or `comment-only` needs `evidence` copying the student's `digest` from the pulled work; list any other participant's entry you relied on in `context_refs`. Feedback is individual: group discussion children are still graded per student, with no shared grade. Missing-response assessments also require complete relevant coverage when posting; an unreadable club does not invalidate an independently complete club. If a student edits a post after the pull, that student is held for re-pull and the others still post. A checkpointed discussion is graded in SpeedGrader; the Engine holds a `grade` row for it. Offer `operation: comment-only` so the written feedback still reaches the student, and the teacher enters the checkpoint grades in SpeedGrader.

New Quiz written-work scoring is the New Quiz section of `score.md` and uses the comment-only path: no quiz/item grade, rubric assessment or late timing is written, and the teacher enters item points in SpeedGrader.

## Resume and report

Resume from saved Canvas IDs and operation outcomes in the actual documents. Preserve returned IDs, student-authored Page content, unsent drafts and partial discussion packets. A missing club page or inaccessible discussion child should not stop independent clubs; name the specific incomplete piece. Do not send announcements, create club conversations or post teacher replies merely to say setup is complete.

Report the course and relevant Canvas links, what was created or read, publication and membership state, exact partial/held items, and what the teacher or students still need to do in Canvas. Use local checks and API responses honestly: neither proves student access or rendering. Routine supported teaching does not require a disposable-course trial. Do not describe pending student-view evidence as proof that the workflow is unusable.

## Individual responses for selected clubs

When the teacher asks for an individual response for one or several clubs, use an ordinary assignment with `audience: {mode: individual, policy: snapshot, source: {group_category_id: SET_ID, group_ids: [CLUB_ID]}}`. Discover exact club IDs; names are display hints. Do not set native group-assignment fields or make a collaborative group override. Each student submits and is graded independently. See `examples/synthetic-individual-club-assignment.md` through the Engine format reference.

The agent saves the draft, runs `prepare_audience {course, path}` / `prepare-audience COURSE FILE`, and checks in with the teacher in the conversation as `authoring.md` describes before creating, unless the request already included creating it. Preparation records current eligible members and the observation time privately by stable refs. Explain empty clubs or pending/unresolved memberships plainly, preserve the draft and add/resolve members before preparing again. A membership change after preparation holds that item; continue independent valid work. The teacher does not maintain student lists or manifests.

For an existing individual assignment, pull its exact assignment-dates document, add the audience intent, remove the unchanged pulled `only_visible_to_overrides` request while retaining its observed baseline, leave the existing rows and dates unchanged, prepare and check in with the teacher. Existing manual exceptions keep their dates and access; tell the teacher about any access beyond the selected clubs. Audience-only targeting needs no due date. To update current members later, prepare an explicit refresh as described below; never erase accepted state or recreate the assignment. Club membership is a dated snapshot, not a permanent automatic binding. New Quizzes use the same intent through their own section below.

For “update this response for the current club,” run `prepare_audience {course, path: RECEIPT_OR_LAST_ACTION, refresh: true}` or `prepare-audience COURSE FILE --refresh`. Use the returned `path` for the check-in and push. The Engine follows saved latest-action links and keeps the original assignment receipt. Explain the additions, removals, retained students, existing manual exceptions and any protected or unreadable cases from the prepared review; the teacher does not maintain a roster list or a second manifest.

Students with current or earlier submitted/saved work, attempts or grades retain access by default. Safe changes for other students continue, and the result reports the actual applied audience separately from current club membership. If new work appears after preparation, the Engine retains that student while applying any independent safe removals in the same row. Unknown evidence is a hold, not proof that work is absent. Only when the teacher explicitly asks to remove a specific protected student's access may the agent use `audience.authorized_submitted_work_change_refs` with that exact ref and prepare again; unreadable evidence still holds. Preserve manual and newer teacher edits. A pending/uncertain write stays in its saved action and must not be discarded or blindly repeated. Do not change club membership, directions, quiz content/settings, grades or attempts just to refresh who can access the work.

## Course Pages for selected clubs

When the teacher asks for a calendar, guide or other reading Page for one or several clubs, use an ordinary course Page with the same `audience` intent. Do not use a group wiki Page or a Hub tier Page: those keep their tag restrictions. See `examples/synthetic-individual-club-page.md` through the Engine format reference.

Save the draft, run `prepare_audience {course, path}` / `prepare-audience COURSE FILE`, then push. The Engine creates the Page unpublished, applies the complete restriction, finishes any requested module placement and publishes last. If the audience stage is refused or uncertain, the Page stays unpublished with its exact ID saved; report that plainly and resume the same document rather than creating another Page. Review explains any access beyond the selected clubs.

Changing who sees a Page never sends stale HTML: an audience-only update after a teacher edits the live body leaves that body alone. Availability dates use `unlock_at`/`lock_at`; omit a date to preserve it and use `null` to clear it. Pages have no due date.

For “update this Page for the current club,” run `prepare_audience {course, path: RECEIPT_OR_LAST_ACTION, refresh: true}` and push the returned path. The Engine recomputes the managed student row and preserves manual rows, availability dates and newer teacher edits. Pages have no submission evidence route, so a student who leaves the club is removed even if they viewed the Page; say so plainly rather than implying work protection. If the managed row was changed or duplicated in Canvas, the refresh holds instead of replacing it. Do not recreate the Page or change club membership to refresh access.

## New Quizzes for selected clubs

When the teacher asks for a quiz that only selected clubs can see, use the ordinary QuizForge file with the same `audience` intent in `metadata.canvas.audience`. The quiz stays one gradebook column and each student answers independently; the clubs are only the audience, never native group work. See `examples/synthetic-individual-club-quiz.md` through the Engine format reference.

Save the draft, run `prepare_audience {course, path}` / `prepare-audience COURSE FILE`, then push. The Engine creates the quiz, adds every question, applies the requested settings and module placement, applies the restriction and publishes last. If the audience stage is refused or uncertain, the quiz stays unpublished with its exact ID saved; report that plainly and resume the same file rather than creating another quiz. A resume repeats only unfinished steps, so questions and settings are never duplicated. Review explains any access beyond the selected clubs.

For “update this quiz for the current club,” run `prepare_audience {course, path: RECEIPT_OR_LAST_ACTION, refresh: true}` and push the returned path. That action changes only who can see the quiz; it sends no question, settings or attempt change. Students with a genuine attempt or grade keep access by default, and the result reports the actual applied audience separately from current club membership. Do not recreate the quiz or change club membership to refresh access.

## A whole unit for one club

When the teacher asks for a complete club unit — a reading Page, an individual response and a quiz — treat it as three independent resources that share one audience. See `examples/synthetic-book-club-unit.md` through the Engine format reference.

Write all three drafts first, then prepare each audience, then review and push each one. Do not wait for one resource to finish before writing the next: if one is held, the others still proceed, and you report exactly which object exists and what remains. Each resource is created unpublished, restricted to the club, placed in the requested existing module, and published last. A refused or uncertain audience leaves that resource unpublished and resumable while the rest continue.

Use the same exact club IDs for all three. The module keeps its existing entries and gains one native entry per resource in the order the teacher asked for them; a New Quiz entry uses its associated assignment ID. Never set native `group_category_id`, use a collaborative group override, or change club membership to make the unit work.

When membership later changes, refresh each resource separately with `prepare_audience {course, path, refresh: true}` and push each returned path. Report the three results together: which students were added, which were removed, which kept access because of real work, and which Page removals were not work-protected. Do not recreate any resource to refresh access.
