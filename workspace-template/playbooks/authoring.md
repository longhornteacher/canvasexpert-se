# Create a new assignment

What the teacher's words mean and when to create are in `AGENTS.md`.

Before designing content, read `context/teaching-profile.md`, relevant teacher reference notes and `context/grading.md` through logical MCP paths or the effective teacher-rules root. Use saved grade/subject, priorities, standards and feedback guidance; ask only for missing details needed for this task. Preserve teacher choices and never use developer class names or differentiation tags as colleague defaults.

## Standards

Apply `TEACHER.md`: 100 points by default, grade-level rigor in plain, concise wording, a one-line Learning Target and three-step directions at the top, a grade-representative exemplar for writing assignments, accessible images and links, and a "Corrections available" line. A writing assignment includes its rubric in the create draft (`rubric`, totaling the assignment's points, STAAR-shaped as `TEACHER.md` describes); don't ask whether to add one. Once the content is shaped, check the course's Green tag with `list_tags` and add a Green tier when it has students, then offer Silver/Red/Blue once unless saved choices settle it (Hub section below).

## Write the draft

Ask only for missing details that matter: course, title, directions, points, due and availability dates, submission type, module, publication, rubric. The saved course nicknames come from MCP `list_courses` (or `context/courses.md`); `.\cse.cmd courses` lists live Canvas courses. `.\cse.cmd modules <course>` lists module targets, and `.\cse.cmd modules <course>` lists module targets.

Write a draft in the course's `drafts/` folder using the fields in `help formats`. Put the teaching content in the body. The default Markdown renderer handles headings, paragraphs, lists, bold, italic, links and fenced code; raw HTML shows as escaped text. Use `body_format: html` explicitly for authored tables, images and Canvas file links. The review page, when the teacher asks for it, shows HTML as escaped source; verify its saved appearance in Canvas. For standalone Pages, asset uploads and module assembly, read `native-content.md`.

For a book-club or collaborative group unit, read `group-work.md` first. It is the workflow guide and states the current group-work limits. The notes below are operation-specific details for authoring within that scope.

## Collaborative groups and book clubs

Use `cse groups <course>` (or MCP `list_group_sets`) to inspect collaborative group sets. `cse groups <course> --set <ID>` lists its clubs, stable-ref/alias memberships, unassigned students, pending requests, and roster completeness; `--members <GROUP_ID>` reads one exact club. No student names, Canvas user IDs, logins, SIS IDs or contacts are returned. Differentiation tags are intentionally excluded. Use `pull-group-set <course> <set-ID>` to create an editable exact-ID baseline, then make only the requested name/settings changes or add keyed clubs and `push` the document. Omitted clubs/settings are preserved. The Engine checks course, group-set and club identity before writes and records created IDs so a partly completed setup can resume.

For membership plans, use `pull-group-memberships <course> <set-ID>` to save the exact membership baseline. Make only explicit changes by `student_ref`, retaining each `from_group_id` from the baseline; `null` means observed unassigned, while `to_group_id: null` requests a removal. Do not infer removals from omitted rows. A move can change access to group work, so check for submitted work; list only the specific `student_ref` values the teacher authorized in `authorized_submitted_work_change_refs`. Use `operation: allocate-unassigned` only when the teacher asks for even allocation; it respects students already assigned, uses Canvas's synchronous allocation and reports the refs actually assigned. If a new unassigned student appears after the baseline, refresh it first. Self sign-up is controlled by the group-set settings. Book preference matching, balanced groups and role assignment remain teacher/agent decisions.

For a shared-product assignment, confirm the exact collaborative group set and intended grading mode with the teacher. Create an ordinary supported assignment with `group_category_id` and explicit `grade_group_students_individually`; submit text or upload work only. Use `pull-assignment-dates COURSE ASSIGNMENT_ID` to review exact override rows and effective dates. Edit only requested rows: omission preserves a date, explicit null clears it, and an explicit `remove` row deletes that exact override. Group-target overrides must belong to the assignment's selected set. Student-target overrides use stable `student_refs`; they are a fixed audience and do not automatically follow future group membership. The Engine keeps a new assignment unpublished until its requested audience/date rows and other create stages succeed. Group assignment authoring is locally implemented; Canvas Live writes and student access have not been checked. For group submission pulls and scoring, see "Assess a shared club product" in `group-work.md`.

For an ungraded discussion use `kind: discussion`: omit both group IDs for a course topic, use `group_category_id` for a common prompt with separate club conversations, or use `group_id` for one direct club topic. Pull the exact topic with `pull-discussion` before editing. A pulled baseline protects requested title/body replacements while allowing settings-only changes to preserve newer live content. Use `is_announcement: true` only when the teacher explicitly asks to communicate an announcement; record the requested audience and intent in `announcement_intent`. For a graded discussion add an `assignment` block on create (`points`, optional `due_at`/`unlock_at`/`lock_at`, optional independent `rubric`); it works for a course topic or a `group_category_id` distributed topic (the group set stays on the topic and the gradebook column stays individual), never for a direct `group_id` topic or an announcement. Graded discussion creation checks in with the teacher first, like any assignment. The linked assignment is set only at creation; later points, date or rubric changes go through the assignment. To score one, see "Assess graded discussion work" in `group-work.md`.

To inspect a conversation, use `pull-discussion COURSE TOPIC_ID [--group GROUP_ID]`. Read both `topic.md` (editable prompt baseline) and the sibling `discussion-packet.yaml` (as-of entries). Check each source's coverage before describing what students did. A partial child, unresolved author, deleted post, unreadable attachment or missing reply is unknown evidence; do not claim nonparticipation from it. The packet identifies students only by stable `student_ref` and alias. It captures written interaction, not oral participation or outside-document edits.

Post a teacher entry or reply only when the teacher explicitly asks to communicate. Use a `kind: discussion-reply`, `operation: create` document with exact `context_type`, `context_id`, `topic_id`, optional `parent_entry_id`, and `body_format`; for a group topic, set `group_id` to the same group as `context_id`. Put only publishable wording in the Markdown/HTML body. Keep private analysis in `teacher_note`; it is never sent. The Engine checks the current topic and exact parent before posting and records the accepted entry ID. If the saved outcome is pending or uncertain, do not make a second reply or match text to decide whether the first one landed.

## Check in and create

When the draft is ready, describe it to the teacher here in a few lines: the title, points and grading type, due and availability dates, submission type, rubric, module placement, tiers and whether it will be published, then the directions in a sentence or two and anything you decided that the teacher did not specify. Don't paste the whole body; the teacher can ask to see it, or ask for a Draft PDF (`save_draft_pdf`) to look at or print as a handout. Make requested changes in the draft and report only what changed. When the teacher says to go ahead, run `.\cse.cmd push <draft-file>` (MCP: `push_document`). When the request already included creating it, push first and then report. If the teacher asks to see it on a page, or has saved that preference, run `.\cse.cmd review <draft-file>` (MCP: `start_review`) instead: the page shows the content as the Engine will write it (it doesn't simulate the student view), and the Engine creates the assignment when the teacher clicks Create.

A new assignment stays unpublished until its requested rubric and module pieces succeed. If `push` reports partial or ambiguous results, rerun the same file; it resumes from saved IDs and adopts an existing matching item or preserves a teacher's change. Report what was adopted or preserved. Never pick a same-titled Canvas assignment arbitrarily or start a second create when the first may have succeeded. Report the resulting Canvas state and anything incomplete. To share a finished module with the team through Collab, see `team.md`.

## Differentiated hub (tier support pages)

Use the hub for the Green tier (automatic when the course's Green tag has students) and for Silver/Red/Blue when the teacher accepts them; `TEACHER.md` says what each holds. It is the only differentiation style (no separate tier assignments, no Bridge). Add `tiers` to a create draft: each has `label` (Green, Silver, Red or Blue), the teacher's exact Canvas differentiation `tag` from `list_tags` or the saved mapping in `context/teaching-profile.md`, and `supports` (Markdown for that tier's page). Never invent a tag. Put shared directions and hints for everyone in the assignment body, and link each tier exactly once with `[Green supports]({{tier:Green}})`, using the color name alone as link text. Tier supports scaffold the same standard; they don't lower it.

`push` creates the restricted pages first, then the assignment with verified links. Report each page, its tag, and every teacher action it prints (for example, a missing tag: that page is restricted to nobody until the teacher sets up the tag). Pages publish only when the draft says `published: true`; if the teacher publishes later in Canvas, the pages stay unpublished, so say so. Tiers can't be added to an existing assignment; for one, offer a tier page built with the Page steps in `native-content.md` and linked from the assignment through `edit.md`. A page title that already exists stops the push before anything is created. Students in other tiers see every link but get Canvas's access-denied page for the others. The Engine verified the restrictions through Canvas, not from a student's view.

For an individual assignment limited to selected book clubs, read `group-work.md`'s individual-response instructions. Use the nested `audience` source and Engine preparation before the check-in; preserve independent submissions and manual exceptions. Initial audience-only updates use the exact assignment-dates document with its existing rows unchanged. Do not hand-maintain recipient lists or substitute native shared-group settings. For later membership changes use explicit `prepare_audience` with `refresh: true` on the saved receipt/latest action, then check in and push the returned assignment-dates path. Preserve protected work, manual exceptions and saved ownership; see `group-work.md` for the agent-driven refresh procedure.

A course Page for selected clubs uses the same `audience` intent and `prepare_audience` call before `push_document`. The Engine creates it unpublished, restricts it, places it in the requested module and publishes last; a refused audience never publishes. An audience-only change sends no stale body. See `group-work.md`'s Page instructions.

A New Quiz for selected clubs uses the same `audience` intent in `metadata.canvas.audience` and the same `prepare_audience` call before `push-quiz` (MCP `push_quiz`). The restriction targets the quiz's exact associated assignment, so the quiz stays one gradebook column and each student answers independently. The Engine creates the quiz, adds items, applies settings and module placement, restricts it and publishes last; a refused audience never publishes, and a resume repeats only unfinished steps. See `group-work.md`'s quiz instructions.
