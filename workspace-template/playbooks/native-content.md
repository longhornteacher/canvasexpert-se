# Canvas-native curriculum authoring

For a book-club or collaborative group unit, read `group-work.md` first for the workflow, supported scope and access limits. This playbook supplies the native Page, asset and module authoring details it references. When the unit targets selected clubs with individual work, `group-work.md` also supplies the audience preparation and refresh procedure; this playbook supplies the content and module assembly.

Use this playbook to turn selected archived teaching material into Canvas Pages, activity Assignments, New Quizzes, Files and Modules. Read `context/courses.md`, the archive's provenance and conversion notes, and `cse help formats` first. The archive and its capture tools stay outside the Engine.

## Teaching preferences

Before authoring curriculum content, read `context/teaching-profile.md`, `context/grading.md` and relevant teacher-selected references through the active rules location. Use this teacher's grade/subject, instructional priorities, standards and feedback guidance. Preserve their preferences and ask only for missing details needed for this task; developer class names and differentiation tags are never defaults for a colleague.

## Choose content and destination

Select material with the teacher and establish the exact destination course nickname and publication scope. Archive source course IDs are not write destinations. Preserve source discrepancies and adaptations in the conversion workspace; do not silently change an assessment key. Keep teacher guides, keys and solutions in the private archive unless the teacher explicitly requests a suitable destination and access scope.

Before pushing anything built here, run the review in `review.md` on it, including Check yourself answers and tier pages. In converted teacher material, report findings to the teacher rather than changing the material.

Prepare static instructional content: headings, lists, tables, code, links and accessible images. Materialize vocabulary or other teaching text generated by vendor scripts. Do not copy launch forms, scripts, signed URLs or vendor exercises into Canvas bodies.

## Build native content

1. Upload student assets with `cse upload-file`, selecting access explicitly. Keep the receipts and provenance beside the conversion drafts, with a local-to-Canvas asset map. An unpublished Page does not make its files private. Use the returned file IDs and stable course links in authored HTML; do not save signed download URLs.
2. Create `kind: page` documents and push them with `cse push`. Use `body_format: html` for tables, images and rich teaching bodies, or `markdown` for the Engine's small Markdown subset. Keep the returned Page ID, slug and URL in the document. To revise a Page, use `cse pull-page` and edit the pulled document. Preserve a held draft's unsent work and compare its fresh baseline before reapplying changes.

For a club reading plan, evidence notebook or meeting log, use the exact configured course plus `group_id` from `cse groups COURSE --set SET_ID`; set `editing_roles: [members]` only when club members should edit (Canvas receives `members` as a role string). Group Pages cannot be placed in course modules. A starter can be as small as:

```yaml
schema: 1
kind: page
operation: create
course: ELA7
group_id: 701
title: Evidence notebook
body_format: html
editing_roles: [members]
published: true
---
<p>Record your evidence here.</p>
```
The header ends with a `---` line and the Page needs a non-empty body after it.

Pull before each edit. If the body conflicts, keep the unsent draft and merge its requested change into a fresh pull; a title-only change leaves current student writing untouched. Never push the starter body again over a populated notebook. `cse page-history COURSE PAGE_ID --group GROUP_ID` reads history; a revision is not a complete record of who contributed or simultaneous editing.
3. Create activities with the existing assignment contract, optionally `body_format: html`. Follow `authoring.md` and its check-in. Choose text entry, file submission, a rubric or teacher grading to suit the student product.
4. Create assessments with `quizzes.md` and the supported QuizForge types. Matching and ordering interactions may become corresponding native questions when their semantics fit. Convert Classic source questions to supported New Quiz types; report or explicitly adapt unsupported questions rather than dropping them. Python work becomes a code/text/file submission with teacher assessment; copying its prompt does not replace vendor execution or hidden autograding. Written New Quiz responses are graded by the teacher in SpeedGrader.
5. Assemble a `kind: module` document using verified existing Page, File, Assignment, native course Discussion and SubHeader references. For a New Quiz use its returned assignment ID. A group-specific Page or discussion uses an explicitly titled `ExternalUrl` with its exact Canvas URL; read `cse external-resources COURSE [--group ID]` for existing collaboration/conference metadata and teacher-selected links. External URLs must be stable HTTP(S) links without embedded credentials or signed temporary parameters. Push the module after its native children exist. An existing module receives the requested additions, positions and explicit removals. Module publication does not publish its children or grant group membership: students can see a course module link and still lack access to the linked group resource. Metadata does not prove document contribution or meeting attendance, and the Engine does not provision external documents or conferences or read their content/recordings.

To replace or remove an existing module item, first read its live item list with `canvas_get` (CLI `cse api /api/v1/courses/COURSE_ID/modules/MODULE_ID/items?per_page=100`, following pages). In a module document for that exact module, add a `remove` row with the observed `module_item_id` (the item's `id`), `type`, `title`, and its `content_id` (File, Assignment, Quiz, Discussion), `page_url` (Page), or `external_url` (ExternalUrl). A SubHeader needs its title. Assignment, Quiz and Discussion removal also requires `confirm_graded: true` to record the teacher's explicit request. For replacement, add the new item to `items` and set `replacement` to its one-based position in that list. The Engine adds the new item, checks and removes the exact old module item, and moves the replacement to its position; it saves each outcome. Removing a module item does not delete the underlying course content. If the item changed or an outcome is uncertain, inspect the module and preserve the document rather than replaying blindly.

For a club unit whose Page, response and quiz are restricted to selected clubs, push each resource first and then the module, so every native reference already exists. A restricted course Page and an individual assignment are ordinary native entries; a New Quiz uses its associated assignment ID. The module itself carries no audience: it is a navigation list, and each child keeps its own restriction. Do not add a group-specific `ExternalUrl` for a resource that is now a native restricted course Page.

Pages, files and modules have no new universal approval gate. Follow the teacher's requested scope; assignments and quizzes keep their check-in with the teacher before creation. A held or uncertain write needs the specific recovery described by the Engine. Do not erase a receipt or saved create record to make a rerun write again; rerun the same file and report what was adopted or preserved. Continue independent content while an item is held and report which objects exist and what remains.

## Teaching Pages: Green supports and Check yourself

Apply `TEACHER.md` to every new teaching Page: plain, concise wording, accessible images and links, and the tiers it describes.

**Green page.** Pages have no hub `tiers`, so when the course's Green tag has students (`list_tags`), build the Green tier as its own Page: push a `kind: page` titled "<Page title>: Green" with the supports, restrict it to the teacher's Green tag with `assign_to` (preview, then apply), and link it from the main Page with the link text "Green supports". If the restriction does not apply, say so plainly: until it does, every student can open that page. Silver/Red/Blue pages for a Page follow the same steps when the teacher accepts them. Use the same steps when the teacher wants a tier page added to an existing assignment or quiz, linking it through `edit.md`.

**Check yourself.** End a substantial teaching Page (`body_format: html`) with two or three questions on its learning target, each answer in a collapsible box:

```html
<h3>Check yourself</h3>
<p>1. What does the narrator want most in chapter 2?</p>
<details><summary>Show answer</summary><p>To be trusted by her older brother.</p></details>
```

It is a self-check only: no "write this on paper", no turn-in, and no link to an activity that does not exist. On the first Page with a Check yourself section, read the saved HTML back once to confirm Canvas kept the `<details>` boxes. If Canvas removed them, take the section out, tell the teacher, and record the finding in `context/engine-notes.md`.

## Verify in Canvas

For an HTML Page conversion only, read the saved HTML back once to see Canvas's normalization (the standing no-read-back rule is for write confirmation). Check links, image alt text, file availability, question keys/points and module order. Open the teacher view and distinguish it from actual student-view evidence. Record both outcomes and remaining checks in conversion notes.

For video, upload MP4 and available VTT assets, then test the saved Page's player, course-file access and captions in the live browser before claiming embedded playback. If Canvas removes the markup or captions fail, use a native course-file link and explain the limitation. Missing source captions remain a source gap; an uploaded MP4 alone is not a working lesson player.

Report Canvas URLs, returned IDs, publication/access states, successful pieces and specific held items. Local tests and API read-back do not establish student rendering or access. Keep provenance and conversion decisions in the teacher's workspace, not in Engine code.

## Differentiation tags

When the teacher asks to create/rename/delete support tags, move students or re-level a class, use `list_tags` to inspect the exact course/set/tag names, then write a `kind: tags` draft (`engine_reference` formats; example `synthetic-tags.md`). The teacher decides placement. An evidence-based suggestion is a proposal until the teacher approves it; never invent a default level or disclose why a student is in a tag.

Call `set_tags {path, preview: true}` first and show current -> new counts, aliases added/removed, content using the tags and any held removals. Use final names after renames; `members.mode: replace` sets exactly the listed members of each listed tag, `add` only adds, and an explicit empty list requests clearing. The student's stable ref or unique saved alias is the target. Apply with `set_tags {path}` on the teacher's go-ahead; a request already specifying the changes authorizes the write. Report the actual structure/member outcomes, including independent successes.

Submitted or saved work protects access; unknown coverage stays held. Set `allow_remove_with_submissions` only when the teacher specifically requests that removal after understanding its access effect. Do not waive missing evidence. If Canvas names, members or usage changed after preview, preserve the draft and show a new preview. Rerun the same draft after failure/uncertainty; do not create another set or manually strip its saved outcomes. To copy a set to another course, create a fresh destination draft with the same structure names and no members, source IDs, observed baseline or outcomes.
