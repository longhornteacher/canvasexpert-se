# Score student work

For a book-club unit, read `group-work.md` first. The current group workflow supports ungraded discussion evidence and ordinary individual assignment/New Quiz scoring; it supports shared and individual grades on a shared group product (`group-results`; see `group-work.md`), and graded discussions (see the graded-discussion section of `group-work.md`). Do not turn discussion participation counts or a discussion packet into a score. Use this playbook only for a supported individual assessment.

The judgment calls are yours; the Engine pulls work, does the arithmetic and posts. What the teacher's words mean and when to post are in `AGENTS.md`; how to report scores in the conversation is under Report and post below.

Read this playbook and grading/calendar references through their logical MCP paths or from the effective teacher-rules root (UserInstall by default, configured UserSync otherwise). Student notes and course configuration use that same authority. Packets, drafts and commands stay in UserInstall. Contact JSON is private and must not be read for scoring. If a shared reference is unavailable, explain that file's problem without reading an inactive local copy; continue independent work that has its needed evidence.

A rubric shared by several assignments is assessed through the ordinary live rubric and exact criterion IDs. To inspect or offer a reusable rubric for future work, see edit.md; save a personal library entry only when the teacher asks. Never alter an existing definition to fit a grade.

## Pull

```powershell
.\cse.cmd pull-work [course] [assignment] --session
```

For every ordinary scoring session, use `--session`, even when the teacher selects a course or assignment (MCP: `pull_work` with `session: true` and the same optional scope). The targeted session uses Canvas's needs-grading count and includes submitted work that is late, due now or not yet due. It does not filter by grading period; a closed-period assignment is reported without pulling its submissions. A bare “scoring session” means pull everything Canvas reports as needing grading, present the assignment list, then ask what the teacher wants scored. If the teacher already narrowed the request, use the report's assignment group and due-state columns to apply that scope with common sense. Resubmissions after grading are ordinary work and are scored normally. When the Engine writes a New Quiz's item points, Canvas marks the attempt graded and it leaves the session. When it posted only a comment (no item scores), that attempt is not pulled again while Canvas still awaits written-item points; pass the “comment posted, item points not entered” row and its student count to the teacher as a reminder to enter points in SpeedGrader. Use an explicit assignment pull without `--session` when the teacher requests reassessment. In a group session packet, retain every member as audience evidence but assess only members marked `score` or `score-and-late`; a member with no `work_purpose` is already handled. If the packet lists `direction_images` (images embedded in the assignment directions, such as a reference image students must reproduce), read each with `read_workspace_asset` before judging. When an image cannot be read reliably enough for an exact-match check, hold that check and say why instead of guessing. Read the packet and student files, especially each row's `work_purpose`: `score` or `score-and-late`. A fresh pull never overwrites unsent scoring work. Before judging anything, read `context/teaching-profile.md` for grade/subject, instructional priorities and relevant standards, `context/grading.md` (the teacher's `voice` and `feedback_guidance`; they override style defaults here, never the rubric or posting rules) and `context/students.md`. Use this teacher's preferences, never another teacher's course/tag policies. Student notes also arrive with each student's pulled work. Apply established accommodations without asking the teacher to repeat them. An incomplete profile does not block scoring when directions, rubric and work supply the needed evidence. In a teammate's course (a course with an `owner`), read `team.md` first: only assignments tagged `(CE)` can be scored, and scores go in hidden for the teammate to post. A session with no course covers only the teacher's own courses.

New Quiz written items (`ESSAY`, `FILEUPLOAD`) are open for regular scoring. Pull the quiz by title or assignment ID with `--session`: `.\cse.cmd pull-work COURSE QUIZ --session` (MCP: `pull_work` with `session: true`); an exact title works, so do not ask the teacher for the ID. `--session` is what keeps students whose comment is already posted out of the pull. Omit it only for a requested reassessment. An explicit assignment is pulled even when its grading period is closed. Broad class pulls include New Quizzes with submitted work. Their results use `operation: comment-only` with item scores; follow the New Quiz section below instead of ordinary assignment grade/lateness instructions.

Score every pulled packet yourself in this conversation rather than handing each packet to its own subagent: the packets share students, rules and timing, and a subagent's summary loses that context. The helpers in `review.md` are different: they only check the finished results, and you apply what they find.

## Fix the scoring basis

- **Canvas rubric attached**: use it. Never invent a criterion or rating ID, and never pick a rating whose points don't match the score you give. If a rubric was just attached, pull again so the packet has Canvas's real IDs.
- **No Canvas rubric**: score anyway. Infer sensible criteria from the directions, the work and the grade level, and record them once in the results file as `scoring_basis` (`title`, and `criteria` each with `id`, `description`, `points`; one overall criterion is fine). Keep each criterion `description` to a short name of two to five words ("Answers the prompt", "Specific details") and do not repeat the item label in it: it prints in the student's comment as `Details 5/5`. The fuller meaning goes in your private rationale. **Reuse before inventing:** first look for earlier results files for this assignment, and for the same-titled assignment in the teacher's other sections, and reuse their `scoring_basis` and `interpretation` exactly so every class is scored on one scale. Create new criteria only when none exists. If an earlier basis looks wrong, ask the teacher rather than changing scales between classes. It drives the arithmetic and the score lines in feedback, without creating a Canvas rubric. Ordinary assignments receive the grade and comment; New Quizzes receive only the comment. If a real rubric would help (a reusable assignment), offer one in a preview.

Before scoring anyone, identify the required response units from the directions, rubric and submission mode. A choice among prompts is one unit. Infer defensible relative weights from what each unit demands; equal weights are allowed but not automatic. Use `repeated` mapping when the rubric applies to each response, `direct` when criteria already match separate prompts. Record a short private rationale and apply the same interpretation to every student unless a documented accommodation applies. `help formats` has the exact fields and arithmetic; `help examples` shows shape only. The shared `interpretation:` block (mapping, rationale, components) is required for scored results; feedback without scores uses the form below. For ordinary assignment grading, start from `synthetic-results-two.md` in `help examples` (MCP: `engine_reference` topic `examples`), and keep the `assignment:` snapshot supplied by `init_results`. Handwritten files may omit it: the Engine resolves it from `packet` in memory. Validation and review leave the saved file and hash unchanged. Each student's `grade` lists criterion points. For New Quizzes, use the `comment_only` contract below and in `help formats`; do not copy a grade operation.

## Assess honestly

- Score a missing required response as missing; don't average only the answered parts. Report missing submissions; don't enter zeros.
- Unreadable work gets `evidence: unknown`: hold that student, explain the specific missing evidence, and continue independent students within the teacher's posting scope.
- Compare with the strongest earlier attempt as one whole submission. Never mix parts of attempts or treat a teacher-adjusted grade as proof of stronger work.
- Reassess when the academic requirements or the submission changed. A title, publication, scheduling or HTML-formatting change alone doesn't need it. The Engine holds a post only when points, rubric, grading type or anonymous/moderated/group mode changed. A new attempt shows up on its own; editing posted feedback doesn't requeue an attempt, but the teacher can ask for a reassessment.

## Possible AI use or copying

While reading each student's written work, watch for signs that it isn't the student's own. You flag; the teacher decides. A flag is never a finding of cheating: it doesn't change the score you give, and it never appears in student feedback, comments, handouts, parent reports or student notes. Don't paste student work into a web search, AI detector or any other outside service, and don't cite a detector's score: they are unreliable and the work is private.

Judge only from what's in front of you: the pulled work, the student's earlier attempts and earlier pulled work in this class, the directions and source texts, and classmates' work in the same pull. Signals:

- **Leftover chat text**: "Certainly! Here's…", "As an AI…", "I hope this helps", "[Your name]", an offer to revise, or Markdown (`**bold**`, `#` headings, bullet lists) pasted into a text box.
- **Invented evidence**: quotes, page numbers, events or characters that aren't in the assigned text, or citations that don't exist.
- **Copied text**: identical or near-identical wording between two students (across all sections in the pull), or long unquoted passages lifted from the source text or an outside source you recognize.
- **Not this student's voice**: a sharp change from the student's earlier work in this class: vocabulary, sentence length, spelling and error patterns, or a jump in polish between drafts with no sign of revision.
- **Far above level**: writing well beyond the grade, such as adult or college-level vocabulary, sentence structure, or analytical moves the class hasn't been taught, especially when it's free of the errors seen elsewhere in the student's writing. Weigh it against what you know about the student's level: the course (an on-level section such as ELA7 rather than PAP/advanced, from `context/courses.md` and the teaching profile), the student's readiness or language tier (Silver, or Green for an emerging English writer) recorded in `context/students.md` or pulled notes, or a Silver/Green tier page they worked from, and their earlier work in this class. Pulled work doesn't list a student's tags; don't guess a tier you can't see.
- **Generic AI style**: polished, general prose that never quite engages the specific text or task; stock phrasing ("delve into", "a testament to", "plays a crucial role", "it is important to note", "in today's world", "rich tapestry", "multifaceted"); every paragraph shaped the same; a tidy "In conclusion" that restates the prompt; answering a broader question than the one asked.

Flag a student on a strong signal (leftover chat text, invented evidence, wording matching a classmate or a source, or writing far above grade level from a student known to work at or below it: an on-level section, a Silver or Green tier, or clearly weaker earlier work) or on at least two independent weaker ones. Writing far above grade level is still flagged on its own, as a weak signal, when you know nothing about the student's level. From a Blue or PAP student whose earlier work is also strong, it's ordinary and not a flag. Style alone is weak evidence: strong writers, students who revise carefully, and students using documented supports (speech-to-text, translation, a scribe; check `context/students.md` and pulled notes) can trip it. Don't count quoted and attributed text, wording from the directions or teacher-provided sentence frames, or a shared group product. Short or formulaic answers are rarely worth a flag. Follow any AI or academic-honesty policy in `Teacher_Override.md` or `context/grading.md` over these defaults.

Score flagged work honestly as submitted and write the usual feedback, then send the flag and its evidence through `review.md`: only flags the arbiter upholds go in the report (below). Before posting, ask whether to hold flagged students; when the teacher already said to post, post everyone else, hold the flagged students and say so, since a held student comes back in the next session. Keep flags in the conversation; don't record them in a results file or student notes unless the teacher asks.

## Feedback without scores

When the teacher requests comments without scoring, use `operation: comment-only` with `comment_only` containing the exact pulled `attempt`, `header: none` and `feedback`. Omit `components`; no rubric, `scoring_basis` or `interpretation` is needed for those rows. If scores are supplied, the Engine still validates them. Read the packet's student-work files and use their `student_ref` directly; the Engine resolves Canvas identities privately, so never match students by submission timestamps. `engine_reference` topic `examples` includes `synthetic-results-feedback-only.md`. Reporting and posting follow the last section. This comment does not mark New Quiz written work as scored; the teacher still enters item points in SpeedGrader.

## New Quiz written items

This path supports individual quizzes graded as points, percent, letter grade or GPA scale. Anonymous, moderated and group grading are outside its current scope.

The scoped pull reads typed Student Analysis essay responses and attempts to download uploaded files into the packet's `students/<student_ref>/files/attempt-N/` folder. File records include status and a reason when retrieval is unavailable; limits are 50 MB per file and 500 MB per pull. Open downloaded files with your normal document tools. An unavailable or unreadable file is `evidence: unknown`, not a missing response to score as zero. Explain the affected student, file and reason, hold that student's feedback, and continue independent students. The teacher can open the affected file in SpeedGrader.

Use the attached Canvas rubric or a `scoring_basis`, with private authored `rubric_hint`s as guidance when available. Start the file with `init_results` (see Save, report, post); `synthetic-results-new-quiz-comment.md` in `help examples` (MCP: `engine_reference` topic `examples`) shows a filled example. Create `operation: comment-only` per student with a `comment_only` body containing the exact pulled `attempt` reference (`attempt`, `submitted_at`), scored `components`, and `item_scores: true` (the scaffold sets it). Give every interpretation part the `item_id` of the one written item it scores. The Engine then writes each written item's points and its own comment into the quiz, the same save SpeedGrader makes, so the teacher has nothing to type and Canvas computes the quiz total:

- **Item comment** (Engine layout): the item's score `X/Y` in its quiz points, then the part's `feedback` as a quick explanation of the score and the one thing to do better, then `Exemplar:` with the part's `exemplar` when the student earned under 90% of the item's points. Write the exemplar at the students' grade level and to the assignment's expectations.
- **Whole-assignment comment** (Engine layout): `Score: X/Y (attempt N)` with the quiz total Canvas reports after the write, so it includes auto-scored items and any fudge points. Remarks about the whole quiz go in the closing `feedback`, which follows that line; leave it empty otherwise.

Grades post as soon as they are written: no hiding or manual posting in the teacher's own courses. The write happens after the review in `review.md` and the teacher's go-ahead in the conversation; the teacher handles any cleanup in SpeedGrader afterward. The Engine validates criterion arithmetic; report and post as in the last section. It writes no rubric assessment or late timing.

When a part cannot name one written item (a choice among prompts), leave `item_scores` off for that file: the Engine posts one whole-assignment comment with each part's item points, and the teacher enters them in SpeedGrader.

Item scores use an undocumented internal New Quizzes call, checked live on 2026-10-29. The Engine holds a student, writing nothing, when the quiz was saved in SpeedGrader since the pull, a new attempt arrived, or it cannot read the quiz result. Say which students were held and why; pull again to rescore them, or the teacher enters those points in SpeedGrader. A teacher's fudge points and items not in the results file are kept as Canvas has them. Treat a failure to match the report student and attempt as a skipped student, and rely on the pulled file status rather than assuming retrieval.

## Ordinary assignment grades

For ordinary assignments, post the honest computed score for the current work, even below an existing grade. Never inflate criterion scores or suppress the assessment to preserve a teacher-adjusted grade.

If the course has an honest-effort floor (the `effort_floor` on the course in `context/courses.md`), set `honest_effort: true` on each grade row whose work is a genuine try. Leave it off for blank, placeholder or accidental work and for work that is not a real try. Keep the assessment and criteria as earned; the Engine enters the floor when the earned score is lower and adds the "Entered as" line to the comment. In your report, say how many students were entered at the floor. Canvas applies late point penalties; you don't. These grade and lateness instructions do not apply to New Quiz comment-only results.

### Lateness

Canvas calculates late point penalties. For work being scored in a session, prepare one batch of first-genuine attempt and accommodation choices with `prepare_late_timing` (CLI: `cse prepare-late-timing FILE`; MCP: `prepare_late_timing` with the packet and student/group choices). Do not re-read or re-time already-scored work in a session. The Engine counts from the applicable deadline to the selected first genuine submission, records school-time provenance, and checks current Canvas state. Use prepared proposals on `score-and-late` grade rows. `late-only` is for an explicit non-session timing task on already-graded work. Never hand-calculate session seconds or substitute a prepared `late-only` row for a grade row. If preparation holds or cannot resolve a timing choice, hold only that timing action and continue the academic assessment when its evidence is sufficient.

1. For each session candidate, use the batch preparation tool against the referenced packet. It confirms the chosen attempt exists in the packet; whether it is the first genuine submission (not blank, placeholder or accidental) is your judgment from the pulled attempts. Later drafts inherit its timing.
2. Read the private `extra_time` fact with the established rules in `context/grading.md`, student accommodations in `context/students.md` and pulled notes, and assignment directions. New pulls include true or false; absence in an older packet is unknown, so refresh that student's evidence when the flag is needed for a timing decision. A documented individual rule takes precedence over a general flag policy; a false flag never cancels a documented accommodation. Neither a bare flag nor a Canvas tag name supplies a duration, multiplier or waiver.
3. Resolve the applicable documented allowance to one absolute RFC3339 deadline using `context/school-calendar.md`. Compare it with the student's pulled `effective_due_at` and the documented base deadline: if Canvas's individualized date already includes the allowance, use that date once. Never add the allowance twice. When using an accommodation, send the resolved `accommodated_deadline` and a private `accommodation_basis` in that student's batch choice, including when the resolved deadline equals Canvas's date. Keep the pulled Canvas date as the `due_at` write guard; the Engine preserves it independently of the counted deadline.
4. The Engine counts from the resolved deadline to the first genuine submission in the calendar's IANA timezone, excluding weekends and listed holidays/non-school ranges while preserving partial-day seconds. Weekdays, including early-release days, count as full calendar dates. An on-time result needs no school-time interval. Review the returned timing, private basis and skipped dates.
5. For a `score-and-late` candidate, attach the prepared proposal's `late_timing` to its grade row. For `late-only`, use only the prepared attempt and timing fields. The Engine rechecks the attempt, live due date, observed timing and school-calendar calculation before writing lateness. A timing hold does not block an otherwise valid grade or comment.

If `extra_time: true` has no usable documented allowance, hold only that student's timing correction and explain the missing rule. Omit their unresolved choice from preparation and continue valid academic scoring and other students' timing. Ask once for the applicable rule when needed; save a teacher-provided standing flag policy in `context/grading.md`, or an individual accommodation in `context/students.md`, through the existing teacher-context workflow. The Engine does not interpret the flag or invent an allowance. Keep the flag and accommodation basis out of student comments, shared feedback and parent reports.

For a scoring session, prepare the resolved timing candidates for work being scored as one batch before saving results and report any unresolved candidates as held. The typed MCP preparation accepts `packet`, `students`, and `groups` inline; the CLI reads a `late-timing-decisions` file under `courses/`. Inspect proposed, unchanged and held rows. Attach proposals to matching grade rows where `work_purpose` is `score-and-late`. Report corrected or unchanged timing and any held candidates with scoring outcomes. Preparation is read-only; the teacher's go-ahead still comes before any write. See `help formats` for the complete field shape and synthetic example.

If the due date, first genuine work, calendar coverage or accommodation details are unclear, omit timing for that student or keep the late-only row held, say what's missing, and continue independent work. Extra time changes timing, never the score or feedback. New Quiz comment-only work has no lateness action.

## Feedback

The Engine starts the comment with the computed score lines. You write the rest as plain text in the teacher's voice: specific, respectful glows and grows grounded in the work, including meaningful changes from the strongest earlier attempt. Use sentences, line breaks and blank lines only: Canvas shows Markdown and HTML literally, so `**Glow:**` posts with its asterisks and `- ` stays a plain hyphen. The same applies to a criterion `comment`. `help fields` records what Canvas shows. Full rubric definitions stay in Canvas. The teacher decides the layout. By default the Engine puts all the scores on top: for ordinary grades `Overall: X/Y` (marked `(late)` when your `late_timing` says late) and, when there are several parts, one `Label: X/Y` line per part in assignment points. Under that it lists each part's rubric lines, then your text, so your text explains the rubric results and what to do better. X is the earned assessment; Canvas applies any late deduction in the gradebook. Order your text as improvement tips, then exemplars. On a New Quiz, `score` and `full` are the same: the scores on top are the Engine's `Questions Canvas scored` line (when pulled) and one line per written part, never an overall line, so apply any saved layout preference (such as "Assessment first") to those lines only and never write an X / Y total for the written portion, even with `header: none`. For any other student, set `header: score` (only the overall line) or `header: none` (the Engine adds nothing and posts your text exactly as written) on the `grade`, `comment_only` or `revise_feedback` body, then put the score where the teacher wants it. The Engine never rewrites the teacher's wording or layout.

### Class exemplars

For each written prompt, pick the two strongest student responses across the teacher's saved current courses that assigned the same prompt; the source course need not be the receiving course. Use short anonymous excerpts: no names, aliases or identifying details. Every student in a receiving class gets the same pair. If fewer than two usable responses exist, use what there is or skip exemplars for that prompt, and say so; never write a model answer and present it as student work.

Exemplars never hold up individual feedback. Post each student's feedback as usual. When the last student whose work answers that prompt is scored, across the courses that assigned it, send the exemplars as a follow-up: a second results file with `operation: comment-only` for each student, `header: none`, no components and the exemplar text as `feedback`. It adds only the comment and never touches the grade, so a grade the teacher changed in SpeedGrader stays as they left it. Post them when the teacher has given the go-ahead for that prompt's feedback.

When a result covers several written items, give each component its own `feedback`, which explains the score and the one thing to do better, and leave the closing `feedback` empty unless something applies to the whole quiz. With item scores each part's feedback becomes that item's comment in the quiz; otherwise the Engine posts one block per item in the comment: `Q11 Remote execution 10/12`, then that item's feedback. For an item where the student earned under 90% of its points, also write `exemplar`: a short, complete model answer to that item, in plain text, at the students' grade level and meeting the assignment's expectations, for the student to hand-copy. It is your model, not a student's work. The Engine shows it only below 90%, so skip it on stronger items.

Give each interpretation component the `item_id` of the written item it scores, from the packet's `written_items`: the Engine scales that part to the item's quiz points (a 7/10 rubric result on a 15-point essay is `10.5/15`), which is the number it writes with item scores. A choice among prompts has no single item, so leave `item_id` off that part and `item_scores` off the file. Without item scores the comment leads with `Questions Canvas scored: X/Y` when the pull recorded that subtotal, then one `Label: X/Y` line per written part and each part's rubric lines, never an overall line; a part without `item_id` shows its rubric points. The Engine adds the subtotal from the pulled work; you never supply, restate or add to it. That comment is posted before the teacher enters the written-item points, so Canvas has no complete quiz result yet. Never build a whole-quiz score from the written portion and the subtotal together. A work file whose attempt shows `auto_scored_note` instead has no subtotal; the comment simply omits that line.

## Save, report, post

Start each results file with `init_results` and the packet path from the pull report (CLI: `.\cse.cmd results-init PACKET`). It creates `courses/<course>/assignments/<id>-<slug>/scoring/results-<YYYYMMDD>-<HHMM>.md` with the packet and its assignment snapshot, an exact component/criterion field example, every student's work-file path and exact attempt, the right operation and any discussion-evidence digest already filled in, flags excused, late, unreadable-file and partial-discussion students in a comment, and reuses an earlier results file's interpretation and `scoring_basis` for the same assignment. You fill the interpretation (unless reused), each student's components and feedback; until then it fails validation, so it can never post half-written. Without the tool, write the same file by hand. Run `.\cse.cmd validate <results-file>` to check criterion arithmetic (ordinary grade `assessment` may be omitted; the Engine fills it in). Then run the review in `review.md` on the finished file, including every possible-AI-use flag, and validate again after applying its rulings.

### Report in the conversation

When the scoring is done and valid, report it here rather than sending the teacher to a page. Keep it short, one block per assignment (and per class when sections differ):

- overall impressions: what most students did well, the most common gap or misconception, and anything surprising, in two or three sentences
- how many students were scored and the distribution in assignment points, including median and rough spread ("median 7/10; most 6–9; four below 5"). Offer one or two hypothetical curve options only when the distribution warrants it and state their numerical effect. No curve is applied; applying one requires a separately requested feature. For a New Quiz, report ranges per written part in item points; Canvas computes the quiz total once item scores are written, so quote a total only from Canvas. Never guess a total or silently apply effort floors to item points or fudge points
- one typical, non-held student’s exact Engine-rendered comment by alias, from `.\cse.cmd validate RESULTS --show STUDENT_REF` (MCP `validate_document {path, show: STUDENT_REF}`). Use the returned text verbatim, never paraphrase it. The sample exposes no submission or private teacher notes; held selections return only the reason. With item scores the sample lists what goes into the quiz: each item's points and comment, then any whole-assignment comment
- each held student by alias with the specific reason, and missing submissions as a count
- possible AI use or copying, headed "For your review", one entry by alias per student whose flag the arbiter upheld: each suspect phrase quoted exactly (a sentence or less each, at most three), the signal it shows ("matches another student's second paragraph word for word" (give that student's alias), "this quote isn't in the novel", "far beyond their last three responses", "college-level syntax from a Silver-tier student in on-level ELA7"), and a plain overall read (strong or weak). Suggest how the teacher could check, such as asking the student to explain a passage or looking at the document's version history. Say nothing about students you didn't flag, and leave this item out when no one is flagged
- late timing that was corrected or held, and any accommodation applied, without the private basis
- for exemplars, which prompts have them ready
- any question the arbiter referred to the teacher, such as "Ten students wrote 'The author's purpose is to show…'. Did that come from you?" When the teacher says it did, treat it as teacher-provided wording for every student

Do not paste every student's feedback. A teacher who wants to read it all can have a Draft PDF of the results file (`save_draft_pdf`): one student per page, held students marked; `handout: true` prints only each student's posted feedback, for handing back on paper. Then ask whether to post. The teacher may ask to see a student's feedback, ask for a change ("go easier on the thesis criterion", "redo Maya's"), or hold someone back. Make exactly the requested change to exactly those students, validate again and report only what changed. A change to the shared interpretation or scoring basis applies to every student. To hold a student back, remove that student's row from the results file before posting; they stay ungraded in Canvas and come back in the next scoring session. Post with `.\cse.cmd post <results-file>` (MCP: `post_results`) when the teacher says to. When the teacher already asked to score and post, post first, then give the same report with the outcomes.

If the teacher asks for a nicer page, write a one-off local HTML file in the course’s scoring folder in UserInstall, using aliases unless names are requested and with no approve or post buttons. Never publish it to a cloud page or sharing service because it holds student work; posting still happens through the conversation.

Report posted, held and failed students from the Engine's output. Explain each held student specifically. Before posting, the Engine checks whether the exact comment text is already present to avoid posting an identical comment twice. Once Canvas accepts a write, treat it as done: do not read it back or rerun just to confirm. If Canvas reports a genuine write error, rerun the same results file to resume; completed writes stay complete. A requested reassessment uses a fresh pull and new results file.
