# Versions and releases

The current version is **1.8** (`1.8.0`), released from `main` on 2026-10-29 as GitHub's latest release: Engine-written New Quiz item scores and item comments, working uploaded-file pulls, agentic review of student-facing content, hot-spot quiz items, small text corrections and hidden student names in raw Canvas reads. The previous releases are **1.7** (`1.7.0`, New Quiz accommodations, differentiation tags, shared rubrics and content edits, 2026-10-28), **1.6** (`1.6.0`, weekly ELA parent updates, 2026-10-26), **1.5** (`1.5.0`, honest-effort floor grades, 2026-10-24), **1.4** (`1.4.0`, chat check-ins and Draft PDF, 2026-10-24), **1.3** (`1.3.0`, teaching defaults, 2026-10-24) and **1.2** (`1.2.0`, team teaching, 2026-10-22); **1.1 beta 4** (2026-10-21) and **1.0** (`1.0.0`, 2026-10-17) came before it. Pushing to `dev` does not publish a release or update UserInstall.

The READMEs link to the latest published release rather than naming a version. Root `VERSION` is the single authority for CLI/help, embedded default builds, loaded MCP adapter identity, generated Cowork manifest and artifact filenames. The source Cowork manifest is a packaging template; `${CE_SE_VERSION}` is replaced before distribution. Do not install that template directly.

Increment beta releases consecutively (`1.0.0-beta.2`, `1.0.0-beta.3`, …). When the beta is ready for stable release, change VERSION to `1.0.0`. After stable release, use patch versions for compatible corrections, minor versions for compatible capabilities, and major versions for intentional breaking contract or installation changes. Document meaningful changes and migration steps in the release notes; keep historical evidence labels intact.

Normal builds are **development** builds. They carry the canonical product version, Git revision (`+dirty` when Dev has uncommitted changes), UTC build time and `build_kind development`. Plain `go build` uses `development`/`unrecorded` identity defaults. `cse version --json` exposes these non-secret fields; MCP initialization and `engine_info` identify the adapter loaded in memory separately from the child Engine started on disk. A version number alone does not certify live client or Canvas behavior.

`scripts/package.ps1 -Release` is the explicit release build route. It requires a clean checkout and an existing immutable `v<VERSION>` Git tag pointing at HEAD. The scripts never create commits/tags, push, sign or publish. Review the changes and local validation first, commit through the project's ordinary process, and create the matching tag only when intentionally releasing. Published tags and assets must never be moved or replaced: fix a release with the next version. The scripts refuse to overwrite an existing versioned release ZIP/MCPB in `dist/release/`. Generate and preserve one approved artifact set; rebuilding can change timestamps and checksums.

Ordinary builds produce only the current output set in `dist/` (`cse.exe`, `cse-mcp-launcher.exe`, `CanvasExpert-SE-<VERSION>.zip`, `SHA256SUMS.txt`) with no dated or versioned siblings; the Engine inside identifies itself as a development build. `-Release` additionally writes the immutable public assets to `dist/release/`: `CanvasExpert-SE-<VERSION>-windows-amd64.zip`, `CanvasExpert-SE-Cowork-<VERSION>-windows-amd64.mcpb` and `SHA256SUMS-<VERSION>.txt`. That is the only place release names appear, so a dirty local preview is never mistaken for a release. Publish those immutable versioned assets when distributing a release, plus a copy of the ZIP named `CanvasExpert-SE-windows.zip`. Every release carries that same file name, so `https://github.com/longhornteacher/canvasexpert-se/releases/latest/download/CanvasExpert-SE-windows.zip` always resolves to the newest release; agents install and update from it. Mark stable releases as latest: GitHub's latest link skips pre-releases. Checksums detect changed bytes; they are not a signature or a claim of publisher verification.

The ZIP includes VERSION, the MIT LICENSE and Engine third-party notices. The extension includes its required license/notices. None of these packaging steps change a teacher's UserInstall, credentials, client configuration or Canvas. Teacher instructions, drafts and unsent work remain subject to the existing preservation rules when updating an actual UserInstall.

Before public distribution, verify the packaged executable and MCP launcher using synthetic fixtures; inspect archive contents, manifest version/target and checksums; and report the real destination-client/fresh-user pilot status separately. The Windows CI workflow is configured for build/package and local MCP smoke checks, but configuration alone does not establish that CI has run remotely. The current packaging work produces unsigned local artifacts, not a published release.

## Git install distribution

`scripts/package-userinstall.ps1` builds the git-install distribution from one flattened tree: `workspace-template/` without `context/` and `Teacher_Override.md`, plus `VERSION`, `LICENSE`, `webui.cmd`, the shortcut icon `engine/canvasexpert.ico`, `get-engine.cmd`, a `.gitignore` for teacher and runtime paths, and `engine/manifest.txt`. The manifest is a plain `key=value` file (`version`, `identity`, `base_url`, and `sha256.<file>` for `cse.exe` and `CanvasExpert-SE-Cowork.mcpb`) that `get-engine.cmd` reads with only `curl.exe` and `certutil`. From that tree the script writes the Engine assets (`<OutputDirectory>/assets`), a fallback ZIP (the tree plus `engine/cse.exe` and the extension) and, with `-UpdateBranch`, one local commit on the orphan `userinstall` branch made through a temporary index, so the checkout, HEAD and index are untouched. It never pushes, tags or publishes. A `-Release` build needs a release compile; any other build needs `-BaseUrl`. The `.mcpb` is not byte-reproducible, so rebuilding changes the manifest hash and produces a new branch commit.

`get-engine.cmd` downloads and verifies the manifest's files into `engine/staged/` (`--stage` stops there), then renames a live `cse.exe` to `cse.exe.previous` and moves the staged files into `engine/`. Exit codes: 3 checksum mismatch, 4 missing tool or manifest, 5 download failed, 6 the running Engine could not be replaced. `package.ps1` and its ZIP are unchanged and remain the fallback until the migration finishes.

To release by git: build with `package-userinstall.ps1 -Release -UpdateBranch`, check the tree and assets, push the `userinstall` branch (it only ever appends commits; never rewrite it) and publish the release assets named in the manifest (`cse.exe`, `CanvasExpert-SE-Cowork.mcpb`) under the tag `v<VERSION>`, so the manifest's `base_url` resolves. The release (1.7.0 and 1.8.0) carries exactly four assets: those two, `assets/SHA256SUMS.txt`, and this script's fallback ZIP (`CanvasExpert-SE-<VERSION>-userinstall.zip`) published as `CanvasExpert-SE-windows.zip`. That ZIP holds the full teacher tree, playbooks included, so `install.md` updates a ZIP install from a temporary extraction rather than extracting over the folder. Publish the assets before pushing the branch: a teacher whose update stages the new manifest before the assets exist fails the download quietly and retries the next day, but a pushed branch with missing assets would keep failing. Teachers stage and apply the update themselves (see `playbooks/install.md`).
