# CanvasExpert-SE architecture

Updated 2026-10-29 (reusable teacher preferences, course notes and assignment expectations/exemplars follow active teacher setup; grading/planning session files stay local). Current development direction is here and in [SCORING-RULES.md](SCORING-RULES.md). Earlier briefs and evidence live only in Git history and are not implementation prerequisites.

## Intent and engineering default

CE-SE is an independent teacher tool distributed under the MIT license. The agent supplies intent, educational judgment, and content; the Engine (a portable Go CLI) and plain workspace files execute tasks against Canvas Live. Optimize for successful work with little friction, speed, and practical accuracy. Ordinary repairable imperfections are acceptable. The current product line is 1.0; `VERSION` is the release-version authority, and [the release policy](releasing.md) distinguishes published releases from development builds.

Prefer direct implementations using existing packages. Add a defensive branch or abstraction when a supported workflow needs it, a real failure demonstrates its value, or a cheap check prevents a consequential mistake. Hypothetical edge cases alone do not justify expansion. Validate at useful boundaries, continue independent items when one fails, and explain uncertainty honestly without turning unverified assumptions into prohibitions.

Test changed behavior in proportion to its consequences. Reuse tests and add focused regressions for meaningful behavior. Cosmetic changes and straightforward reversible rearrangements do not automatically need tests. Do not create coverage quotas, branch matrices, source-text architecture tests, or incidental snapshots. Finish after relevant checks pass; broaden only for a concrete concern.

Preserve useful content and teacher intent rather than byte equality of unrelated state. A renamed assignment does not invalidate a score; dates affect lateness; a new attempt needs assessment; an unreadable optional attachment is reported without inventing contents.

## Vocabulary

Use these names for folders. They describe the task and ownership, regardless of which agent app is used.

The distribution flow is **Dev → userinstall branch → UserInstall**, with optional **UserInstall ↔ UserSync**. A release flattens `workspace-template/` into an orphan `userinstall` branch (`scripts/package-userinstall.ps1`); a teacher's clone of it is already UserInstall, and `get-engine.cmd` downloads and checksum-verifies the Engine named in `engine/manifest.txt`. The same tree plus the Engine is the fallback ZIP. In a git install git owns the playbooks, `TEACHER.md` and the root `AGENTS.md`/`CLAUDE.md`; only `context/`, `Teacher_Override.md` and the teacher's own root guides follow UserSync (`IsSharedRulePathIn`), and `playbooks update` changes nothing. Updates are staged quietly (`git fetch` plus a verified Engine download) and applied with the teacher's yes or at the next session start. First setup connects apps and Canvas in place; it does not copy the product into a second folder. These are role names, not required directory names.

Keep existing command and storage contracts: `cse install` means connect/setup this UserInstall; `--workspace`, `install_root`, `rules_root`, `sync_root`, and mode values `local`/`sync` retain their spelling. No folder rename, saved-data migration or client re-registration is required just for this terminology change. In ordinary teacher conversation, say "your CanvasExpert-SE folder" and "your Sync folder".

Preference read failures use the system palette with a separate notice and never block ordinary work or fall back to inactive local settings. The dedicated local save changes no teaching data and preserves unsaved page state.

CE-SE directly accesses selected shared files rather than replicating them; the cloud provider synchronizes UserSync. Rule of thumb: if it needs judgment, it goes in a playbook or the context; if it needs Canvas access, exact identity or exact math, it goes in the Engine.

Results scaffolds include the pulled assignment snapshot. Handwritten results may omit it; validation and review resolve it from the packet in memory and never rewrite saved drafts or invalidate their hashes. Posting persists the resolved snapshot with its action outcomes. A feedback-only comment (`comment-only`, `header: none`, no components) needs no scoring basis or interpretation; supplied scores still validate, and existing identity/attempt/evidence and duplicate checks remain in force. Such comments do not mark New Quiz written work as scored for session discovery.

One UserInstall folder by default. A teacher clones (or unzips) one **CanvasExpert-SE** folder, points Code/Codex at it and says "set this up" (or "install this"); the setup agent connects the selected destination and opens the private WebUI for the Canvas PAT. UserInstall contains the Engine in `engine/` and lives on the local drive because district OneDrive sync blocks executables. The Engine carries the starter playbooks and context from Dev. UserInstall holds the teacher's actual playbooks and context (started from the seed, theirs to change) and student information (`.cse/`, `courses/`). New program versions add missing seed files and never overwrite teacher files automatically. The bundled Engine binds CLI, WebUI and direct MCP to UserInstall regardless of the agent's current directory; a conflicting explicit root fails with an installation mismatch. The WebUI shows UserInstall's location as read-only information and never selects or restores another teacher folder. Developer test binaries retain advanced explicit `--workspace` roots. The new Cowork extension carries a thin launcher targeting UserInstall's Engine rather than its own Engine; actual destination-client adoption remains pending. UserSync optionally holds authoritative reusable teacher setup; commands and grading/planning session state remain in UserInstall.

## Reusable teaching context (2026-10-29)

`workspace-template/playbooks/teacher-context.md` defines agent-maintained memory, using existing shared-context routing rather than a new Engine policy schema. `Teacher_Override.md` records standing changes to shipped defaults; `context/teaching-profile.md` and `context/grading.md` retain general facts and preferences. `context/courses/<course-id>/notes.md` holds course-only norms and taught skills. `context/courses/<course-id>/assignments/<assignment-id>.md` holds reusable task expectations, teacher decisions, explicit local scoring basis/interpretation when needed, and authored models for written prompts. Each scoped note records Canvas origin and exact IDs; a New Quiz uses its associated assignment ID and actual written-item IDs. `context/courses.md` remains the unchanged structured course configuration. The context README files supply outlines, not prepopulated teacher facts.

Agents save clear ongoing teacher requests/corrections with scope, date and source during ordinary work, preserving prior choices and keeping tentative inferences distinct. Authoring prepares models with the local draft, reviews verbal and intellectual fit to the actual grade/taught skills, then saves reusable expectations after accepted creation. Exact-question quiz models remain private until intended release. Accepted substantive edits update affected guidance; unsent changes remain local. Scoring compares saved expectations with the normal current pull, uses the live rubric when present, and treats models as calibration, never hidden criteria or required wording. Missing notes do not block ordinary work. Equivalent cross-section tasks may share a scale only after confirming requirements and mapping destination IDs.

These paths already follow the configured teacher-setup authority: UserInstall by default, UserSync when selected. In git installs product playbooks/instructions remain git-managed in UserInstall. Reusable assessment guidance is shared, while student responses/excerpts, result rows, drafts, write receipts and grading/planning sessions remain local. File-tool hash guards preserve intervening teacher edits. Educational calibration and remembering choices are playbook judgment; local routing tests do not prove provider delivery, agent adoption or classroom calibration.

## Spine and operation boundaries

UserSync must contain no CE-SE `.cmd` launchers. CE-SE's `cse.cmd` and `webui.cmd` belong in local UserInstall. MCP-connected agents access UserInstall's instructions, playbooks and context through tools; no CE-SE launcher or copy of UserInstall belongs in UserSync. MCP registrations target UserInstall. The optional extension launcher forwards stdio to UserInstall's `engine/cse.exe`; direct registration starts that Engine itself. Old extensions with a separately bundled Engine need explicit replacement through the client.

Ordinary setup creates a per-user **CanvasExpert WebUI** desktop shortcut targeting UserInstall's `webui.cmd`, with UserInstall as its working directory. Windows resolves the actual Desktop location, including redirected desktops. Repeating setup reuses the same shortcut; an existing shortcut for another target is preserved and reported. Shortcut failure is nonfatal and leaves `webui.cmd` available. Read-only setup inspection and checks do not create a shortcut. The shortcut is machine integration, not reusable teacher setup, and moving UserInstall requires reconnecting its paths.

```text
Agent (follows a playbook) -> Engine: typed MCP / cse CLI / hub -> feature operation -> shared spine -> Canvas Live
The Engine and student/course work stay in UserInstall; teacher rules resolve to UserInstall or the explicitly configured UserSync authority.
```

The seed lives in `workspace-template/`; judgment belongs in the playbooks and context.

`cse mcp` is a local stdio adapter, not a separate Canvas implementation. Its typed tools expose supported Engine commands, workspace instruction/draft/asset access, and existing local review/setup/student pages. It invokes allowlisted existing commands, with QuizForge local validation reusing the workflow validator. No arbitrary shell or HTTP-write tool exists; `canvas_get` retains the CLI's deliberate read-only API exception and can return raw names. The adapter keeps file access outside hidden/private/Engine paths and rejects links beneath the workspace. Existing-file hashes protect unsent work; course writes stay under `courses/`. Teacher-only setup/student pages return only their local URL and lifecycle status, not private contents.

MCP `list_courses` reads saved nickname/id/current/timezone configuration on every call by default (`source: configured`) and includes root/instance metadata; this works offline and sees WebUI saves without restart. Explicit `source: canvas` uses the existing CLI catalog discovery. Setup checks structured courses rather than preserved starter prose. MCP initialization directs the agent to read workspace `AGENTS.md` and the task's playbook, so separate folder sharing is unnecessary. Posting scope, honest assessments, the teacher's go-ahead in the conversation and task-specific resume decisions remain in those playbooks; direct typed write tools add no Engine approval token. Local desktop Cowork and Work use the same stdio surface; optional hosted tunnel access is a separate client route. Local tests establish implementation behavior, not client compatibility or Canvas Live results; see [the MCP adapter guide](mcp-adapter.md).

### Engine packages

| Package | Responsibility |
|---|---|
| `internal/canvas` | Origin, authenticated HTTP, pagination, ordinary API errors and downloads |
| `internal/workspace` | Paths, configuration, file I/O and stable student identity |
| `internal/platform` | Per-machine credentials, portable startup and Windows integration |
| `internal/workflow` | Feature operations and their relevant preconditions, outcomes and recovery; Service supplies shared dependencies |
| `internal/domain`, `internal/render` | Feature contracts, rubric arithmetic, feedback and content rendering |
| `cmd/cse`, `internal/localui` | CLI entry points and temporary setup/student/settings UI |
| `internal/mcpserver` | Typed local MCP command/file adapter and temporary page lifecycle; no educational judgment |

A normal Go function/package is a module. A feature usually adds an operation, command entry point and short playbook. Shared utilities emerge from actual use. Assignment editing shares Canvas transport and workspace I/O but owns its field patch and conflict checks. Feedback revision uses those same mechanics but owns selection and recovery of an exact comment ID. Grading semantics belong with grading, even when several grading functions share them.

Keep the existing layout and useful transport, parsing, identity and arithmetic code. Do not introduce a plugin loader, registry, event bus, job engine, persistence layer, universal policy schema, arbitrary-HTTP write interface for the agent (the read-only `cse api PATH` GET is the deliberate exception, decided 2026-10-10: when the Engine gets stuck the agent reads directly, the teacher makes any write in Canvas, and the gap goes in the workspace `context/engine-notes.md` for development) or new agent protocol. Large files alone do not require splitting.

## Teacher decisions and working behavior

- Teacher instructions authorize the requested scope: score and post posts, draft does not. No mandatory preview/apply tokens. **Decided 2026-10-10, changed 2026-10-24:** the gate is a check-in in the conversation. Before posting scores, creating assignments or quizzes, or editing assignments, the agent reports the work there (for scores: ranges, general impressions, held students) and writes on the teacher's go-ahead; a request that already includes the write ("score and post", "create it") is the go-ahead. Rubric attachments and page edits are not gated. Scoring/authoring page commands were retired on 2026-10-28; offline `validate RESULTS --show STUDENT_REF` / `validate_document.show` returns one exact feedback sample through the shared draft renderer. Private family review and Draft PDF remain. The gate is the Playbook instruction, not an Engine token.  Scoring session alone pulls current-course work and asks what to do; it never implies posting.
- Canvas Live governs existing content. Pull before editing; send only requested changes. Preserve unsent edits when replaced content conflicts, return a fresh version, and let the agent reapply. Read-before-write checks reduce conflicts but cannot eliminate a concurrent edit race.
- Assess honestly. For ordinary assignments, post the Engine's computed assessment even below an existing entered grade; the teacher handles later adjustments. For New Quiz written work, post truthful criterion scores in the comment-only feedback and leave quiz/item grades to the teacher. The agent compares with the strongest earlier academic attempt from actual work, not a teacher-adjusted grade. See scoring rules for arithmetic and posting behavior.
- Use the official Canvas rubric when present, and a common-sense local scoring basis otherwise. A missing Canvas rubric is not a blocker. Rubrics the Engine attaches have automatic grading disabled; existing coupling is not silently changed. Ordinary assignment grading posts the honest rubric and computed grade, including coupled assignments. New Quiz written-work scoring uses the rubric as a scoring basis without writing a rubric assessment. An accepted grading/comment write counts as done: report once and stop, without a post-write readback or reply-shape confirmation. Preserve pre-write identity, attempt, scope, basis and duplicate checks, and explain actual failures or held items. No workspace certification is needed.
- Canvas alone calculates late point penalties. Broad scoring pulls use `--session`/`session: true` to find unscored submissions Canvas reports as needing grading, including work not yet due. Session discovery does not use grading periods; assignments Canvas marks as in a closed grading period are reported without pulling submissions. A bare session request returns the list and asks what to score; a narrowed request is applied from the report's assignment-group and due-state columns. New attempts after grading are ordinary work and are assessed normally. Already-scored work is not re-read or re-timed in a session. Prepare timing only for work being scored; attach prepared timing to grade rows. The explicit non-session `late-only` operation remains for already-graded timing tasks. The Engine reads `context/school-calendar.md` to count from the applicable deadline to the selected first genuine submission, preserves the Canvas due date separately, and writes only late-policy status and seconds-late override. Unclear dates, attempts, visibility or Canvas timing hold only the timing action. New Quiz comment-only results carry no lateness actions; when a current-attempt comment is already posted but Canvas still awaits item points, report the count and remind the teacher to enter them in SpeedGrader.
- Parent reports require a valid school calendar with one active grading period. Each saved run records its period, timezone, retrospective date window and upcoming boundary; the Engine builds complete due-based inventory from student-visible published assignments and individualized effective dates. Missing/0, correction and history lists are derived only from that inventory. Default email and print render the full inventory regardless of which rows the agent selects for draft text; the explicitly requested weekly ELA email layout instead renders its computed Missing and Failing lists. A saved report without scope is preserved and cannot be sent or printed; pull a fresh report.
- Posting holds only for changes to points, rubric, grading type or grading mode; the Engine does not read directions at post.
- Ordinary assignment feedback begins with the computed assessment, then compact per-response criterion scores, then conversational glows/grows. New Quiz written-work comments begin with criterion scores and omit an aggregate quiz assessment. Full criterion definitions stay in the rubric; context/grading.md can shape voice.
- The agent infers response units, rubric application and weights consistently; no hardcoded three-response or equal-weight recipe. A deliberately absent Canvas rubric may use an explicit local scoring basis.
- Completed action records refer to the course/student/attempt, not permanent exact output. Teacher feedback/rubric edits do not automatically enqueue completed attempts. New attempts remain discoverable; explicit scoped pulls permit reassessment. Uncertain creates require bounded identity lookup, known IDs when available, and an explanation if ambiguous; never blind replay.
- Newly created assignments stay unpublished until requested rubric/module pieces succeed. Save returned IDs for resumption. "Pending my finalization" means post directly to Canvas, then the teacher reviews and may leave it unchanged. There is no pending state or approval polling. Private family review waits for the teacher’s send decision; "pending" stays a local file state. Posting policy and SIS sync are outside scope.

## UserInstall and platform

Windows 11, standard user, no installer/admin/runtime requirement for teachers. Go builds a portable executable; platform/distribution checks are ordinary release work, not workspace certifications. The package is one folder with the Engine in `engine/`; on a hub or MCP launch, the embedded Playbook seed adds missing files without overwriting work. Temporary loopback UI exists only while its command runs. No resident service or database.

PAT and Canvas origin live in per-machine Windows Credential Manager. Never expose the PAT in files, logs, output or agent context. Private student mapping stays in the active authority�s .cse/students.csv and out of ordinary agent reads; private contact JSON has the same exclusion. Stable student references target persisted work; aliases decorate filenames/metadata and remain editable. Real names are allowed in student writing and teacher notes; do not scrub writing. Expand intentional name placeholders only, and keep teacher-only notes out of student feedback.

**Team courses (1.2.0-beta.1).** A teammate's Canvas key is a named Credential Manager entry, `CanvasExpert-SE/Canvas/v1/teammate/<canvas_user_id>`, on the team PC only; the team list is `context/team.md` (labels, names, emails, key expiry, no secrets), each teammate's preferences are `context/team/<label>.md`, and every write made with a teammate's key is appended to `.cse/team-log.jsonl` in UserInstall. A course with an `owner` in `courses.md` routes to the owner's key unless the operator is an active teacher in that course, in which case the operator's key is used; a transient Canvas error never switches the key. Consent (only `(CE)` assignments are scored) and hiding (grades go in with manual posting for the teammate to post) attach to **ownership**, not to whichever key was routed, so the rules hold even when the operator's key does the work.

Workspace context maps course nicknames (CS8, ELA7PAP, ELA7), grading preferences and student notes. Plain files support authoring/resumption; pulled data is disposable, while unsent work and ordinary returned IDs/outcomes are preserved. One teacher uses one machine at a time; no locks, sync merge system, backup ledger or permanent gradebook.
