# CE-SE MCP adapter

Updated 2026-10-12. `cse mcp` runs a local stdio server on the Windows computer containing local CE-SE **Install** and the saved Canvas credential. Its 26 typed tools cover every currently supported Engine command and the workspace files needed to use those commands. It reuses existing Engine operations; it accepts neither arbitrary shell commands nor arbitrary HTTP writes. Future capabilities are not included in this parity claim.

**Source** is the development checkout (code, starter templates and build/release artifacts); **Install** is the local runnable CE-SE folder with course/student configuration and work; optional **Sync** is a dedicated locally accessible OneDrive/Google Drive directory for authoritative teacher rules. An agent developing CE-SE uses Source; an agent doing teacher work uses Install, regardless of the app. MCP's workspace tools retain logical paths and root metadata refers to Install. Teacher instructions, playbooks, root .md/.txt guides (except product README.md) and context references resolve to Sync when configured; `context/courses.md`, `context/students.md`, course work, private state and integration glue stay local. MCP runs Install's Engine directly; the teacher-first Cowork extension is a thin launcher targeting that same Engine and Install. The Source bundle builder uses this thin launcher too; a previously installed old extension may still carry an older executable until the client reconnects through the new route. The provider synchronizes Sync; CE-SE performs no replication.

New Quizzes, including written-response items, are open for regular authoring, use and scoring within supported limits. Use an explicitly scoped `pull_work` for the quiz assignment ID and `operation: comment-only` results for written-work review/post. Criterion scores appear in a submission comment without an aggregate quiz assessment; the teacher enters per-item points in SpeedGrader. This operation carries no grade, rubric-assessment or late writes. Pending live/human evidence is not a prohibition or a preliminary test required for each task. Read Install's scoring playbook and `engine_reference` formats/examples for the exact contract.

Teacher-provided run evidence, 2026-10-11: cloud Claude through remote-devices completed teacher-reviewed creation and reported fresh Canvas readbacks for one unpublished assignment and one unpublished MC/TF/ESSAY New Quiz in CS8, plus ordinary student text/history pulls and local canonical scoring validation. This establishes that route's authoring/read workflow, not direct desktop Work/Cowork compatibility, real-student grade/comment posting, student rendering, or persistence across local MCP restarts. The [run review](../handoffs/active/COWORK-RUN-REVIEW-20261011.md) led to locally verified contract and review fixes: routing uses file contents, an optional assignment/results course must match the document, and QuizForge reviews require a course. `validate_quiz` now checks the same settings as review/push. Canonical top-level rationales appear in review; inline item/choice rationales fail with a correction hint, and other unknown item/choice keys warn. Read the supported QuizForge contract and synthetic MC/TF/ESSAY example through `engine_reference` before authoring.

## Tools and workflow

| Tool | Purpose |
|---|---|
| `engine_reference` | Command help, file formats, field limits, synthetic examples. |
| `engine_info` | Version/build information, dummy credential self-test (`doctor`), executable launcher registration (`link`), or teacher rules location status/setup. |
| `list_courses`, `list_modules` | Read saved course selections by default (`source: configured`); explicit `source: canvas` discovers the live Canvas catalog. Read configured-course modules. |
| `pull_assignment`, `pull_page` | Pull exact content and its edit baseline. |
| `pull_work` | Pull pseudonymized student work/history/attachments, optionally scoped to a course and assignment. |
| `list_workspace_files` | Discover allowed workspace files/directories, optionally recursively. |
| `read_workspace_file` | Read root Markdown/text references (including `AGENTS.md`, `CLAUDE.md`, `README.txt`), `context/`, `playbooks/`, or `courses/` text and its SHA-256. |
| `write_workspace_file` | Save teacher instructions, context, and playbooks with conflict protection. |
| `write_draft` | Save `.md`, `.yaml`, `.yml`, `.json`, or `.txt` course drafts with conflict protection. |
| `read_workspace_asset`, `write_asset` | Read/save base64 course attachments and assets with hashes. |
| `validate_document`, `validate_quiz` | Local Engine document or QuizForge validation. |
| `start_review`, `review_status` | Teacher review, revision notes, and actual posting/creation outcomes. |
| `push_document` | Assignment/Page/module create, resume, update, or assignment/New Quiz rubric attachment as specified by the document. |
| `post_results` | Scoped computed assessment, rubric, feedback, late timing, or selected feedback revision. |
| `push_quiz` | Supported QuizForge New Quiz authoring/resumption, including written items and hub differentiation. |
| `upload_file` | Explicit course/access/folder asset upload with a reusable course receipt and deliberate new-upload option. |
| `list_quiz_points`, `set_quiz_points` | Inspect or change exact decimal New Quiz question points. |
| `canvas_get` | Existing read-only Canvas API GET escape hatch, one page per call. |
| `start_local_ui`, `local_ui_status` | Teacher-only hub, setup, and student editor pages; return URLs/status without private page contents. |

Read saved configuration first with `list_courses`: the default configured source returns JSON `source`, `root`, `instance` and `courses` (including inactive courses, with nickname/id/current/timezone fields and an empty array when none exist). Each call reads the current course file without Canvas credentials or requests. WebUI course saves appear on the next call without restarting MCP. Use `source: canvas` to test the connection or choose additional courses; CLI `courses` remains Canvas catalog discovery. Setup status comes from structured courses, not obsolete starter prose in the preserved document body.

Begin by reading `AGENTS.md` with `read_workspace_file`, then the relevant playbook. Separate folder sharing is unnecessary for these files. The initialization instructions also direct the client to this workflow. Use `engine_reference` for contracts rather than inventing fields.

Configure shared rules only after the teacher supplies a dedicated directory. CLI `cse rules-location` reports status; `cse rules-location --sync "PATH"` explicitly selects Sync and `cse rules-location --local` returns to Install. Settings offers the same operation. Status distinguishes `install_root`, `rules_root` and mode; `list_courses.root` stays Install. Empty Sync starts from current customized rules, existing Sync becomes authoritative, and local originals are preserved. Logical file reads and writes use the active file and its hash; changes appear on the next call without restarting MCP. If configured Sync is unavailable, report the path error without silently reading inactive local rules. Independent local course/work operations remain available. Local-agent AGENTS.md/CLAUDE.md bootstraps point to shared teacher instructions while commands and work stay in Install. Returning to local copies readable shared rules, archives differing local copies and leaves Sync intact.

Typed MCP: `engine_info` with `operation: "rules-location"` returns status (mode `local` or `sync`) and an `availability_error` when needed. `operation: "set-rules-location", sync_root: "ABSOLUTE PATH"` explicitly selects Sync; an empty `sync_root` selects Install. This operation changes only local file authority and never Canvas. Preserved originals are under Install's private `.cse/rules-archive/`; explicit hub playbook replacement archives the active prior version under its rules root's `playbook-old/`. Do not read private archives through other tools to bypass MCP exclusions.

Review remains the default for scores, new assignments/quizzes, and assignment edits. Start the review, present the loopback URL to the teacher, and check status for approval/outcomes or revision notes. Status includes `state` (`pending`, `finished`, or `failed`); a finished process can report a `partial` or `held` write outcome, so inspect the outcome and readable details. Only pending sessions return a usable review URL. Completion returns the resulting file path and any revision notes; a busy-slot refusal names the active review ID. An MCP permission prompt is not approval on the CE-SE review page. Direct posting/creation tools are available when the teacher explicitly skips review for that task, or when resuming a partly created item as the playbook permits. Pages, uploads, native module assembly, and rubric attachment follow requested scope directly. There is no extra Engine approval token.

Open returned `127.0.0.1` links on the computer running CE-SE. The teacher alone operates setup/student pages, which can contain credentials and real identities; the agent must not fetch or inspect those pages. Review pages display the computed assessment and intended content. MCP process shutdown closes its child pages. A slow-starting page remains discoverable through its status tool.

## Teacher-first desktop installation

The release leads with the teacher's three steps: unzip on the local drive; open Install in Code/Codex and say "install this for Cowork/Work"; enter Canvas address and PAT in the private WebUI. Packaged `AGENTS.md` routes to `playbooks/install.md`, distinct from normal Canvas/course setup. Source, developer runtimes, terminal commands and a separate Codex CLI are unnecessary on the teacher's computer.

The installing agent runs Install's bundled `cse install --inspect` for read-only configuration-directory hints and uses a supported actual app inventory when available. Directory presence does not prove an app is installed, running or in a supported destination mode. The teacher's named destination authorizes its selected registration; when unclear, one plain Cowork-or-Work question is enough. There is no default registration of both clients.

The agent then runs `cse install --client work|cowork` (one selected client). This helper uses narrowly scoped registration with backup and preservation, checks the local MCP using the SDK without Canvas writes, and opens the WebUI directly without waiting for the destination to restart. `--check-only` performs diagnostics; `--no-ui` suppresses the WebUI for explicit diagnostics. Another Install's existing CE-SE entry requires an explanation of the old/new folders before `--replace-existing`. Neither repeat registration nor replacement migrates teacher files or erases unsent work. Do not dump whole client configuration into agent output.

Work registration writes the supported desktop host configuration without requiring `codex` on PATH, respecting configured Codex home and other settings. This does not configure hosted Work. Cowork prepares a ready extension and returns `extension_path` for the app's trust/install action. Its thin launcher points to this Install's `engine/cse.exe`: updating Install updates the authoritative Engine rather than leaving a second Engine in the extension. Selected destination availability, extension trust and organizational controls still depend on the actual app. Cowork destination adoption through this thin route remains pending a real-client pilot.

Engine starts, configuration saved (or extension prepared), local MCP check passed and destination tool access are different outcomes. A successful subprocess handshake, tool discovery and local instruction/course read do not prove destination access. After the necessary trust/reconnect action, the destination agent must actually read current `AGENTS.md`, the relevant playbook and configured `list_courses`, confirming the returned Install root. Loaded MCP adapter identity is reported separately from the child/on-disk Engine identity; a stale loaded adapter needs reconnect after active review work finishes.

The installer gives the exact short `TEACHING-ASSISTANT.md` starter if no supported app action can prepare a teaching chat. It establishes the assistant role and current-file reads without copying full playbooks into client instructions or claiming a project was created. `setup.md` offers existing teacher-selected instruction carryover or gradual grade/subject, priorities, standards and feedback elicitation. Plain `context/teaching-profile.md` follows active Install/Sync authority; `grading.md` remains the feedback preference file. Existing preferences are merged, not overwritten. Assignment, quiz, native-content authoring and scoring consult this context; developer ELA7 classes/tags are not colleague defaults. An incomplete profile never creates a questionnaire prerequisite.

The teacher alone operates the private setup form; the agent sees only non-secret outcomes. Missing/rejected credentials can justify token setup. Network/outage/proxy/TLS failures do not establish that a PAT needs replacement, so saved credentials and course selections stay intact. Sync remains optional.

For advanced direct configuration, use stdio, an absolute local Engine path and arguments stored separately: `--workspace`, the absolute Install path, `mcp`. A bundled Engine also accepts just `mcp`, resolving its own Install independently of working directory and rejecting a conflicting explicit root. Never register against Sync; keep launchers on the local drive. The machine's Canvas credential is not client configuration. The Source `scripts/connect-mcp.ps1` and optional `scripts/package-mcp.ps1` are historical/developer conveniences, not release prerequisites. [Official OpenAI MCP documentation](https://learn.chatgpt.com/docs/extend/mcp) describes direct stdio and shared desktop/Codex configuration.

Fresh-user ZIP extraction under a standard Windows account, actual selected destination adoption, WebUI PAT entry and a teacher-judged small lesson/feedback example remain pending. Local fixtures establish mechanics, not completion of this user journey or pedagogical quality.

## Hosted ChatGPT and optional tunnel

Hosted ChatGPT Work uses plugins/remote MCP tools rather than reading local Codex configuration. This differs from desktop Work's direct stdio connection. An optional [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) can connect a local server to supported hosted contexts without a public inbound endpoint. Follow that guide for tunnel/account setup, key handling, and permissions; point its MCP command at `cse.exe --workspace <workspace> mcp`. The tunnel is not required for the two desktop clients. Hosted account/policy availability and tunnel operation are not verified by CE-SE's local tests.

## Data and validation boundaries

Text transfers are limited to 1 MiB. Base64 asset read/write transfers are limited to 20 MiB decoded. Larger files already staged in an allowed workspace folder can still be passed to `upload_file`; its upload is not subject to the base64 transfer limit. Uploads require an explicit reusable receipt path under `courses/`. Existing files require their current SHA-256 before replacement. Recursive listing is bounded to 2,000 entries.

File tools block hidden components, `.cse/`, and `engine/`, including linked paths such as junctions/symlinks beneath the workspace. Reads are limited to the allowed instruction/context/playbook/course roots; course drafts and assets stay under `courses/`. Student writing can itself contain real names. Unlike pseudonymized `pull_work`, `canvas_get` returns raw Canvas JSON and can include real names. Teacher notes intentionally read from context also enter model context; keep them out of student-facing output. The credential and private identity mapping are not file-tool inputs or returned setup/student page contents.

Cowork desktop initialization/tool discovery and enabled connector were observed; the shared Work/Codex client runtime successfully called workspace reading and Engine version tools. The teacher-provided cloud Claude remote-devices run described above subsequently established reviewed Canvas authoring and ordinary student pulls through that route. Existing CLI Canvas evidence does not establish those client workflows. Report the Engine's held/partial/uncertain output accurately, preserve receipts and saved IDs, and continue independent items.

Local single-folder checks cover bundled-root selection from another directory, conflicting-root rejection, developer/extension overrides, MCP-first seed preservation and WebUI course saves observed by an already-connected MCP client without Canvas calls. These do not establish the behavior of already-running old binaries or corrected client registrations.

The reproducible compiled smoke check is `node scripts/check-mcp.mjs dist/cse.exe`. For an actual local review/revision check, use `--review` and set `CSE_MCP_CHECK_ORIGIN` to the machine's saved Canvas origin; this requires the existing saved connection but makes no Canvas writes.

Existing installations retain their current `AGENTS.md` and `playbooks/setup.md`, even after an Engine update. To adopt the revised course-discovery instructions, use Settings -> Your playbooks and context -> Get the new version for those files; their previous copies are archived under `playbook-old/`. Review any teacher customizations and carry them forward as needed. No existing instruction or context file is automatically overwritten.
