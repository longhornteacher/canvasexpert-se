# CE-SE MCP adapter

`cse mcp` runs a local stdio server on the Windows computer that holds the CE-SE **UserInstall** and the saved Canvas credential. Its typed tools cover supported Engine commands and the workspace files needed to use them. They reuse existing Engine operations; the adapter accepts neither arbitrary shell commands nor arbitrary HTTP writes. Future capabilities are not included in this parity claim.

Terms: **Dev** is the development checkout (code, starter templates, build/release artifacts). **UserInstall** is the local runnable CE-SE folder with course/student configuration and work. Optional **UserSync** is a dedicated, locally accessible OneDrive/Google Drive directory holding authoritative teacher rules. Developing CE-SE uses Dev; teacher work uses UserInstall, regardless of the agent app. MCP workspace tools use logical paths, and root metadata refers to UserInstall.

When UserSync is configured, teacher instructions, playbooks, root `.md`/`.txt` guides (except the product `README.md`) and context references resolve to UserSync. Saved course configuration, student notes, aliases/settings and private roster/contact records also use UserSync. `.cse/` remains excluded from agent tools, including contact JSON. Grading/planning session files, course work and machine integration stay local. The provider synchronizes UserSync; CE-SE performs no replication. MCP runs the UserInstall's Engine directly; the Cowork extension is a thin launcher targeting that same Engine and UserInstall.

New Quizzes, including written-response items, are open for regular authoring, use and scoring within supported limits. For written-work review/post, use an explicitly scoped `pull_work` for the quiz assignment ID and `post_results` with `operation: comment-only`. Criterion scores appear in a submission comment without an aggregate quiz assessment; the teacher enters per-item points in SpeedGrader. This operation carries no grade, rubric-assessment or late writes. Read the UserInstall's scoring playbook and `engine_reference` formats/examples for the exact contract, including the supported QuizForge contract and its synthetic MC/TF/ESSAY example. `validate_quiz` checks the same settings as review/push. QuizForge reviews require a course; an optional assignment/results course must match the document. Canonical top-level rationales appear in review; inline item/choice rationales fail with a correction hint, and other unknown item/choice keys warn.

### Workflow

Begin by reading `AGENTS.md` with `read_workspace_file`, then the relevant playbook; the server's initialization instructions direct clients to do the same. Use `engine_reference` for contracts rather than inventing fields.

**Courses.** `list_courses` with the default configured source returns JSON `source`, `root`, `instance` and `courses` (including inactive courses, with nickname/id/current/timezone fields, and an empty array when none exist). Each call reads the current course file without Canvas credentials or requests, so WebUI course saves appear on the next call without restarting MCP. Use `source: canvas` to test the connection or choose additional courses; CLI `courses` remains Canvas catalog discovery. Setup status comes from the structured courses, not obsolete starter prose in the preserved document body.

**Review.** Review is the default for scores, new assignments/quizzes, and assignment edits. Start the review, present the loopback URL to the teacher, and check status for approval/outcomes or revision notes. Status includes `state` (`pending`, `finished`, or `failed`); a finished process can report a `partial` or `held` write outcome, so inspect the outcome and readable details. Only pending sessions return a usable review URL. Completion returns the resulting file path and any revision notes; a busy-slot refusal names the active review ID. An MCP permission prompt is not approval on the CE-SE review page. Direct posting/creation tools are available when the teacher explicitly skips review for that task, or when resuming a partly created item as the playbook permits. Pages, uploads, native module assembly, and rubric attachment follow requested scope directly. There is no extra Engine approval token.

**Local pages.** Open returned `127.0.0.1` links on the computer running CE-SE. The teacher alone operates setup/student pages, which can contain credentials and real identities; the agent must not fetch or inspect them. Review pages display the computed assessment and intended content. MCP process shutdown closes its child pages. A slow-starting page remains discoverable through its status tool.

### PATH and portable startup

Teacher setup does not add anything to PATH. Work/Codex and Antigravity registrations store an absolute path to UserInstall's `engine/cse.exe`; the Cowork extension launches its bundled thin launcher, which invokes that same absolute Engine path. `cse.cmd` and `webui.cmd` resolve the Engine relative to themselves. Use an explicit launcher path (or `engine/cse.exe`) from the agent's shell. No Go, Node, PowerShell or separate agent CLI is needed for these packaged routes. If UserInstall moves, reconnect apps to the new path; PATH changes will not repair a stale registration.

The Dev checkout has separate build tooling requiring Go, PowerShell and Git. Its unshipped `register-cse.cmd` convenience helper now calls the selected UserInstall's Engine directly. Browser opening and folder selection use native Windows APIs; the Explorer fallback resolves Windows' directory through the OS rather than searching PATH. The legacy `program.txt` launcher fallback is a per-machine pointer, not a PATH entry, and is unnecessary for a complete extracted package.

### Shared rules location (UserSync)

Configure shared rules only after the teacher supplies a dedicated directory. CLI `cse rules-location` reports status; `cse rules-location --sync "PATH"` selects UserSync and `cse rules-location --local` returns to UserInstall. Settings offers the same operation. Via MCP, `engine_info` with `operation: "rules-location"` returns status (mode `local` or `sync`, `install_root`, `rules_root`, and an `availability_error` when needed), and `operation: "set-rules-location", sync_root: "ABSOLUTE PATH"` selects UserSync (an empty `sync_root` selects UserInstall). This changes only local file authority and never touches Canvas; `list_courses.root` stays UserInstall.

An empty UserSync starts from the current customized rules; an existing UserSync becomes authoritative; local originals are preserved under the UserInstall's private `.cse/rules-archive/`. Returning to local copies readable shared rules, archives differing local copies and leaves UserSync intact. Logical file reads and writes use the active file and its hash, and changes appear on the next call without restarting MCP. If configured UserSync is unavailable, the error names the path, there is no silent fallback to inactive local rules, and operations requiring shared setup report that error. Local-agent `AGENTS.md`/`CLAUDE.md` bootstraps point to shared teacher instructions while commands and work stay in UserInstall. Do not read private archives through other tools to bypass MCP exclusions.

### Playbook status and replacement

Compare seed-managed instructions and playbooks with `cse playbooks status` or `engine_info` operation `playbooks-status`. Each row reports `same`, `missing`, `differs` or `unavailable`, the active file's SHA-256 when present, and whether the file is replaceable. A difference does not mean a file is old. To adopt one eligible seed, use `cse playbooks replace PATH --expected-sha256 HASH` or operation `replace-playbook` with `path` and `expected_sha256` (use `missing` only when status reports the file absent). A stale hash, context preference, or unavailable UserSync leaves the active file untouched; context preferences are never eligible. The prior active file is archived first under that authority's `playbook-old/`. Existing installations keep their `AGENTS.md` and `playbooks/setup.md` across Engine updates; no instruction or context file is overwritten automatically, and the teacher can adopt new seeds from Settings -> Your playbooks and context -> Get the new version.

### Doctor

`cse doctor` runs a fixed checklist: running Engine/build identity, UserInstall readability, active `AGENTS.md` and setup playbook readability, `context/courses.md` parsing, saved Canvas-origin consistency, the temporary native dummy credential round trip, an authenticated read-only `GET /api/v1/users/self`, and the same-UserInstall hub identity endpoint. The Canvas request has a five-second deadline, sends no writes, discards the returned account identity, and never returns Canvas response data. Outcomes:

- A missing saved credential is `not_configured`.
- HTTP authentication rejection is `fail`.
- Transport, DNS, TLS, proxy, service-outage and unusable-response errors are `not_verified` and do not imply the credential needs replacement.
- Hub health means only that a loopback process answered with this UserInstall's identity. It does not show that a browser page appeared or that a destination adopted MCP. With no healthy hub, the action is `cse ui`; doctor never opens a private page.
- An unavailable configured UserSync is an active-rules failure, with no local fallback.

`cse doctor --offline` skips the Canvas and loopback hub requests and marks them `not_verified`. `cse doctor --json` emits the checklist as JSON and exits nonzero for failed checks. MCP `engine_info` with `operation: "doctor"` returns the whole checklist even when a check fails; `offline: true` suppresses network checks. Doctor does not inspect student files or client settings and does not alter rules, bindings, configuration or real credentials. The normal hub launcher reports whether it requested a browser launch or the launch call failed, separately from HTTP availability.

## Connecting a client

The teacher-facing first-run flow (unzip locally, ask an agent to install for Work/Cowork, enter the Canvas address and PAT in the private WebUI) is documented in the shipped `playbooks/install.md` in the UserInstall; the packaged `AGENTS.md` routes there. Dev, developer runtimes, terminal commands and a separate Codex CLI are not needed on the teacher's computer. This section covers the adapter-side behavior.

**Work/Codex registration (desktop).** `cse install --client work` registers the supported desktop host configuration with narrowly scoped edits, backup and preservation, without requiring `codex` on PATH and respecting a configured Codex home and other settings. It checks the local MCP through the SDK without Canvas writes and opens the WebUI directly without waiting for the destination to restart. This does not configure hosted Work.

**Cowork extension.** `cse install --client cowork` prepares a ready extension and returns `extension_path` for the app's trust/install action. Its thin launcher points to the UserInstall's `engine/cse.exe`, so updating the UserInstall updates the authoritative Engine rather than leaving a second Engine in the extension. The Dev bundle builder (`scripts/package-mcp.ps1`, an internal step of `scripts/package.ps1`) produces this same thin launcher; an older installed extension may still carry an older executable until the client reconnects through the new route. Extension trust and organizational controls depend on the actual app.

**Antigravity registration.** `cse install --client antigravity` merges the `canvasexpert-se` stdio entry (`--workspace <UserInstall> mcp`) into `~/.gemini/config/mcp_config.json`, keeping other servers and settings, backing up first, leaving an identical entry unchanged and requiring `--replace-existing` for another UserInstall.

**Installer behavior.** With no `--client` (or `auto`/`all`), `cse install` registers every client whose configuration folder exists (Claude `cowork`, ChatGPT/Codex `work`, Antigravity `antigravity`) and reports each outcome; one failing does not stop the others. A single `--client` still registers just that app. `cse install --inspect` is a read-only hint of configuration directories; directory presence does not prove an app is installed, running or in a supported mode. `--check-only` performs diagnostics; `--no-ui` suppresses the WebUI. Another UserInstall's existing CE-SE entry requires explaining the old/new folders before `--replace-existing`. Neither repeat registration nor replacement migrates teacher files or erases unsent work. Do not dump whole client configuration into agent output. If no supported app action can prepare a teaching chat, the installer gives a short `TEACHING-ASSISTANT.md` starter that establishes the assistant role and current-file reads without copying playbooks into client instructions.

Ordinary install also creates a **CanvasExpert WebUI** shortcut on the current user's Windows desktop, targeting this UserInstall's `webui.cmd`; WebUI app-connection setup uses the same operation. `--no-ui` suppresses launching, not shortcut creation. Inspection, check-only and invalid invocations create no shortcut. Repeated setup reuses a shortcut for this target; another target's same-named shortcut is preserved and reported. Shortcut failure is a separate nonfatal warning with `webui.cmd` as the fallback, so registration and local checks continue. The shortcut stores a local launcher path, not a temporary authenticated browser URL.

**Advanced direct stdio.** Use stdio with an absolute local Engine path and separate arguments: `--workspace`, the absolute UserInstall path, `mcp`. A bundled Engine also accepts just `mcp`, resolving its own UserInstall independently of the working directory and rejecting a conflicting explicit root. Never register against UserSync; keep launchers on the local drive (district OneDrive can block executables). The machine's Canvas credential is not client configuration. `scripts/connect-mcp.ps1` in Dev is a developer convenience, not a release prerequisite. [Official OpenAI MCP documentation](https://learn.chatgpt.com/docs/extend/mcp) describes direct stdio and shared desktop/Codex configuration.

**Hosted ChatGPT (optional).** Hosted Work uses plugins/remote MCP tools rather than reading local Codex configuration, unlike desktop Work's direct stdio connection. An optional [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) can connect a local server to supported hosted contexts without a public inbound endpoint; follow that guide for account setup, key handling and permissions, and point its MCP command at `cse.exe --workspace <workspace> mcp`. The tunnel is not required for the desktop clients.

### What counts as working

These are different outcomes: the Engine starts; configuration is saved (or the extension prepared); the local MCP check passed; and the destination actually uses the tools. A successful subprocess handshake, tool discovery and local instruction/course read do not prove destination access. After the needed trust/reconnect action, the destination agent must actually read current `AGENTS.md`, the relevant playbook and configured `list_courses`, confirming the returned UserInstall root. Loaded MCP adapter identity is reported separately from the child/on-disk Engine identity; a stale loaded adapter needs a reconnect after active review work finishes.

The teacher alone operates the private setup form; the agent sees only non-secret outcomes. Missing or rejected credentials can justify token setup; network/outage/proxy/TLS failures do not, so saved credentials and course selections stay intact. UserSync remains optional.

## Data and validation boundaries

- Text transfers are limited to 1 MiB. Base64 asset read/write transfers are limited to 20 MiB decoded. Larger files already staged in an allowed workspace folder can still be passed to `upload_file`, whose upload is not subject to the base64 limit.
- Uploads require an explicit reusable receipt path under `courses/`. Replacing an existing file requires its current SHA-256.
- Recursive listing is bounded to 2,000 entries.
- File tools block hidden components, `.cse/` and `engine/`, including linked paths such as junctions/symlinks beneath the workspace. Reads are limited to the allowed instruction/context/playbook/course roots; course drafts and assets stay under `courses/`.
- The credential and private identity mapping are not file-tool inputs or returned setup/student page contents.
- Student writing can itself contain real names. Unlike pseudonymized `pull_work`, `canvas_get` returns raw Canvas JSON and can include real names. Teacher notes read from context also enter model context; keep them out of student-facing output.
- Report the Engine's held/partial/uncertain output accurately, preserve receipts and saved IDs, and continue independent items.

## Checks

The reproducible compiled smoke check is `node scripts/check-mcp.mjs dist/cse.exe`. For a local review/revision round trip, add `--review` and set `CSE_MCP_CHECK_ORIGIN` to the machine's saved Canvas origin; this needs the existing saved connection but makes no Canvas writes.

## Evidence limits

Local tests establish mechanics (tool registration, scoped files, arguments, QuizForge validation, page lifecycle, root selection), not live Canvas behavior, destination-client adoption, or pedagogical quality. The authoritative, current verification status of each capability (Canvas Live evidence vs. local tests vs. pending human validation) is kept in `docs/engine-capabilities.md` and the WebUI Capabilities page in the CE-SE Dev repository; consult those rather than treating this guide as proof of any client workflow.

Individual book-club audiences use `prepare_audience`, `start_review` and `push_document` for assignment create or initial `assignment-dates` application. The Engine preserves student submissions/grading semantics and manual exceptions, refuses stale/incomplete audiences, saves exact owned overrides and does not replay accepted or uncertain writes. Explicit refresh uses the latest saved ownership and preserves protected/unknown recipients, manual exceptions and accepted outcomes. Course Pages and New Quizzes use the same `prepare_audience` intent and `push_document`. See the individual-club assignment, Page and quiz examples in `engine_reference`.

`prepare_audience {course, path, refresh: true}` accepts an existing prepared assignment-dates audience, a saved assignment create receipt, a course Page or a New Quiz. Its JSON includes workspace-relative `path` for the new action; use it for `start_review` and `push_document`. The original receipt links to the latest action and keeps its create IDs/outcomes. The review and push response show safe completed changes, actual applied managed refs, protected work and unknown evidence. A stale manual/owned/visibility baseline holds the affected work. Pending/uncertain writes must be resumed from their existing action, never erased by preparing a replacement.

Course Pages use the same `prepare_audience` call before `push_document`. Push creates the Page unpublished, applies the complete date-details restriction, finishes requested module placement and publishes last; a refused or uncertain audience never publishes. An audience-only update after a live body edit sends no body or title PUT. Pages have no submission evidence route, so refresh removals are not work-protected; manual rows, availability dates and newer teacher edits are preserved.

New Quizzes use the same `prepare_audience` call before `push_document` (or `push-quiz`). The audience restricts the quiz's exact associated assignment, so the quiz stays one gradebook column and each student answers independently. Push creates the quiz, adds items, applies settings and module placement, applies the audience and publishes last; a refused or uncertain audience never publishes. The sidecar records accepted stages, so a resume repeats only unfinished work. Audience-only refresh returns an `assignment-dates` action and sends no quiz, item or settings write; New Quiz attempts and grades protect removals.
