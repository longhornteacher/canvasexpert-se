# CanvasExpert-SE architecture

Updated 2026-10-15 (UserSync preserves reusable teacher setup; grading/planning session files stay local). Current development direction is here and in [SCORING-RULES.md](SCORING-RULES.md). Earlier briefs and evidence live only in Git history and are not implementation prerequisites.

## Intent and engineering default

CE-SE is an independent teacher tool distributed under the MIT license. The agent supplies intent, educational judgment, and content; the Engine (a portable Go CLI) and plain workspace files execute tasks against Canvas Live. Optimize for successful work with little friction, speed, and practical accuracy. Ordinary repairable imperfections are acceptable. The current product line is 1.0 beta; `VERSION` is the release-version authority, and [the release policy](docs/releasing.md) distinguishes published releases from development builds.

Prefer direct implementations using existing packages. Add a defensive branch or abstraction when a supported workflow needs it, a real failure demonstrates its value, or a cheap check prevents a consequential mistake. Hypothetical edge cases alone do not justify expansion. Validate at useful boundaries, continue independent items when one fails, and explain uncertainty honestly without turning unverified assumptions into prohibitions.

Test changed behavior in proportion to its consequences. Reuse tests and add focused regressions for meaningful behavior. Cosmetic changes and straightforward reversible rearrangements do not automatically need tests. Do not create coverage quotas, branch matrices, source-text architecture tests, or incidental snapshots. Finish after relevant checks pass; broaden only for a concrete concern.

Preserve useful content and teacher intent rather than byte equality of unrelated state. A renamed assignment does not invalidate a score; dates affect lateness; a new attempt needs assessment; an unreadable optional attachment is reported without inventing contents.

## Vocabulary

Use these names for folders. They describe the task and ownership, regardless of which agent app is used.

The distribution flow is **Dev → ZIP → UserInstall**, with optional **UserInstall ↔ UserSync**. Dev's `dist/CanvasExpert-SE-<VERSION>.zip` is the user distribution. Extract it into the local folder where it will run: that folder is already UserInstall. First setup connects apps and Canvas in place; it does not copy the product into a second folder. These are role names, not required directory names.

Keep existing command and storage contracts: `cse install` means connect/setup this UserInstall; `--workspace`, `install_root`, `rules_root`, `sync_root`, and mode values `local`/`sync` retain their spelling. No folder rename, saved-data migration or client re-registration is required just for this terminology change. In ordinary teacher conversation, say "your CanvasExpert-SE folder" and "your Sync folder".

| Folder | What it holds | Who uses it |
|---|---|---|
| **Dev** | Development checkout: code, starter templates, Engine contracts, build tools; `dist/` holds generated release artifacts | An agent developing CE-SE, typically Claude Code/Codex |
| **UserInstall** | One local runnable CE-SE folder: `engine/`, the teacher's actual instructions, playbooks, context, drafts, pulled work and private runtime data | An agent doing teacher work, typically Cowork/GPT Work; Claude Code/Codex also use UserInstall for teacher work |
| **UserSync** | Optional dedicated locally accessible OneDrive/Google Drive directory | Authoritative reusable teacher setup, including course selections, student settings/notes and private contacts; provider synchronization handles delivery |

Develop in Dev, teach from UserInstall, optionally share teacher rules through UserSync. The extracted release folder is UserInstall; a colleague does not need Dev. CE-SE directly accesses selected shared files rather than replicating them; the cloud provider synchronizes UserSync. Existing internal names such as `internal/workspace`, `--workspace`, and MCP workspace tools remain unchanged; their teacher-task root is UserInstall. Client configuration and Windows Credential Manager are machine integration, not additional teacher folders.

**Reusable teacher setup, updated 2026-10-15:** optional UserSync is the authoritative home of teacher-customized instructions, playbooks, root Markdown/text guides (except product README.md) and context references. Each UserInstall reads and edits those files directly; the provider handles delivery. Without a binding, one-folder ownership stays in UserInstall. `context/courses.md`, `context/students.md`, `.cse/students.csv`, `.cse/rosters.json` and `.cse/student-contacts.json` also use UserSync. Private contact JSON is not ordinary agent context: the WebUI alone edits one student email and repeatable parent phone/email rows with separate text/email preferences. No parent names or language fields are collected. US phones normalize to xxx-xxx-xxxx; missing destinations are allowed even with Yes selected. Contact identity uses Canvas instance and user ID. Student aliases, monitoring, extra-time settings, stable references and notes survive a replacement PC. Existing rules-only bindings copy missing setup files into UserSync once and preserve local originals; existing UserSync files win. Grading/planning session files, pulled work, drafts, posting records, credentials, Engine and machine integration stay local. These sessions are deliberately not durable across PCs. The per-UserInstall `.cse/rules-location.json` binding stores the explicit absolute UserSync directory; Settings, CLI `rules-location` and MCP `engine_info` expose mode and UserInstall/rules roots. Reads reload the binding and active files, with no stale local fallback if UserSync is unavailable. Empty UserSync initializes from current customized rules; existing UserSync wins. Local originals are preserved before AGENTS.md/CLAUDE.md become bootstraps directing local agents to shared authority. Explicit return to local preserves readable shared rules and archives differing local copies. Seed updates add missing files at their active location; explicit replacement archives the replaced active file and protects context preferences.  Temporary local fixtures establish shared-file routing, not provider propagation or human-client adoption.

| Name | What it is | Where it lives | Its job |
|---|---|---|---|
| **CE-SE** | The whole product | Developed in Dev; used from UserInstall | n/a |
| **Engine** | The Go program: `cse.exe` CLI plus the local hub pages | Dev: `cmd/`, `internal/`. UserInstall: `engine/cse.exe` | Mechanical work the agent can't do reliably: talk to Canvas, keep student, attempt and assignment identity straight, exact score arithmetic, safe write recovery. No educational judgment. |
| **Playbook** | The instruction set the agent follows for one kind of task. A teacher says "scoring playbook" and the agent reads that file. Every judgment call about scoring, assignments and policy is the teacher's and agent's, and lives here | Dev seed: `workspace-template/playbooks/` (embedded in the Engine). Teacher's copy: UserInstall `playbooks/` (plus the standing `AGENTS.md`, `CLAUDE.md`) | Tells the agent how to do a job: score, create an assignment, edit one, set up |
| **Context** | The teacher's preferences and facts the playbooks draw on | Dev seed: `workspace-template/context/`. Teacher's copy: UserInstall `context/` | Feedback voice, grading habits, student notes, courses, calendar |
| **Agent** | Claude or ChatGPT working with UserInstall for a teacher task | n/a | Makes the judgment calls using the playbooks and context, then hands decisions to the Engine |

Rule of thumb: if it needs judgment, it goes in a playbook or the context; if it needs Canvas access, exact identity or exact math, it goes in the Engine.

One UserInstall folder by default. A teacher unzips one **CanvasExpert-SE** folder, points Code/Codex at it and says "set this up" (or "install this"); the setup agent connects the selected destination and opens the private WebUI for the Canvas PAT. UserInstall contains the Engine in `engine/` and lives on the local drive because district OneDrive sync blocks executables. The Engine carries the starter playbooks and context from Dev. UserInstall holds the teacher's actual playbooks and context (started from the seed, theirs to change) and student information (`.cse/`, `courses/`). New program versions add missing seed files and never overwrite teacher files automatically. The bundled Engine binds CLI, WebUI and direct MCP to UserInstall regardless of the agent's current directory; a conflicting explicit root fails with an installation mismatch. The WebUI shows UserInstall's location as read-only information and never selects or restores another teacher folder. Developer test binaries retain advanced explicit `--workspace` roots. The new Cowork extension carries a thin launcher targeting UserInstall's Engine rather than its own Engine; actual destination-client adoption remains pending. UserSync optionally holds authoritative reusable teacher setup; commands and grading/planning session state remain in UserInstall.

## Spine and operation boundaries

UserSync must contain no CE-SE `.cmd` launchers. CE-SE's `cse.cmd` and `webui.cmd` belong in local UserInstall. MCP-connected agents access UserInstall's instructions, playbooks and context through tools; no CE-SE launcher or copy of UserInstall belongs in UserSync. MCP registrations target UserInstall. The optional extension launcher forwards stdio to UserInstall's `engine/cse.exe`; direct registration starts that Engine itself. Old extensions with a separately bundled Engine need explicit replacement through the client.

```text
Agent (follows a playbook) -> Engine: typed MCP / cse CLI / hub -> feature operation -> shared spine -> Canvas Live
The Engine and student/course work stay in UserInstall; teacher rules resolve to UserInstall or the explicitly configured UserSync authority.
```

The seed lives in `workspace-template/`; judgment belongs in the playbooks and context.

`cse mcp` is a local stdio adapter, not a separate Canvas implementation. Its 29 typed tools expose all currently supported Engine commands, workspace instruction/draft/asset access, and existing local review/setup/student pages. It invokes allowlisted existing commands, with QuizForge local validation reusing the workflow validator. No arbitrary shell or HTTP-write tool exists; `canvas_get` retains the CLI's deliberate read-only API exception and can return raw names. The adapter keeps file access outside hidden/private/Engine paths and rejects links beneath the workspace. Existing-file hashes protect unsent work; course writes stay under `courses/`. Teacher-only setup/student pages return only their local URL and lifecycle status, not private contents.

MCP `list_courses` reads saved nickname/id/current/timezone configuration on every call by default (`source: configured`) and includes root/instance metadata; this works offline and sees WebUI saves without restart. Explicit `source: canvas` uses the existing CLI catalog discovery. Setup checks structured courses rather than preserved starter prose. MCP initialization directs the agent to read workspace `AGENTS.md` and the task's playbook, so separate folder sharing is unnecessary. Posting scope, honest assessments, default review and task-specific skip/resume decisions remain in those playbooks; direct typed write tools add no Engine approval token. Local desktop Cowork and Work use the same stdio surface; optional hosted tunnel access is a separate client route. Local tests establish implementation behavior, not client compatibility or Canvas Live results; see [the MCP adapter guide](docs/mcp-adapter.md).

### Engine packages

| Package | Responsibility |
|---|---|
| `internal/canvas` | Origin, authenticated HTTP, pagination, ordinary API errors and downloads |
| `internal/workspace` | Paths, configuration, file I/O and stable student identity |
| `internal/platform` | Per-machine credentials, portable startup and Windows integration |
| `internal/workflow` | Feature operations and their relevant preconditions, outcomes and recovery; Service supplies shared dependencies |
| `internal/domain`, `internal/render` | Feature contracts, rubric arithmetic, feedback and content rendering |
| `cmd/cse`, `internal/localui` | CLI entry points and temporary setup/student/settings UI |
| `internal/mcpserver` | Typed local MCP command/file adapter and temporary page lifecycle; no educational judgment |

A normal Go function/package is a module. A feature usually adds an operation, command entry point and short playbook. Shared utilities emerge from actual use. Assignment editing shares Canvas transport and workspace I/O but owns its field patch and conflict checks. Feedback revision uses those same mechanics but owns selection and recovery of an exact comment ID. Grading semantics belong with grading, even when several grading functions share them.

Keep the existing layout and useful transport, parsing, identity and arithmetic code. Do not introduce a plugin loader, registry, event bus, job engine, persistence layer, universal policy schema, arbitrary-HTTP write interface for the agent (the read-only `cse api PATH` GET is the deliberate exception, decided 2026-10-10: when the Engine gets stuck the agent reads directly, the teacher makes any write in Canvas, and the gap goes in the workspace `context/engine-notes.md` for development) or new agent protocol. Large files alone do not require splitting.

## Teacher decisions and working behavior

- Teacher instructions authorize the requested scope: score and post posts, draft does not, "show me first" is the default review page (decided 2026-10-10). No mandatory preview/apply tokens. **Decided 2026-10-10, built for scoring (slices 1-2):** review is the default gate. The agent stops at its review page before posting unless the teacher explicitly skips review for that task (scoring, new assignments, new quizzes and assignment edits are gated; rubric attachments and page edits are not); "score and post" still sets scope. The gate is the Playbook instruction plus the command, not an Engine token.  Scoring session alone pulls current-course work and asks what to do; it never implies posting.
- Canvas Live governs existing content. Pull before editing; send only requested changes. Preserve unsent edits when replaced content conflicts, return a fresh version, and let the agent reapply. Read-before-write checks reduce conflicts but cannot eliminate a concurrent edit race.
- Assess honestly. For ordinary assignments, post the Engine's computed assessment even below an existing entered grade; the teacher handles later adjustments. For New Quiz written work, post truthful criterion scores in the comment-only feedback and leave quiz/item grades to the teacher. The agent compares with the strongest earlier academic attempt from actual work, not a teacher-adjusted grade. See scoring rules for arithmetic and posting behavior.
- Use the official Canvas rubric when present, and a common-sense local scoring basis otherwise. A missing Canvas rubric is not a blocker. Rubrics the Engine attaches have automatic grading disabled; existing coupling is not silently changed. Ordinary assignment grading posts the honest rubric and computed grade, including coupled assignments. New Quiz written-work scoring uses the rubric as a scoring basis without writing a rubric assessment. An accepted grading/comment write counts as done: report once and stop, without a post-write readback or reply-shape confirmation. Preserve pre-write identity, attempt, scope, basis and duplicate checks, and explain actual failures or held items. No workspace certification is needed.
- For ordinary assignment grading, Canvas alone calculates late point penalties. The agent works out lateness from the actual work, `context/school-calendar.md` and teacher notes, and supplies `grade.late_timing` (`status`, `seconds_late`, `due_at`, `basis`). The Engine writes the lateness timing the agent supplies after checking the attempt is current and the live due date still equals `due_at`; it does not read the calendar. Unclear inputs mean the agent omits timing and tells the teacher. New Quiz comment-only results carry no lateness actions.
- Posting holds only for changes to points, rubric, grading type or grading mode; the Engine does not read directions at post.
- Ordinary assignment feedback begins with the computed assessment, then compact per-response criterion scores, then conversational glows/grows. New Quiz written-work comments begin with criterion scores and omit an aggregate quiz assessment. Full criterion definitions stay in the rubric; context/grading.md can shape voice.
- The agent infers response units, rubric application and weights consistently; no hardcoded three-response or equal-weight recipe. A deliberately absent Canvas rubric may use an explicit local scoring basis.
- Completed action records refer to the course/student/attempt, not permanent exact output. Teacher feedback/rubric edits do not automatically enqueue completed attempts. New attempts remain discoverable; explicit scoped pulls permit reassessment. Uncertain creates require bounded identity lookup, known IDs when available, and an explanation if ambiguous; never blind replay.
- Newly created assignments stay unpublished until requested rubric/module pieces succeed. Save returned IDs for resumption. "Pending my finalization" means post directly to Canvas, then the teacher reviews and may leave it unchanged. There is no pending state or approval polling. A command that exits when the teacher clicks Post on a review page is not polling, and "pending" stays a local file state. Posting policy and SIS sync are outside scope.

## UserInstall and platform

Windows 11, standard user, no installer/admin/runtime requirement for teachers. Go builds a portable executable; platform/distribution checks are ordinary release work, not workspace certifications. The package is one folder with the Engine in `engine/`; on a hub or MCP launch, the embedded Playbook seed adds missing files without overwriting work. Temporary loopback UI exists only while its command runs. No resident service or database.

PAT and Canvas origin live in per-machine Windows Credential Manager. Never expose the PAT in files, logs, output or agent context. Private student mapping stays in the active authority�s .cse/students.csv and out of ordinary agent reads; private contact JSON has the same exclusion. Stable student references target persisted work; aliases decorate filenames/metadata and remain editable. Real names are allowed in student writing and teacher notes; do not scrub writing. Expand intentional name placeholders only, and keep teacher-only notes out of student feedback.

Workspace context maps course nicknames (CS8, ELA7PAP, ELA7), grading preferences and student notes. Plain files support authoring/resumption; pulled data is disposable, while unsent work and ordinary returned IDs/outcomes are preserved. One teacher uses one machine at a time; no locks, sync merge system, backup ledger or permanent gradebook.

## Current scope and future capabilities

Current operations cover course/module reads, assignment create/edit and rubric attachment, text submission/history pulls with attachments, component scoring, no-rubric scoring, assessment posting, feedback posting/revision, discovery, and local setup/student/settings pages. Attachments may be unreadable; report that honestly. Normal calls use current API responses and narrow action checks, not disposable-course proof in each workspace.

**New Quizzes are open for regular authoring, use and scoring within current supported limits**, including written-response items (`ESSAY`, `FILEUPLOAD`) and mixed quizzes. The agent pulls an explicitly selected quiz by assignment ID, reads typed responses and downloaded files, assesses them using the attached rubric or an explicit local scoring basis, and saves `operation: comment-only` results for review/post. Students receive truthful criterion scores and conversational feedback in a whole-assignment submission comment, without an aggregate quiz assessment. The Engine does not write New Quiz item points, quiz grades, rubric assessments or late timing in this workflow; the teacher enters item points in SpeedGrader. Broad course pulls include New Quizzes that have submitted work. An unreadable file or unmatched attempt affects that student specifically while independent work continues. See [the implementation contract](docs/new-quiz-written-work-spec.md) and UserInstall's scoring playbook.

A New Quiz can gain an independent rubric (`pull-item` + `attach-rubric`, useful for ECR/SCRs). Question-point changes use quiz-points before student submissions; subsequent point changes and existing question-content edits remain in Canvas. New Quiz authoring uses `push-quiz`, which reads QuizForge files (item types in `help formats`). Hub differentiation exists for assignments and New Quizzes; Hub is the only differentiation style, because the Bridge was declined. Standalone Pages use kind: page documents through push and pull-page, with explicit HTML/Markdown bodies and baseline field checks. Course assets use upload-file with explicit access and reusable receipts; kind: module documents assemble verified native references with saved item IDs. Shared rubrics and curves are future capabilities, not parity requirements. Differentiation uses teacher-managed Silver/Red/Blue tags in ELA7 only (Support/Core/Accelerate), with hints for everyone in the hub itself. Preserve those educational choices without building them to demonstrate modularity.

New Quiz written-work Engine paths have local tests; earlier hand-runs supply limited Canvas Live report/file/comment evidence. Some authoring paths, student rendering and limit enforcement still await live or human checks. State those evidence limits honestly while using the supported workflows; pending checks do not make New Quizzes off-limits or require a disposable-course probe before ordinary teacher work.

Historical platform and district observations remain in the evidence document and must not be presented as proof of the current build. Live experiments require a concrete authorized scope; saved credentials or historical IDs are not authorization.
