# Source development

**Developer or teacher?** If the user is writing code, fixing bugs, building the Engine, running tests or discussing architecture, follow this file. If they ask for classroom work (an assignment, a page, a quiz, scoring, class setup), stop acting as a software engineer: read [workspace-template/TEACHER.md](workspace-template/TEACHER.md) and the matching playbook, and speak in plain classroom terms. Real teacher work belongs in Install, not Source.

Use the folder names **Source**, **Install**, and **Sync** consistently. **Source** is this development checkout: code, starter templates, contracts and build tools. **Install** is the local runnable CE-SE folder: Engine, the teacher's actual playbooks/context, drafts, pulled work and private runtime data. **Sync** is optional teacher/agent cloud storage (OneDrive/Google Drive), independent of Install; CE-SE does not automatically synchronize them. Choose the folder by task: develop in Source, do teacher work in Install, regardless of which agent app is used. The internal `workspace` term and MCP workspace tools refer to Install during teacher work.

Configured Sync is the shared authority for teacher rules/preferences across PCs; each Install accesses it directly and the provider synchronizes files. The unconfigured default stays one folder. The shared/local boundary and preservation rules are in [ARCHITECTURE.md](ARCHITECTURE.md). Local fixtures verify routing; actual provider delivery and client adoption remain pending observation.

Optimize for the teacher completing the requested task with little friction. Use existing packages and direct implementations; add defenses for concrete supported workflows or consequential demonstrated failures. Keep validation at useful boundaries and tests proportionate to changed behavior. Do not add coverage quotas, certification rituals, universal operation frameworks, or speculative migrations.

A conceivable failure is not sufficient reason to add code, tests, or a prerequisite. Before expanding scope for an edge case, establish why it matters to the requested teacher workflow: observed occurrence or credible likelihood, consequence, whether the teacher would notice it, and the cost of ordinary recovery. Unknown frequency is not evidence of importance. For an uncommon, visible, cheaply repairable authoring mistake, prefer a clear explanation and teacher-directed correction or recreation when that loses no student work. Do not invent a recovery workflow, framework, or test matrix for it, and do not turn such findings into backlog items by default. Keep cheap checks for wrong-target writes, privacy exposure, dishonest grades, or loss of student/unsent work even when rare. This is a reasoning rule, not a requirement for a risk document or approval ceremony. A plan should deliver the requested capability; incidental findings become prerequisites only when they materially prevent that delivery.

Preserve teacher intent and unsent work. Canvas Live is authoritative. Check course/student/attempt identity, protect credentials and teacher-only notes, post the honest computed assessment, keep rubric assessments honest, and respect requested posting scope. Continue independent work when one item cannot proceed and explain that item specifically.

CE-SE has two parts: the **Engine** (Go code in `cmd/`, `internal/`: Canvas access, identity, exact math, safe writes) and the **playbooks and context** (all judgment; `workspace-template/` is their seed embedded in the Engine, and the Engine's own contract docs, such as the format reference, live with the Engine). Put judgment in the playbooks, not the Engine.

Read [ARCHITECTURE.md](ARCHITECTURE.md) and [SCORING-RULES.md](SCORING-RULES.md). The shipped workspace AGENTS.md is for teacher sessions; the old 0.1b brief is historical.

New Quizzes, including written-response items, are open for authoring, use and scoring within current supported limits. Written-work scoring uses the Engine's scoped pull and comment-only review/post path; the teacher enters item points in SpeedGrader. Keep evidence limits honest without treating pending live checks as a blanket prohibition or a prerequisite for ordinary teacher use.

Keep the WebUI Capabilities page current: when changes or findings affect a capability, limitation, or verification status, update the status data and review date in `internal/localui/capabilities.go` together with [docs/engine-capabilities.md](docs/engine-capabilities.md). Preserve the distinction between Canvas Live evidence, local tests, and pending human validation; local tests alone must not be presented as live proof.
