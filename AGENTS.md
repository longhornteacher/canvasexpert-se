# Dev development

**Installing CanvasExpert for a teacher?** Stop: this is the development source, not the teacher's folder. Don't build it. Follow "For AI agents installing or updating CanvasExpert for a teacher" in [README.md](README.md).

Distribution is **Dev → userinstall branch (git) → UserInstall**, with a ZIP as the fallback and optional **UserInstall ↔ UserSync**. `scripts/package-userinstall.ps1` builds the teacher-facing tree; a teacher's clone of the `userinstall` branch (or the extracted fallback ZIP) is already UserInstall and runs in place. In a git install git owns the playbooks and `AGENTS.md`/`CLAUDE.md`, and the teacher's choices live in `Teacher_Override.md` and `context/`. Setup connects apps and Canvas without creating a second product folder. These are role names, not mandatory directory names. Keep existing CLI/API/storage spellings (`install`, `--workspace`, `install_root`, `sync_root`, `local`/`sync`) compatible.

**Developer or teacher?** If the user is writing code, fixing bugs, building the Engine, running tests or discussing architecture, follow this file. If they ask for classroom work (an assignment, a page, a quiz, scoring, class setup), stop acting as a software engineer: read [workspace-template/TEACHER.md](workspace-template/TEACHER.md) and the matching playbook, and speak in plain classroom terms. Real teacher work belongs in UserInstall, not Dev.

Use the folder names **Dev**, **UserInstall**, and **UserSync** consistently. **Dev** is this development checkout: code, starter templates, contracts and build tools. **UserInstall** is the local runnable CE-SE folder: Engine, the teacher's actual playbooks/context, drafts, pulled work and private runtime data. **UserSync** is optional teacher/agent cloud storage (OneDrive/Google Drive), independent of UserInstall; CE-SE does not automatically synchronize them. Choose the folder by task: develop in Dev, do teacher work in UserInstall, regardless of which agent app is used. The internal `workspace` term and MCP workspace tools refer to UserInstall during teacher work.

Configured UserSync is the shared authority for reusable teacher setup across PCs (rules/preferences, course selections, student aliases/settings/notes and private contacts); each UserInstall accesses it directly and the provider synchronizes files. The unconfigured default stays one folder. The shared/local boundary and preservation rules are in [ARCHITECTURE.md](docs/ARCHITECTURE.md). Grading/planning session files stay in UserInstall. Local fixtures verify routing; actual provider delivery and client adoption remain pending observation.

Optimize for the teacher completing the requested task with little friction. Use existing packages and direct implementations; add defenses for concrete supported workflows or consequential demonstrated failures. Keep validation at useful boundaries and tests proportionate to changed behavior. Do not add coverage quotas, certification rituals, universal operation frameworks, or speculative migrations.

A conceivable failure is not sufficient reason to add code, tests, or a prerequisite. Before expanding scope for an edge case, establish why it matters to the requested teacher workflow: observed occurrence or credible likelihood, consequence, whether the teacher would notice it, and the cost of ordinary recovery. Unknown frequency is not evidence of importance. For an uncommon, visible, cheaply repairable authoring mistake, prefer a clear explanation and teacher-directed correction or recreation when that loses no student work. Do not invent a recovery workflow, framework, or test matrix for it, and do not turn such findings into backlog items by default. Keep cheap checks for wrong-target writes, privacy exposure, dishonest grades, or loss of student/unsent work even when rare. This is a reasoning rule, not a requirement for a risk document or approval ceremony. A plan should deliver the requested capability; incidental findings become prerequisites only when they materially prevent that delivery.

Preserve teacher intent and unsent work. Canvas Live is authoritative. Check course/student/attempt identity, protect credentials and teacher-only notes, post the honest computed assessment, keep rubric assessments honest, and respect requested posting scope. Continue independent work when one item cannot proceed and explain that item specifically.

CE-SE has two parts: the **Engine** (Go code in `cmd/`, `internal/`: Canvas access, identity, exact math, safe writes) and the **playbooks and context** (all judgment; `workspace-template/` is their seed embedded in the Engine, and the Engine's own contract docs, such as the format reference, live with the Engine). Put judgment in the playbooks, not the Engine.

Family emails about activities and reminders use the shared Family Contact flow ([contract](docs/family-contact-flow.md), seed `playbooks/family-contact.md`); book-club variants also use `family-contact-book-clubs.md`. Grade updates and printable reports retain the unchanged `parent-updates.md` playbook and grade-report guarantees. Teacher sends occur only through the private review page; developing this flow does not authorize real-family sends.

Read [ARCHITECTURE.md](docs/ARCHITECTURE.md) and [SCORING-RULES.md](docs/SCORING-RULES.md). The shipped workspace AGENTS.md is for teacher sessions; the old 0.1b brief is historical.

New Quizzes, including written-response items, are open for authoring, use and scoring within current supported limits. Written-work scoring uses the Engine's scoped pull and comment-only review/post path; the teacher enters item points in SpeedGrader. Keep evidence limits honest without treating pending live checks as a blanket prohibition or a prerequisite for ordinary teacher use.

Keep the WebUI Capabilities page current: when changes or findings affect a capability, limitation, or verification status, update the status data and review date in `internal/localui/capabilities.go` together with [docs/engine-capabilities.md](docs/engine-capabilities.md). Preserve the distinction between Canvas Live evidence, local tests, and pending human validation; local tests alone must not be presented as live proof.

**Group work (book clubs)** is specified in [docs/group-work/](docs/group-work/README.md): Tier A and B are implemented and live-checked on CS8 (evidence and limits in its README); Tier C (peer critique, calendars, group files, conference slots, Inbox messages) is frozen as "maybe nice for later" and is built only if the teacher asks. Read the README, the shared contracts and the relevant slice before touching group, discussion-evidence, shared-product or group-grading code. The standing teacher preferences for that work are in the README's Boundaries and the capability pages.

**Team teaching (1.2b1)** is specified in [docs/team/](docs/team/README.md), with retired execution handoffs in [handoffs/retired/team-1.2b1/](handoffs/retired/team-1.2b1/00-BRIEF.md). A course may have an `owner`; the Engine routes each course to the right Canvas key, requires the teammate's `(CE)` tag for scoring, writes grades hidden for the teammate to post, copies a Collab module at most once per course, and routes family replies to the actual teacher. Read the README before touching routing, consent, post-policy, copy or family-delivery code.
